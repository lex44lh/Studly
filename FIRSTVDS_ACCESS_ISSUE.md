## Проверка с VPN и без VPN — 17 октября около 03:47–03:53 МСК

- В текущем подключении агента SSH с диагностикой завершился `Connection refused` до авторизации, отдельная TCP-проверка порта 22 — тайм-аутом. HTTP на том же IP с Host `studly-help.ru` вернул `301` на HTTPS.
- `route -n get 153.76.172.88` показал интерфейс туннеля `utun6`. Владелец уточнил, что использует AdGuard VPN.
- Первый присланный владельцем тест был запущен из `root@slowwinplay`: это успешное подключение VPS к самому себе, оно не проверяет маршрут с Mac.
- Затем владелец открыл новое окно Терминала Mac (`viktorkovarov@MacBook-Pro-Viktor`), выключил VPN и успешно вошёл на VPS. Следовательно, SSH доступен по обычному подключению, а отказы наблюдаются на пути через VPN. Это не устанавливает конкретный источник фильтрации: ограничение может действовать в VPN, на промежуточном участке или на стороне сервера в отношении адреса VPN.
- Перезапуск ОС, смена SSH-порта, отключение Fail2ban и сброс firewall по этим данным не требуются. Сохранено открытое соединение владельца; настройки защиты нами не менялись.

Владелец добавил `studly-help.ru` в исключения сайтов AdGuard VPN, сохранив VPN включённым. После этого агент один раз успешно вошёл по ключу; около 03:58 МСК с VPS подтверждены активные службы Backend/Nginx, правильная A и отсутствие AAAA на всех четырёх NS Timeweb. Затем сеанс оборвался, новые подключения по IP и домену вновь получили `Connection refused`. Исключение домена пока не обеспечило устойчивый доступ, считать проблему решённой нельзя.

**Обновление около 04:04 МСК:** владелец добавил также сам IP `153.76.172.88` в тот же список исключений, VPN оставил включённым. Новый независимый SSH-вход агента только по ключу успешен. Журнал VPS подтвердил `Accepted publickey` с адреса обычного подключения владельца, в отличие от предыдущего успешного сеанса через адрес VPN. SSH/ssh.socket, Nginx и Backend активны. Fail2ban блокирует один другой адрес после неудачных парольных попыток; оснований отключать защиту или снимать эту блокировку нет.

Локально подтверждена версия AdGuard VPN 2.10.1; в ресурсах установленного приложения есть поле `Website or IP address` и проверка формата домена/IP (`Contents/Resources/sp-sciter-vpn_SciterVPN.bundle/Contents/Resources/locales/en.json`). Настройки VPN программно не изменялись. Поддержка исключений описана в [официальном обзоре AdGuard VPN для Mac](https://adguard-vpn.com/kb/adguard-vpn-for-mac/overview/). Для работы сохранять исключение именно IP VPS: один домен ранее не обеспечил устойчивый доступ. VPN для чата остаётся включённым. Точный источник отказов на прежнем пути через VPN не установлен; доступ удалось восстановить обходом этого пути.

Около 04:10 МСК выполнен ещё один независимый вход агента по ключу: успешен, Nginx/Backend/Certbot timer активны. Основной сеанс использован для выпуска и проверки HTTPS. Если отказы повторятся, через открытое соединение владельца нужно проверить текущие `ssh`/`ssh.socket`, прослушивание порта 22, Fail2ban и журнал SSH в момент отказа. Прежние внутренние проверки не заменяют текущую диагностику. Архивный текст обращения ниже не отправлять как актуальное описание.

## Основания для обращения

Статус Active и результат VNC сообщены владельцем. Результаты SSH/TCP получены проверками с Mac; они не доказывают конкретную причину отказа. Возможная блокировка IP, ошибка сети и проблема сервиса VNC остаются версиями для проверки.
