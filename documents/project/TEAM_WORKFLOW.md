## 1. Люди, продукт и источник состояния

GitHub — источник опубликованного состояния. В начале задачи: проверить абсолютный cwd, ветку, status, worktree list; fetch origin; проверить новые Backend-коммиты, контракт, документы и решения. Незакоммиченная работа учитывается отдельно. Контракт в отчёте привязывается к commit, а не только к подвижному имени ветки. Код на GitHub и размещённый сайт — разные состояния.

## 4. Общие файлы: изменение через согласование, а не запрет
Общие зоны: src/app/** (особенно layout.tsx и /search), AppShell/навигация, globals.css, BrandMark, CampusShell/primitives, LiveSearch и формы регистрации, типы/API boundary, package.json/package-lock.json, next.config.ts, launcher, AGENTS, общий индекс документации. У файла может быть визуальный и функциональный владелец.

Перед совместным изменением автор указывает пути, задачу, публичный интерфейс/props/DTO, риск для соседнего направления и проверки. PO назначает одного автора конкретного изменения и согласует порядок. Второй чат может исследовать или работать в другом файле, но не параллельно переносить конфликтующие правки того же общего файла. После короткого согласованного блока — diff, тесты и PR. Второе направление получает изменение через Git после одобрения; копирование целых файлов между папками не является способом синхронизации.

Примеры: redesign меняет оформление LiveSearch без изменения запроса; integration расширяет его данные, согласовав props и состояние ошибок. Изменение токенов, семантики выбора ролей или root providers требует проверки обоих направлений. Изменения зависимостей и public API общих компонентов проходят координацию основной разработки; это не абсолютный запрет для других чатов.

## 5. Ветки, PR и объединение
- codex/frontend-main-dev — общая Frontend-линия. Redesign и integration отправляют в неё небольшие PR с понятной целью. Сама ветка main-dev не является production.
- Основная разработка для собственных существенных изменений использует короткую codex/frontend-core-<topic> и PR в main-dev, при чистом состоянии своего worktree; между задачами возвращается на main-dev. Одна задача/чат владеет checkout в этот момент.
- Commit/push/merge выполняются только по отдельному разрешению PO; утверждение регламента само по себе не разрешает будущие публикации; исключение — явно разрешённые организационные commit/push этапа 1.2. PR обязателен для объединения направлений, общих файлов, изменений контракта и выпуска в main. Для публикации PR его текст и проверки готовятся до запроса окончательного одобрения.
- Рецензент Frontend — PO с помощью основного чата; для изменений API/безопасности привлекается Backend-разработчик. Чат не заменяет человеческое утверждение.
- Перед merge: свежие сравнения базы/head, понятный diff, checks соответствующего слоя и регрессия Demo/Live/дизайна. GitHub branch protections и CI-checks считаются только предложенными, пока не настроены отдельно.
- main обновляется отдельным release PR после приёмки и согласования Backend; сейчас не меняется. Backend продолжает публиковаться в codex/backend. Автоматически сливать всю Backend-ветку в Frontend ради чтения API нельзя.
- Для общей истории используется обычное merge-сохранение коммитов только после отдельного разрешения, без rebase опубликованных веток и force push. Не использовать squash как способ потерять известные исходные коммиты при миграции.

## 6. Синхронизация и конфликты
После одобренного PR main-dev публикуется. В каждом worktree автор завершает собственную работу, сохраняет её согласованным commit, проверяет чистоту, делает fetch и смотрит входящие изменения. В локальной main-dev при отсутствии расхождений допустимо согласованное fast-forward обновление. Рабочие направления получают main-dev обычным merge после разрешения владельца. GitHub merge сам по себе не переписывает файлы уже открытого worktree.

При конфликте остановиться и показать файлы/стороны/семантику. Ответственный за общий компонент согласует объединённый результат с обоими направлениями и PO. Не выбирать автоматически «всё ours/theirs», не выкидывать код, не reset --hard, не rebase опубликованной истории. После разрешения проверить контракты, режимы, темы, тесты и итоговый diff. Cherry-pick допустим только для явно выбранного независимого исправления с известными зависимостями; это исключение, а не параллельный способ постоянно переносить одни и те же изменения.

Локальные редизайн/API ветки не переключать из соседнего чата. Общие Git-операции с worktree/ref/config координирует основной чат и выполняет последовательно. Исходники в отдельных деревьях редактировать параллельно можно. Очистка worktree/кэша — отдельное решение, не автоматическое завершение задачи.

## 7. Backend-контракт и продуктовые решения
Первичный API/OpenAPI остаётся в Backend-ветке. Frontend ведёт индекс ссылок и DTO mapping, используя конкретный Backend commit и дату fetch. При несовместимом изменении Backend сначала публикует контракт, миграционный путь и тесты; обе команды подтверждают приёмку. Настоящие Telegram/CSRF/session/DB проверки не заменяются Demo или успешной сборкой.

Комиссии, платежи, статусы заказов и правила допуска не выводятся агентом из UI или примеров. Разработчик поднимает вопрос PO, фиксирует ответ, Backend реализует правило. Нельзя копировать секреты/env или настройки production для удобства локального Live. Секреты не попадают в отчёты, PR, screenshot, Git.

## 8. Запуск по рабочим пространствам
В каждом Frontend-worktree отдельно выполнить согласованный npm ci из его корня. Основная копия сохраняет уже установленные собственные зависимости, если они соответствуют lock-файлу. Файлы node_modules и .next принадлежат своему worktree; npm ci не изменяет исходный lock-файл. Ничего не копировать через symlink. Установка новых зависимостей — только в рамках утверждённой задачи. Повторные Next dev одного дерева конфликтуют за .next/dev/lock даже при разных портах.

Команды после подготовки (фактические результаты запуска — в отчёте этапа 1.2):

```sh
# Основная разработка, из /Users/alekspih/Projects/studly
npm run dev:demo -- --port 3000
# Redesign, из /Users/alekspih/Projects/studly-redesign
npm run dev:demo -- --port 3001
# Integration, из /Users/alekspih/Projects/studly-integration
npm run dev:live -- --port 3002
```

В integration при необходимости вместо Live можно явно запустить Demo на том же порту после остановки предыдущего процесса. Для Live Django запускает/подготавливает Backend-владелец, по умолчанию на 127.0.0.1:8000; Frontend rewrite сохраняет единый browser origin /api/. Согласовать trusted origin http://localhost:3002 (и другие реально используемые Live-origin) с Backend. Не отключать CSRF и не смешивать localhost/127.0.0.1 в одной сессии.

DJANGO_API_ORIGIN задаётся только явно для выбранного окружения; настройки .env* читаются из apps/web конкретного worktree, корневой .env launcher не использует. PORT — аргумент/переменная shell, не .env. Отдельные worktree не наследуют ignored env автоматически. Создать только нужные значения вручную без вывода секретов; .env, .venv и настройки сотрудника автоматически не копировать и не вносить в .worktreeinclude. Не подставлять production Backend как автоматический fallback.

Порты разделяют dev-серверы, но cookies одного host не изолируются по порту: для независимых Live-аккаунтов использовать отдельные браузерные профили/контексты. Общая тестовая Django БД также остаётся общей: параллельные сценарии не должны менять одну запись или рабочие данные без соглашения Backend. [RFC 6265 §8.5](https://www.rfc-editor.org/rfc/rfc6265#section-8.5).

Dev-процессы останавливаются своим Ctrl+C; нельзя завершать неизвестный PID или удалять чужой lock. Изменения режима/API origin требуют перезапуска; production mode/rewrites задаются на этапе build. Публикация ветки не означает обновление сервера — источник выпуска и snapshot согласуются с Backend-инфраструктурой отдельно.

## 10. AGENTS: структура и доставка изменений
Не создавать взаимно противоречащие role-инструкции в каждом worktree вручную. Принято: root AGENTS — общие границы, Git, PO, отчётность и ссылки; apps/web/AGENTS — общие Frontend-правила и сохранённый блок Next.js; apps/api/AGENTS — правила Backend, подготовленные его владельцем. Редизайн/API правила описываются в TEAM_WORKFLOW и тематических документах; локальные вложенные AGENTS нужны только для реально отдельной области, а не для переопределения правил всему дереву.

Общие файлы версионируются. Согласованное изменение policy оформляется отдельным reviewable commit/PR в main-dev; ответственные затем принимают его обычной синхронизацией. В отчёте задачи указывается policy revision/commit. При fetch сравнивать AGENTS/TEAM_WORKFLOW/LOCAL_START с последним утверждённым источником; при расхождении показать его и согласовать обновление. Файл AGENTS одной ветки автоматически не изменится в другой. Изменения общих корневых правил Backend принимает отдельно; Frontend не переписывает его инструкции.

Не синхронизировать AGENTS копированием через общий абсолютный путь, symlink или ignored AGENTS.override.md. Это обходит Git-review и может незаметно подменить инструкции. Этап 1.2 обновляет только root AGENTS и apps/web/AGENTS, сохраняя существующие Frontend-инструкции и автоматически поддерживаемый блок Next.js.
