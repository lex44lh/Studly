## 5. Синхронизация, PR и конфликты
Предлагается общая Frontend-линия codex/frontend-main-dev. Небольшие тематические PR из redesign/API (и коротких core-веток основной разработки) объединяются только после приёмки PO. Для public API/безопасности требуется участие Backend. Разрешение на commit/push/merge остаётся отдельным; утверждение аудита не равно разрешению на публикацию.

После принятого PR: fetch, проверка чистоты и incoming diff, согласованное обновление своего checkout. Main-dev принимает ff-only из своей origin-ветки без локального расхождения; рабочие направления принимают main-dev обычным merge после разрешения. Rebase опубликованных линий и force push не используются. Cherry-pick — только отдельное согласованное исправление, не постоянный второй путь дублирования изменений. При конфликте остановка, список сторон и смысловых различий, ручное согласование владельцами файла и PO, затем тесты. Не отбрасывать «чужую» сторону целиком.

main остаётся неизменённой до отдельного release PR. Backend-ветка не служит веткой автоматического обновления Frontend. Перед общей интеграцией в main отдельно проверить корневой AGENTS/package/config и серверный контур. Изменение ветки GitHub не развёртывает сайт автоматически; деплой согласуется отдельно.

## 8. Запуск и критерии его проверки

- npm ci выполняется отдельно в каждом Frontend-корне после согласования; package-lock сохраняется, node_modules/.next не объединяются.

- Live: согласовать Django 8000 и trusted origin localhost:3002 с его владельцем. Ничего не отключать в CSRF/Telegram/cookie ради зелёной проверки.
- Cookies не изолируются по порту одного host: для независимых сессий нужны отдельные профили/контексты браузера, даже если Next port различается. Общая Django БД также не становится отдельной на каждый Frontend.
- ENV/секреты не копировать автоматически. Нет попытки читать значения .env или внедрять их в отчёт. Контракты/API URL берутся из согласованного окружения, не из старой памяти чата.

## 11. Основные риски и меры
1. Продолжение старых чатов в общем checkout — исправить привязку, не только указать другую ветку в тексте.
2. Старт от origin/main потеряет готовую Frontend-линию в новом дереве — база 7e85114/одобренный потомок.
3. Отчёты/политики незакоммичены после аудита — отдельное сохранение перед ветвлением, не неявное копирование.
4. Одна ветка в двух checkout или общий .next/node_modules — отдельные ветки/зависимости/кэши.
5. Divergence общих props/DTO/CSS — один автор пересекающегося блока, маленький PR и совместная регрессия.
6. Cookies и общие данные Live — отдельные browser contexts и согласованные тестовые записи/окружения, порты не гарантируют это сами.
7. Диск и время npm ci — текущие deps/cache >1 ГБ; заранее оценить свободное место, не обещать бесплатные дубликаты окружения.
8. Автоматическое чтение production/API или копирование env — явный origin, ручная настройка, никаких секретов в Git/отчётах.
9. Общие Git refs/config и будущие конфликтующие корневые файлы Backend — последовательные Git-операции, отдельный review политик и release PR.
10. Desktop временный managed worktree vs постоянный manual — выбрать один путь, не полагаться на неверное default main/detached состояние.
11. GitHub snapshot не равен deployed snapshot — release/деплой отдельно; никаких новых утверждений о работе production по одному git fetch.
12. Старая копия Documents/Projects/studly выглядит похожей — сохранить её нетронутой и не выбирать автоматически как актуальный проект.
