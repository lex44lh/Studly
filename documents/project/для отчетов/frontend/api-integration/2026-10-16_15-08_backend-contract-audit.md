## 5. Поля: Frontend → опубликованный контракт
| Frontend view model | Django wire model / правила | Что потребуется |
|---|---|---|
| roles: customer/performer[] | roles с теми же значениями, без повторов; [] допустим для черновика | Формат совместим; заменяется весь массив. Frontend правильно требует роль перед продолжением |
| profile.displayName | profile.display_name, ≤255 символов | Mapper, полевая ошибка и лимит; непустое имя требуется для complete, но пустой черновик разрешён |
| profile.university/city | Те же ключи, ≤255 каждый | Добавить клиентские ограничения/обработку 400 |
| profile.about | То же, ≤10000 | Обработка длины и серверной ошибки |
| performer.description | То же, ≤10000 | Не смешивать с общим about |
| performer.studyYear | performer.study_year, строка ≤100 | Mapper; не навязывать числовой enum курсов |
| performer.portfolio | Строка ≤10000 | Текущее текстовое поле соответствует; файлового портфолио нет |
| performer.specializations: id/title[] | Чтение specializations: UUID/title; запись specialization_ids: UUID[] | Отдельный read/write mapper; не отправлять объекты, дубли или выдуманные ID |
| profile.avatarFile | Multipart avatar на отдельном POST | Не JSON.stringify(File); дождаться подтверждения загрузки |
| profile.avatarUrl: строка/blob/Telegram photo | Серверный avatar_url: null либо /api/v1/registration/avatar/, только чтение | null → пустое UI-значение; blob и Telegram URL не PATCH-поля |
| Нет в draft | progress.current_step, performer_skipped, updated_at | Модель сохранения/восстановления и подтверждённого пропуска |
| Нет в draft | status.is_complete, completed_at, missing_fields, performer_ready, performer_missing_fields | Серверный статус отдельно от полей формы; не вычислять успех из /me/ |
| performer всегда локальный объект | Backend может вернуть performer: null | Безопасное преобразование в пустую форму, без создания/сохранения по одному GET |

Неуказанный PATCH-ключ сохраняет значение; пустая строка очищает, null для текстовых полей не допускается. Неизвестные ключи и пустой PATCH дают 400. Не отправлять весь локальный draft: avatarFile/avatarUrl, служебные поля и лишние ключи будут некорректны. Изменение выполняется атомарно; ошибка одного поля не сохраняет остальные.

Регистрация завершается отдельным POST после подтверждённого PATCH/аватара. Повторный complete сохраняет прежний completed_at. Очистка имени/всех ролей сбрасывает завершённость. performer_ready требует роль, имя и специализацию; может быть true до complete. Пропуск не подменяет готовность. Снятие роли не удаляет профиль исполнителя, услуги и историю.

## 6. Три категории готовности
### 6.1. Готово к интеграции по контракту (не означает проверено end-to-end)
- Чтение/изменение обеих ролей и всех запрошенных текстовых полей.
- Создание/обновление необязательного performer и сохранение пропуска.
- Постоянный черновик с GET/PATCH, восстановление после повторного подтверждённого входа с любого устройства.
- Complete и независимые серверные статусы общей регистрации/готовности исполнителя.
- Публичный справочник с поиском и множественным выбором UUID без продуктового лимита.
- Приватный аватар PNG/JPEG/WebP до 5 МиБ; три операции и проверка содержимого.
- Mini App/session/CSRF и website OIDC endpoints. Первые пять auth-путей уже имеют локальный Frontend-клиент, но это ещё не доказанный обмен с Django.

### 6.2. Требует согласования или клиентской работы
- Кто настраивает единый browser origin, прокси /api/v1/ → Django, Host/Origin, HTTPS и dev/staging адреса. Прокси обязан сохранять завершающий слеш, cookies/Set-Cookie, multipart, X-CSRFToken и поток изображения. Новый Next API взамен Django не нужен.
- Приоритет первой версии: Backend-документы фиксируют решение владельца «отдельный сайт с Telegram-входом», а исходная задача Frontend ориентирована на Mini App. Поддерживаются оба пути, но очередность и UX следует подтвердить.
- Клиент website OIDC и переход после callback: Backend отвечает JSON, Frontend пока использует только Mini App; флаг telegram_website в клиенте входа фактически не используется.
- Авторизация перед приватным GET/PATCH, загрузка/восстановление до route guards, ручные изменения при позднем ответе сервера; последовательные сохранения, обработка полевых ошибок/истёкшей сессии и CSRF.
- Справочник пока намеренно пуст: нужны утверждённые значения от владельца. Backend API и пустой список не являются отсутствием API.
- Загрузка всех нужных страниц (100 элементов на страницу, не лимит выбора); сохранение выбранных объектов вне текущего фильтра/страницы. next нельзя использовать для передачи cookie на произвольный origin.
- Multipart и DELETE аватара, показ приватного PNG с session-cookie, no-store и сброс blob; Backend не скачивает Telegram photo URL. Выбрать UX использования Telegram-аватара без выдуманного wire-поля.
- Production gate не снимать до реальной интеграционной проверки. Код нового AuthProvider уже глобально загружает SDK и проверяет сессию, в том числе на production /welcome; старый тест «SDK отсутствует в production» относится к состоянию до этих незакоммиченных изменений и больше не доказывает это для рабочего дерева.

### 6.3. Отсутствует на Backend или намеренно вне текущего контракта
- Анонимный серверный черновик до входа: не предусмотрен; серверное восстановление только после проверки Telegram-аккаунта.
- Загрузка файлов портфолио: отсутствует, сейчас только строка. Для текущей формы это не блокер.
- Автоматическое скачивание/сохранение внешнего Telegram photo URL: отсутствует намеренно; avatar_url не записывается JSON.
- Публичная выдача новых регистрационных полей/аватара для чужих профилей: не включена автоматически; старый публичный performer возвращает ограниченный формат.
- Проверка performer_ready при подаче/публикации конкретной услуги: флаг есть, но регистрационный этап не изменил существующий API модерации/подачи. Новые/старые услуги и снятие роли требуют отдельного бизнес-решения.

Ключевых API для трёх первоначальных экранов в категории «отсутствует» не обнаружено. Отсутствуют подключение Frontend и внешние условия, а не сами endpoints регистрации.

## 7. Текущее состояние Frontend и расхождения с контрактом
- Три страницы существуют; production layout пока возвращает нейтральную недоступность, development показывает предпросмотр.
- registrationClient всё ещё возвращает unavailable. loadDraft и submitDraft не вызываются формами; GET/PATCH/complete не подключены.
- Context сохраняет данные только между шагами внутри layout; reload сбрасывает их. API-backed restore предусмотрен типом, но не выполняется. Guards сейчас видят только локальные роли/имя и без ожидания восстановления вернут пользователя на предыдущий шаг.
- Финальные кнопки не выполняют complete. Состояние performer_skipped не сохраняется на сервере.
- SpecializationPicker принимает внешний список, но default client недоступен. Пустой реальный results[] следует показывать как пустой справочник, а не ошибку unavailable.
- Новый незакоммиченный apiRequest поддерживает GET/POST/PATCH и только JSON. Для аватара нужны DELETE, FormData без ручного Content-Type и чтение бинарного ответа/обычный img-запрос с cookie. Нельзя подключить avatar API к этому клиенту без согласованного расширения.
- Auth-клиент использует credentials: same-origin, cache: no-store; получает JSON CSRF перед login/logout; передаёт raw init_data; проверяет /me/ после входа. Это совместимо с базовым auth-контрактом. Перед следующей мутацией нужен новый CSRF; получение токена на каждую мутацию решает ротацию, если используется и для PATCH/DELETE/complete.
- Общая обработка 403 ещё не различает отсутствие сессии, блокировку пользователя и CSRF во всех сценариях. 403 записи не должен автоматически означать anonymous; проверять /me/ и не повторять запись вслепую.
- Frontend сейчас не ограничивает длину текстовых полей по новым серверным maxLength; требуется согласованный UX ошибок 400.
- Текущий Image unoptimized подходит как отправная точка для cookie-bound изображения; показ именно серверного приватного аватара через прокси ещё не проверен. Старый blob-preview не доказывает работу server image.
