## Утверждённое направление

**Дизайн — «Кампус / Ясный ритм». Стек — A: Next.js + React + TypeScript + CSS/CSS Modules + Motion.**

Сохранить существующий знак, синий `#3547B8` и написание STUDLY. Выразительность строится на ясной типографике, качественных карточках, собственном мотиве ленты и коротких реакциях. Основные действия выполняются немедленно и остаются семантическим DOM. Не устанавливать весь исследованный набор. Three/R3F — только отдельный будущий необязательный branded pilot после разрешения и проверки пользы; WebGPU не является базовой платформой STUDLY.

| Концепция | Смысл | Сильная сторона | Основной риск | Рекомендация |
|---|---|---|---|---|
| **Кампус / Ясный ритм** | Чистый, дружелюбный цифровой маркетплейс | Понятные ежедневные задачи, единая система и дешёвый static fallback | Стать типовым без собственной графики/типографики | **Выбрать** |
| Студенческий редактор | Типографические категории и редакционные подборки | Оригинальность без тяжёлого GPU | Коллажный шум и неоднородность пользовательского контента | Не основное направление |
| Орбита / Спокойная глубина | Один пространственный брендовый объект, строгий DOM core | Сильный первый контакт | Дорогой GPU/asset pipeline, излишняя технологичность | Только отдельные идеи после пилота |

Одинаковые продуктовые правила и навигация обязательны во всех концепциях; прогноз привлекательности ещё не подтверждён исследованием студентов.

## Ответы на 15 вопросов задания

1. **Насколько слаб Frontend?** Это неоднородный функциональный прототип, а не пустое приложение. Регистрация уже заметно аккуратнее shell/каталога. Слабые места: отсутствующая общая дизайн-система, 289 inline-style блоков, смешанные темы, пустой собственный профиль, информационные заглушки, неполный mobile/Telegram lifecycle, неясное различие empty/error/unsupported. 22 page templates сохранены; одинаковая зрелость всех разделов не заявляется.
2. **Что актуально в октябре2026?** Next16.4.x/React19.3.x, стабильные CSS/Motion/GSAP, Three/r186, R3F9.x; WebGPU и TSL полезны в GPU-задачах, но runtime-охват неоднороден. Точные версии/даты/peers и experimental-границы проверены в Technology Research. TS7 не нужен ради редизайна при несовместимом tooling.
3. **Подходит ли Three.js?** Да, для небольшой отдельной сцены. Для поиска, регистрации, чатов и заказа не нужен.
4. **Нужен ли R3F?** Основному UI — нет. При утверждённой React-сцене — удобный адаптер lifecycle, но не оптимизатор тяжёлого контента.
5. **Нужен ли WebGPU?** Нет как обязательная основа. Ни одна ключевая операция от него не зависит. Возможный будущий pilot обязан иметь WebGL2/2D fallback и проверенную renderer/material compatibility.
6. **Какие альтернативы лучше для отдельных задач?** CSS — focus/press/hover; Motion — sheets/presence/короткие springs; SVG/poster — иллюстрации; native View Transitions — progressive enhancement после version/engine QA. GSAP — для отдельной сложной timeline, Babylon — для другого, существенно более сложного 3D-продукта.
7. **Что использует Oryzo?** Авторские BTS подтверждают Three.js/WebGL и гибрид splat/mesh с offline Houdini/Redshift pipeline, а не автоматически WebGPU/R3F/GSAP. Полезны один центральный предмет, непрерывность и визуальная дисциплина. Интерактивная плавность в нашем IAB не проверена: страница оставалась на loader.
8. **Лучшая концепция?** «Кампус»: современный, узнаваемый сервис для регулярных коротких сессий, без добавления трудности. Это рекомендация для проверки прототипом, а не доказанный вкус всех студентов.
9. **Один стек?** A: Next + React + TS + CSS + Motion. Candidate versions и security baseline проверяются отдельным малым этапом до нового Live-релиза.
10. **Производительность Telegram?** Надёжного полевого baseline пока нет. Современный initial JS текущего `/search` —148557bytes локального gzip-суммирования, не HAR; 3D отсутствует. Плановые p75: LCP≤2.5s, INP≤200ms, CLS≤0.1, initial self-hosted JS≤170KiB gzip, сцены не входят в critical path. Все цели требуют проверок на реальных клиентах.
11. **Какие ошибки интеграции?** Ранние return-заглушки меняли видимое содержимое, но не удаляли routes; восстановление legacy UI есть только в незакоммиченном diff. Категории/rating/chat/notifications API отсутствуют, create-service/orders API есть, но не подключены. Фильтры текущей страницы — реальное ограничение. `api` против `live` в deployment требует согласования. Ошибка локального API не доказывает недоступность production Django.
12. **Как организован Demo/Live?** Сейчас явный build/dev mode без автоматического fallback; есть оставшееся дублирование views и неполные demo-сценарии. Будущая цель — общие views + typed live/demo repositories, отдельные capabilities/commands/storage и постоянный Demo badge. Production NEXT_PUBLIC mode заморожен при build; одного перезапуска с другой env недостаточно.
13. **Как не сломать Django?** Сохранить DTO/URL/trailing slash/CSRF/session/decimal money/server final state/request_key, реальный API client и существующие маршруты. Мигрировать представления по одному feature, без Next API замены Django и без изменений Backend. Проверять unit/contract + staging Django E2E + реальные Telegram-клиенты.
14. **С какой страницы начать?** После baseline/токенов — `/search` с общей ServiceCard и shell; затем `/service/[id]`. Welcome/3D позже.
15. **Каков план?** Аудит → утверждение → config/security/contracts baseline → токены/platform/UI → поиск/главная/категории → услуга/исполнитель/избранное → auth/регистрация/кабинет → welcome → публикация/заказы → чаты/прочее → итоговый performance/Django release gate. Измерения идут на каждом этапе; каждый шаг имеет отдельный откат.

## Следующее решение после реализации /search

Направление «Кампус» и стек A утверждены. Настоящий `/search` перенесён; для его анимаций достаточно CSS, Motion не устанавливался без необходимости. Требуются визуальная приёмка, физические Telegram-проверки и отдельное решение о публикации. Остальные страницы, 3D и новый release этим этапом не разрешены. Commit и push не выполнялись.
