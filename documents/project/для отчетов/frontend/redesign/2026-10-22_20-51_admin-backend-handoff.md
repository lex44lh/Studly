## 1. Что реализовано на Frontend

Отдельный `AdminWorkspace` в существующей Campus-системе. Его данные — единый canonical Demo workspace, используемый кабинетами, каталогом, заказами и отзывами. Отдельные «административные» копии профиля, услуг или заказов не создаются.

Разделы: обзор, пользователи, модерация профилей, услуги, заказы, обращения/споры, жалобы/безопасность, отзывы, финансы, аналитика, история решений, настройки.

Работают локальные поиск по доступным разделам, поиск в разделе, фильтры по состоянию/роли/датам, сортировка, пагинация, сохранение фильтров при переходе между разделами, детальная боковая карточка, обязательная причина отказа/исправлений, отдельное подтверждение решения. При изменении workspace между просмотром и подтверждением требуется повторная проверка заявки.

Две категории административных команд:

1. `profile.decide` — approved/rejected/changes только по поданной заявке.
2. `service.decide` — approved/rejected/changes только по поданной редакции и с одобренным профилем исполнителя.

Команды вызываются с отдельным Demo-actor `MODERATOR`, а не сменой activeRole обычного аккаунта. Domain/repository/provider выполняют собственные проверки и создают события в canonical state; UI не конструирует отдельный журнал с якобы серверным автором/временем.

Начальное открытие требует явного подтверждения тестовой среды. `sandboxEnabled` задаётся согласованной compile/runtime-конфигурацией Demo provider; экран не выдаёт полномочия через localStorage/query/роль пользователя. Development Demo разрешает sandbox; production Demo — только с явным `NEXT_PUBLIC_STUDLY_DEMO_ADMIN=enabled`, по умолчанию выключен. Live-маршрут и общую wiring выполняет root; ни данный компонент, ни переключатель представления не являются серверной защитой.

Переключатель «представление прав» показывает предполагаемое разделение обязанностей: профили, услуги, поддержка, финансовые отчёты, общий Demo-обзор. Он фильтрует видимые разделы/поиск и действия UI. Это **предложение для будущего RBAC, не настоящие staff permissions**.

## 2. Текущее состояние Backend и существенные разрывы

На указанном SHA уже существует стандартная Django Admin по `/admin/`. Модерация услуг там требует `is_staff` и `catalog.moderate_service`. Решение подписано, связано с модератором, выбором и просмотренной редакцией; подтверждение действительно 30 минут. Устаревшее содержание не публикуется, решение журналируется Django.

REST API пользовательских услуг поддерживает только pending/published/rejected. Причины отклонения, needs_changes и модерации исполнителя пока нет. Профиль исполнителя содержит необязательный текст portfolio; `performer_ready` обозначает роль/имя/специализации, а не административное одобрение. Новые требования к портфолио и публикации должны проверяться Backend, а не только disabled-кнопкой.

Существующие orders — pending_acceptance/awaiting_payment/cancelled/declined с проверкой участника. Никаких настоящих paid/IN_PROGRESS/REVIEW/COMPLETED, арбитражных операций, review API, общей переписки, финансовой админской статистики или security cases в проверенном контракте нет. Есть только служебная диагностика тестовых объектов ЮKassa, без публичного создания оплаты и изменения заказа.

Серверный quote и снимок заказа сейчас используют 3%, Decimal/ROUND_HALF_UP. Новая продуктовая ставка 5% действует в новой Demo-модели; Live продолжает показывать серверные значения. Старые заказы не пересчитываются. Нельзя выдавать сумму локальных симуляций за оборот или выручку STUDLY.

## 3. Адрес и граница доступа

Маршрут Frontend `/admin` — проектное решение для закрытого Demo, не согласованный адрес будущей публикации. На Backend уже используется `/admin/`; при размещении Nginx/маршрутизация должны явно решить, кому принадлежит этот путь. Нельзя молча затенять существующую Django Admin или обещать доступность новой панели по этому URL.

Backend-разработчик должен отдельно оценить:

- Какие внутренние операции достаточно оставить в стандартной Django Admin.
- Каким сценариям нужен специальный интерфейс STUDLY и отдельный административный API.
- Финальный URL, reverse proxy, доступ только нужным сотрудникам, окружение проверки и условия включения Live.

Минимальная серверная модель: настоящая сессия, отдельные staff roles/permissions и object-level ограничения. Обычные customer/performer и локальный activeRole ничего не разрешают. `is_staff` сам по себе не означает доступ ко всем данным или ко всем административным операциям.

Frontend получает доступные capabilities от сервера и отображает их. Backend повторно проверяет каждую операцию, в том числе прямой запрос к endpoint. Автор решения, время, служебные роли, наличие оплаты и права не принимаются от браузера как доверенные данные.

## 6. Повторы, конфликты и ошибки

Для значимых решений Backend должен атомарно проверить текущий статус, просмотренную редакцию, полномочие, основания и связанный профиль, затем записать решение и audit event. Конкретный способ optimistic concurrency — `If-Match`, expected_revision или иной контракт — выбирает Backend. Не выбирать автоматически последнюю редакцию без её просмотра человеком.

Повтор одного намерения с тем же содержимым должен иметь определённый идемпотентный результат. Другой payload с тем же ключом и конфликтующее повторное решение должны возвращать явный конфликт, не создавать второе событие и не менять автора/время прежнего решения. Необходимы тесты параллельных решений двух сотрудников и правки автора между просмотром/подтверждением.

Ожидаемые категории ответов для будущего согласования:

- 400: валидация, обязательная причина, неверный фильтр/решение.
- 401/403: сессия/CSRF/полномочие в соответствии с будущей auth-схемой; текущий Django session API обычно использует 403.
- 404: отсутствующий или недоступный в области сотрудника объект.
- 409/412: устаревшая версия/недопустимый переход по выбранной модели конфликтов.
- 413/415: ограничение размера/формата там, где появится загрузка.
- 429/503 и сетевой обрыв: честное временное состояние без ложного успеха.

Frontend блокирует повторный клик во время pending, сохраняет причину при ошибке, предлагает перечитать объект при конфликте. Это удобство UI; авторитетная защита выполняется сервером. Мутации не повторяются автоматически после неоднозначной сетевой ошибки.

## 7. Портфолио и защищённый просмотр

Demo поддерживает согласованные PNG/JPEG/WebP/PDF ≤10 МиБ и HTTP(S)-ссылки. Бинарные данные находятся в отдельном локальном IndexedDB-хранилище, metadata refs — в canonical state. Blob URL существует только во время просмотра и освобождается; отсутствующий локальный файл отображается ошибкой, а не фиктивным успехом.

Это **не серверный файловый контракт**. Для настоящего хранения нужны независимые проверки формата/содержимого/размера, выбор метаданных и имени сервером, защищённая выдача по разрешению, определение публичности, хранение и резервирование. HTTP(S)-ссылка не означает доверенный файл; сервер не должен автоматически скачивать произвольный пользовательский URL. Будущий preview PDF/изображений должен исключать доступ к неразрешённым активным форматам и объектам.

Необходимы решения о том, какие работы входят в принятую редакцию профиля/услуги и как сохраняется принятой snapshot при последующей правке. Неподтверждённые новые материалы не должны наследовать старое одобрение без правила повторной модерации.

## 8. Частные сообщения, критические фразы и обжалование

В текущей админке **нет чтения массива messages, массовой рассылки и общей ленты личной переписки**. В карточке заказа показываются отдельно переданные результат, замечания и история этого заказа. Финансовое представление не показывает эти материалы.

Для Live доступ к содержимому сообщений допускается только в объёме рассмотрения конкретного случая: серверная связь case↔материал, полномочие и область сотрудника, необходимый контекст, журнал открытия и основания. Детали хранения, сроков, оповещения/обжалования и удаления требуют утверждения; здесь сроки не выдумываются.

**STUDLY 2.0: алгоритмическая проверка критических фраз. AI-модерация отложена до STUDLY 3.0.** Никакой AI или действующий сканер Live-переписки этим Frontend не подключён.

Нужна согласованная модель правил/категорий и их версий, оснований срабатывания, минимального excerpt, статуса ручной проверки и обжалования. Само слово Telegram не является нарушением: учебные проекты, боты и ссылки могут быть допустимым контекстом. Не следует строить автоматическую санкцию по простому совпадению слова. Ложное срабатывание должно иметь путь человеческой проверки и обращения пользователя; окончательные решения/санкции и сроки ещё не утверждены.

## 9. Финансы, отзывы, арбитраж: явные запреты

- Нет административных команд изменения цены, оплаты, order status, тарифа, выплат и возврата средств.
- Нет редактирования/удаления пользовательского отзыва; один допустимый review на внутренний завершённый заказ. Рейтинг/количество берутся через canonical `ratingFor`.
- Нет действующих команд открытия/закрытия/решения арбитража, назначения арбитра или санкции, пока правила не утверждены.
- Нет фиктивных жалоб/споров для наполнения таблиц. Отсутствие подключённого источника жалоб обозначено недоступностью, а не показателем «нарушений ноль».
- В Demo финансы — сумма сохранённых снимков симуляций, не реальная выручка. Агрегирование защищено от выхода за точный числовой диапазон: завышенная сумма не округляется незаметно.
- В Live используются только серверные деньги. Существующие 3% не подменяются локальными 5%; старые заказы не пересчитываются. Для смены тарифа требуется защита подтверждённой quote от изменения ставки между просмотром и созданием заказа.

Проверены: закрытый sandbox, явный вход, storage error/retry, обязательная причина и второе подтверждение, canonical profile/service commands, stale confirmation и сохранение причины при ошибке записи, privacy финансов/безопасности, scoped projections/search, metrics без чтения messages, комбинированные фильтры без изменения данных, пагинация и сохранение запроса после возврата. Suite не доказывает настоящий browser focus/dialog lifecycle, серверную защищённость или реализацию Django RBAC.

Ошибки этапа: первоначальный локальный ESLint обнаружил неиспользуемый type import; удалён. TypeScript обнаружил избыточную проверку уже суженного access и передачу nullable суммы; исправлено. Один локальный скрипт редактирования был вызван из неверного cwd, завершился до записи; повтор выполнен по точному абсолютному пути. После исправлений проверки выше прошли.

Git: commit/push/merge/rebase/reset/stash/git add не выполнялись. Изменения остаются untracked/working tree Redesign. Backend/DTO/Auth/CSRF/package/lock не менялись, соседние checkout не редактировались, процессы не запускались и не останавливались.

## 11. Следующая приёмка и решения PO/Backend

1. Утвердить дополнение архитектурной области и окончательную схему публикации/URL с учётом существующей Django Admin.
2. Согласовать серверный RBAC и минимальный доступ по каждому объекту, а не единый неограниченный admin-флаг.
3. Утвердить profile moderation contract и связь approval с публикацией услуг; причины/needs_changes и правила повторной модерации.
4. Утвердить доступ к контексту жалобы, критические фразы/исключения, обжалование, санкции, сроки и арбитражные полномочия. До этого зависимые действия недоступны.
5. Опубликовать API/OpenAPI с новым Backend SHA, проверить concurrency/idempotency/CSRF/object access и отсутствие утечки личных данных.
6. Root выполняет общий UI/build/regression gate; затем новый полный manifest и независимая приёмка основным Frontend. Старый manifest не считается актуальным после этой реализации.

Публикация Live-админки допустима только после готовности Backend permissions и настоящих серверных проверок. Текущий Frontend sandbox не заменяет этот этап.
