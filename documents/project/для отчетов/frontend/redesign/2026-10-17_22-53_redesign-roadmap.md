## 1. С чего начать

**Первый пользовательский экран редизайна — `/search`**, с общей карточкой услуги и компактным shell. Он проверяет реальную ценность продукта: быстро найти и сравнить предложения. Затем `/service/[id]`, чтобы получить один завершённый вертикальный сценарий. Welcome с иллюстрацией делать после проверки повседневного ядра.

До первой визуальной замены нужны согласованные архитектура/концепция и технический baseline. Нельзя одновременно обновить framework, переписать API и заменить все страницы: тогда невозможно локализовать регрессию или быстро откатить интерфейс.

## 2. Этапы

### Этап 0. Аудит и фиксация состояния — выполнено исследованием

- **Цель:** отделить существующие возможности, недостающую интеграцию и регрессии.
- **Изменения:** семь отчётов и индекс; 22 фактических маршрута, список компонентов, Demo/Live, Git и источники. Исходники приложения не изменяются.
- **Зависимости:** локальный проект, read-only доступ к remote refs/официальной документации.
- **Риски:** принять незакоммиченный фикс за опубликованную версию; старый Backend hash за актуальный контракт; ошибку API за удалённую страницу.
- **Проверки:** status/branch/log/diff, безопасный fetch; существующие тесты, tsc, lint, production build; осмотр части экранов, измерение артефактов.
- **Готовность:** различия HEAD/working copy и непроверенные возможности явно записаны; пользователь получает три концепции и один стек.
- **Откат:** только удалить/вернуть новые отчёты по решению владельца; исходное приложение не менялось. Этот сеанс ничего не коммитит.

### Этап 1. Утверждение продуктового направления и ADR — ожидает пользователя

- **Цель:** выбрать «Кампус / Ясный ритм» и стек A либо получить конкретные поправки.
- **Изменения:** зафиксировать решения о цветах, типографике, shell, навигации, границах 3D, режиме демонстрации и критериях качества. План и бюджеты становятся согласованным ADR.
- **Зависимости:** результат этапа 0 и решение пользователя; отдельно определить приоритет публикации услуг/заказов в нижней навигации.
- **Риски:** оценивать лишь красоту hero; принять экспертные оценки за исследование аудитории.
- **Проверки:** обзор трёх направлений по сценариям студентов; проверить сохранение знака и основного синего.
- **Готовность:** один выбранный вариант, согласованный список первого пилота и запретов; ясно, разрешена ли какая-либо 3D-разработка.
- **Откат:** изменить ADR и прототип до кода; существующий UI остаётся рабочим.

### Этап 2. Технический и интеграционный baseline

- **Цель:** убрать неоднозначности до визуальной миграции.
- **Изменения:** отдельными малыми изменениями проверить security patch Next/React/sharp; согласовать `api` против `live` в deployment configuration с владельцем Backend; зафиксировать API DTO/capability matrix; включить TS registration tests в штатный test runner после согласования реализации.
- **Зависимости:** этап 1; Frontend changes только в своей области; deployment/Backend-файлы исправляет их владелец. Прочитать локальные guides конкретной версии Next до её изменения.
- **Риски:** minor update framework имеет несовместимость; неверные build-time переменные; production Live собирается в Demo; контракт callback website изменился с прошлой проверки.
- **Проверки:** текущие 21 тест, lint, tsc, build; same-origin proxy/trailing slash, cookies/CSRF, auth options, регистрация и каталог на staging. Проверить именно production build с целевыми переменными.
- **Готовность:** подтверждён patched baseline и одна согласованная Live-конфигурация; старые и новые ошибки классифицированы; deployment воспроизводим без секретов в отчёте.
- **Откат:** предыдущий проверенный build/config, при этом нельзя сознательно возвращать уязвимую production-версию вместо исправленного безопасного baseline. Изменения UI ещё не начинаются.

### Этап 3. Токены, платформенный адаптер и базовые компоненты

- **Цель:** единое поведение независимо от маршрута, режима и темы.
- **Изменения:** semantic color/space/type/radius/motion tokens; Button, Field, FormMessage, Sheet, Dialog, Tabs, Badge, ApiState, базовая ServiceCard; Telegram safe area/viewport/lifecycle adapter; явная motion policy; корректные темы и focus.
- **Зависимости:** этапы 1–2. Motion устанавливается только после проверки peers/bundle; существующие страницы мигрируют постепенно.
- **Риски:** новый глобальный CSS ломает старые inline-экраны; дублирование Tailwind/CSS Modules; неправильная клавиатура; совместный scroll native Telegram и веб-страницы.
- **Проверки:** component preview всех состояний, клавиатура/screen reader, 320–430 px и desktop, 200% text zoom, light/dark, Reduced Motion; CSS isolation от unmigrated routes.
- **Готовность:** базовые компоненты покрывают реальные состояния, нет смешанных тем, действия доступны без анимации. Применены в одном пилотном экране, а не просто созданы в пустой библиотеке.
- **Откат:** отключить новую тему/компонент для пилотного route, не глобально откатывать API.

### Этап 4. Пилот каталога и поиска — `/search`, затем `/` и `/category/[slug]`

- **Цель:** проверить качество продукта на главном сценарии.
- **Изменения:** новая выдача, карточка, поиск, фильтры в sheet, пагинация, URL-state, debounce/abort; loading/error/empty/unsupported; shared Demo/Live view models. Сохранить `/category/[slug]`: полноценные известные категории и фильтры в Demo, честное unavailable-состояние и переход к поиску в Live. Категории не выдавать за рабочую серверную фильтрацию, пока контракт её не поддерживает.
- **Зависимости:** этап 3, существующий services API; глобальные фильтры и rating требуют отдельного согласования Backend-контракта, это не скрытая часть Frontend-редизайна.
- **Риски:** локальная фильтрация текущей страницы выглядит как глобальная; гонки запросов; найденное количество не соответствует видимому набору; фиктивные рейтинги; утечка demo IDs в Live.
- **Проверки:** пустой запрос/кириллица, длинные названия, медленная сеть/429/503, back/forward, повторное открытие, pagination с query; одинаковый UI на Demo и Live; 6–8 студенческих usability-сессий.
- **Готовность:** пользователь находит подходящее предложение без подсказок; цена/срок/ограничения понятны; бюджеты JS/LCP/INP/CLS выполнены на тестовой матрице; нет обязательного canvas.
- **Откат:** визуальный route flag возвращает старый экран с тем же Live adapter. Новый поиск не меняет источник данных при откате.

### Этап 5. Детали услуги, исполнитель, избранное

- **Цель:** завершить путь поиска и создать доверие к предложению.
- **Изменения:** `/service/[id]`, `/profile/[id]`, `/favorites`; честный состав услуги, срок, цена и серверный quote/комиссия; общие действия и блок доступной информации об исполнителе. Галерея/портфолио — только Demo/прототип до согласования media-контракта: текущий публичный Service не содержит images, performer возвращает id/name/about. Приватный регистрационный аватар не считать публичным портретом. Неподдержанные заказ/chat явно обозначены и не обещают успех.
- **Зависимости:** этап 4; существующие detail/performer/quote endpoints; favorites пока локальны, без обещания синхронизации. Live-изображения и портфолио требуют будущего отдельного контракта; их отсутствие не блокирует честный текстовый UI.
- **Риски:** отображённая цена устарела перед заказом; пользовательская картинка увеличивает CLS/трафик; отсутствующие оценки подменяются нулями; IDs demo/live смешиваются.
- **Проверки:** реальные и отсутствующие IDs, пустые поля, quote change/error, long content, slow images, batch favorites, возврат к позиции выдачи, безопасные URL аватара.
- **Готовность:** понятна итоговая сумма и доступность операции; нет выдуманных фактов; интерфейс работает без изображений/анимаций; карточка едина во всех разделах.
- **Откат:** по одному route; API money/quote модели не откатывать вместе с оформлением.

### Этап 6. Авторизация, регистрация и личный кабинет

- **Цель:** сохранить серверную корректность при обновлении форм.
- **Изменения:** обновить существующие три `/register/*` шага и `/profile`, сохранить one/both roles, Telegram prefill, draft/progress/avatar/specializations. Website login подключать только по актуальному auth options и callback контракту. Разделить проверку сессии и ошибку сети.
- **Зависимости:** baseline auth/registration; этап 3; Backend callback/auth availability. `/register` не существует как page: при необходимости отдельного redirect сначала согласовать и проверить.
- **Риски:** мнимая регистрация в Demo; PATCH ошибочно считается complete; потеря черновика после смены роли; initDataUnsafe используется для входа; повторное отправление формы.
- **Проверки:** fresh CSRF,401/403/409/validation, refresh/direct link/возврат шага, skip performer, avatar upload/delete, manual input сохраняется после late prefill; logout/account switch; настоящие Mini App и Website login на staging.
- **Готовность:** успех подтверждён Django; пользователь понимает режим; формы доступны с клавиатурой; текущие registration tests сохранены и расширены только для новой логики.
- **Откат:** прежнее представление с тем же auth adapter и server draft; не менять/очищать серверный прогресс ради UI.

### Этап 7. Welcome и фирменная графика

- **Цель:** повысить узнаваемость после проверки основных задач.
- **Изменения:** `/welcome`, короткий блок главной, SVG/CSS-лента, ясные действия «Смотреть услуги»/регистрация. Если пользователь отдельно утвердил реальную 3D — небольшой независимый WebGL pilot с постером, budgets и lazy loading.
- **Зависимости:** положительные результаты этапа 4 и дизайн-концепция; 3D требует своего решения и mobile proof, не блокирует выпуск UI.
- **Риски:** welcome становится препятствием перед каталогом; сцена тянет global bundle; Touch/GPU инициализация тормозит вход.
- **Проверки:** CTA активна до загрузки иллюстрации; no-WebGL/no-WebGPU/context-lost/Reduced Motion; background/foreground; старые iPhone/Android, offline/slow network; zero animation loops в покое.
- **Готовность:** фирменность сохраняется в статике; task completion не ухудшается; при отказе canvas остаётся полноценная страница.
- **Откат:** удалить enhancement flag и оставить тот же постер/SVG; маршруты и auth не меняются.

### Этап 8. Публикация услуги и заказы

- **Цель:** перенести реальные операции в общий качественный UI, не путать local demo с Live.
- **Изменения:** `/create-service`, `/orders`, `/orders/[id]`, `/orders/[id]/additional-payment`; формы, status timeline, состав/quote, подтверждения. Проверить уже существующий Django create-service/orders контракт; интегрировать отдельно от визуальной замены. Доплаты/платежи включать только при подтверждённой поддержке.
- **Зависимости:** этапы 5–6 и согласованные capability/permissions/status transitions Backend. Его код не меняется Frontend-командой.
- **Риски:** повторный заказ, stale quote, disabled-fieldset пропускает Link, локальная запись воспринимается как серверная, неверные разрешённые переходы статуса.
- **Проверки:** customer/performer/both, unauthorized/forbidden, duplicate click, race/stale service, network interruption после submit и повторное чтение server state; Demo не отправляет настоящие команды. Сохранить существующий `request_key`: один UUID на одно намеренное оформление, тот же ключ при повторе этого оформления после сетевой ошибки; новая попытка/новый заказ — отдельное явное намерение, а не новый UUID на каждый retry.
- **Готовность:** каждая активная Live-кнопка имеет реальный контракт и наблюдаемое server confirmation; неподдержанные операции честно объяснены; нет фиктивной оплаты.
- **Откат:** отдельно UI flag и capability flag; уже созданные серверные записи сохраняются, нельзя откатом повторить команду.

### Этап 9. Чаты, уведомления и вспомогательные разделы

- **Цель:** покрыть весь существующий route inventory без исчезновения содержимого.
- **Изменения:** `/chats`, `/chats/[id]`, `/notifications`, `/about`, `/rules`, `/safety`, `/support`. Для будущего chat/notification API сначала согласовать transport/permissions/delivery semantics с владельцем Backend. До этого — маркированные Demo-сценарии и понятная Live-недоступность.
- **Зависимости:** существующие разделы сохраняются; реальный chat не предполагается готовым из-за наличия ChatWindow.
- **Риски:** выдать browser storage за доставку сообщения; отсутствие клавиатурной safe area; потеря local draft; необработанный quota error; дублирование меню/навигации.
- **Проверки:** длинная переписка, клавиатура, отправка/ошибка/повтор без дубликата, reconnect при наличии контракта, empty states, support links; screen reader и focus; все 22 route templates проверены по матрице.
- **Готовность:** каждый старый раздел имеет новый доступный UI; статус Live/Demo ясен; нет dead-end ссылок; unsupported не означает удалённую страницу.
- **Откат:** route-by-route к прежнему безопасному UI; не стирать browser data пользователя и не сбрасывать будущую серверную переписку.

### Этап 10. Итоговое качество, Django E2E и постепенный выпуск

- **Цель:** доказать работоспособность в реальной целевой среде.
- **Изменения:** устранить найденные дефекты; завершить image/font/code splitting; проверить аварийное восстановление; зафиксировать наблюдаемость без секретов/PII. Измерения проводятся и на предыдущих этапах, этот этап — выпускной gate.
- **Зависимости:** мигрированные маршруты, staging Django и реальные Telegram-клиенты; участие владельца Backend для интеграционных условий.
- **Риски:** лабораторный desktop результат выдаётся за Telegram; cached local build скрывает cold start; телеметрия пишет initData/переписку; production env отличается от staging.
- **Проверки:** полный critical path на Demo и Django Live; auth/registration/catalog/favorites/publish/orders и согласованные остальные функции; HTTPS/proxy/CSRF/cookies, 3G-like стресс, слабые устройства, screen reader, background/resume, cache/memory; RUM p75 после ограниченного rollout.
- **Готовность:** все обязательные проверки зелёные, бюджеты выполнены или документировано согласованное исключение; нет потери функциональности, настоящие платежи не имитируются; release/rollback playbook согласован.
- **Откат:** route flags → предыдущий проверенный patched build; неизменные контракты API позволяют откат UI без миграции БД. Публикация/коммиты/push требуют отдельного разрешения пользователя.

## 3. Правила размера изменений

Один reviewable change — одна граница: baseline update, токены/компонент, feature adapter или маршрут. Не выносить все файлы в новую структуру первым PR. Не соединять security update, data mode, auth rewrite и новую графику в один diff. На каждом шаге сохранять доступный существующий сценарий, а не оставлять временную белую страницу.

Тестировать поведение, которое реально изменилось; не плодить тесты, повторяющие CSS. После успешного набора проверок не повторять весь suite без новой причины. Обновлять тематический отчёт и индекс после логического этапа, фиксировать commit baseline и фактическое время.

## 4. Зависимости и работа параллельно

```text
0 аудит → 1 согласование → 2 технический baseline → 3 дизайн-система/platform
                                                     ↓
                                            4 поиск/главная → 5 услуга/исполнитель
                                                     ↓                  ↓
                                          6 auth/registration ───────→ 8 publish/orders
                                                     ↓
                                          7 welcome/брендовая графика
3 + API договорённости ─────────────────────────────→ 9 chat/прочее
Все этапы: performance/accessibility/integration checks → 10 release gate
```

После общих токенов можно параллельно вести регистрацию и публичные details, если не редактировать одни и те же провайдеры. Backend-команда независимо развивает contracts; Frontend не создаёт фиктивный Next API для замены недостающих функций. Отсутствующий chat/ratings API не должен блокировать редизайн уже работающего каталога.

Календарные обещания без команды, доступности staging и результатов пилота были бы предположением. Оценивать трудозатраты после этапа 1 и вертикального пилота: текущий документ задаёт порядок и gates, а не выдуманный срок завершения.

## 5. Факты, предположения, рекомендация

**Проверено:** route inventory и текущие контракты; проект собирается, но не все существующие Live-операции интегрированы. **Предполагается:** поиск как первый пилот быстрее выявит UX-проблемы и регрессии; нужно проверить прототипом и измерениями. **Вывод:** мигрировать вертикальными сценариями и малыми изменениями. **Рекомендация:** после утверждения начинать с baseline и `/search`, а не с большого трёхмерного Welcome.
