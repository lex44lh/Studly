# STUDLY 2 Решения Backend

24 октября 2026. План: [BACKEND_2_IMPLEMENTATION_PLAN.md](BACKEND_2_IMPLEMENTATION_PLAN.md). Контракт: [API_CONTRACT.md](API_CONTRACT.md). Это решения локальной разработки, без deployment и production-миграций.

## Один аккаунт и канонические данные

Сохранены Django/DRF/PostgreSQL, Telegram Mini App и OIDC, session/CSRF. Регистрация остаётся источником profile/roles, кабинеты читают те же модели. Role switch не выдаёт прав. Создание заказов требует customer, создание/правка услуг — performer; старые заказы читают и обслуживают их реальные участники, без копий для двух кабинетов. Неизвестные рейтинги/completed/reviews возвращаются null с явной недоступностью.

## Версии контракта и денег

Владелец подтвердил opt-in v2 5%, сохранив старый v1 3%. Это требует отдельных DTO услуг/quote/order, но не копии бизнес-сущностей: обе версии сохраняют одну Order. Общие новые ресурсы остаются в v1. Дополнения — JSON со строго проверенными UUID/title/Decimal-string/extra_days; редактируются только в транзакции услуги и меняют её revision, не существуют как независимо изменяемая цена.

Новый Quote — серверная запись UUID с owner и полным неизменяемым snapshot; стоимость клиента не используется. В Order сохраняются subtotal, base, selected extras, percent/fee/total, revision и тариф. При создании актуальное предложение сравнивается с показанным; любое изменение требует нового согласия. Quote не резервирует услугу/деньги. Его срок жизни пока не ограничен продуктовым правилом, но проверка актуальности обязательна. Версии Tariff через модель не переписываются. Изменение active code и отсутствие новой версии не дают silent fallback.

Историческая price_amount v1 означала основную цену; v2 хранит subtotal, сохраняя существующее DB-ограничение total=price_amount+fee. base_price_amount и selected_extras отделяют компоненты. Старые записи не пересчитываются; новые nullable quote/base и default tariff_code=buyer-3-v1 не означают, что в прошлом был настоящий Quote. Миграционный тест проверяет переход старой схемы с 3% и создание одного conversation без изменения сумм/состава.

## Модерация и редакции

PerformerProfile имеет отдельную moderation status/reason/revision. Registration performer_ready не меняет смысла. Владелец подтвердил: изменения модерируемых полей/аватара/работ после approval возвращают профиль в pending и скрывают услуги. Смена только customer/шага и no-op не снимает approval. Клиент может передать performer_revision для optimistic guard. Пока старый клиент не передаёт guard, совместимый PATCH сериализует запись, но не защищает от пользовательского last-write-wins; Integration должен включить новый guard.

Подтверждённые published services хранят свой статус, но публичные чтения и заказ проверяют актуальный profile approval/роль/active/связанные работы. После исправления/одобрения профиля они вновь видимы, если их собственная редакция всё ещё approved и работы действительны. При изменении содержимого published service действует старое правило: новая revision и pending. Новые черновики можно сохранять неполными; submit и оба admin-пути проверяют полноту, профиль и выбранные свои работы.

Порядок основных блокировок: строки аккаунтов по возрастанию ID → услуга/заказ. Изменения профиля и аватара используют одну блокировку User; модератор не может подтвердить текст до конкурентной правки. Receipt уникален по actor/operation/request_key; он и результат одной команды фиксируются атомарно. Повтор успешного намерения возвращает исходный response, поэтому клиент после восстановления выполняет GET актуального ресурса. Редакция не заменяет ключ намерения.

## Приватные файлы

Владелец отдельно утвердил PNG/JPEG/WebP/PDF до 10 МиБ и HTTP(S)-ссылки. Сервер не скачивает URL. Бинарные работы имеют сгенерированное имя, валидируются по содержимому, выдаются только владельцу/разрешённому модератору, без публичного alias. Изображения нормализуются, PDF проверяется pypdf 6.21.2 и отдаётся скачиванием с CSP/nosniff. Это не антивирусная гарантия; автоматического исполнения PDF нет. Удаление логическое, политика retention/публичного показа требует отдельного решения. Файлы нельзя потерять из-за отката DB-команды; незакреплённый файл удаляется при исключении. Шаблон Nginx изменён на 12m для multipart, действующий сервер не менялся.

## Переписка и проверка перед доставкой

Conversation связан OneToOne с Order; создание заказа/контекста атомарно. До-заказное обсуждение хранится отдельно в Discussion с уникальной парой buyer/service. Conversation ссылается ровно на Order либо Discussion, что проверяется БД. Новый заказ всегда получает новый контекст; старый discussion не перепривязывается. Sender/время/ID определяет сервер. Уникальный client_message_id и Receipt защищают от повторов. Сообщение stored означает запись и доступность адресату, а не прочтение. Cursor использует отдельный монотонный sequence: ручной release удержанного сообщения получает новый номер, сохраняя message ID, и не теряется за курсором получателя.

Нормализация NFKC/регистр/пробелы/невидимые символы и узкие контекстные правила выполняются до создания доступного адресату сообщения. Held виден только автору. Удержание, обжалование, чтение сотрудником с рабочим основанием и решение создают AuditEvent без копии полного текста. Staff не получает общий API переписки. Автор/участник не решает свой case. Владелец утвердил held/appeal без автоматических наказаний; нет AI, скрытых лимитов банов или финансовых последствий.

## Staff и существующая Django Admin

Новые административные списки read-only, с явными permissions по ресурсу. Отдельные мутации только для согласованной модерации и security case. is_staff сам по себе не раскрывает пользователей/заказы/файлы. Django Admin сохраняется для существующей модерации услуг и справочника; её publisher не обходит approval/полноту. Пользовательский Frontend /admin пока конфликтует с серверным /admin/ и не размещается этой задачей. Полноценные финансы/аналитика/споры/отзывы не заменяются пустыми «успешными» API.

## План будущих миграций и выпуска

1. Получить отдельное разрешение на публикацию и deployment; согласовать точный SHA Backend и совместимый Integration. Текущий код пока не является remote HEAD.
2. Перед production настроить внешнюю копию PostgreSQL и MEDIA_ROOT, секреты хранить отдельно; проверить восстановление. Ни этой копии, ни миграций на live в задаче не выполняли.
3. На изолированной staging Postgres применить полный migration graph: accounts.0004, catalog.0004–0005, operations.0001, orders.0003–0004, conversations.0001–0004. Проверить 3% snapshots, OneToOne contexts, приватные файлы/12m multipart, staff permissions и CSRF.
4. Проверить legacy profile/service rows. Миграции **не одобряют автоматически** прежних исполнителей. Такие услуги будут скрыты до явного профильного одобрения; неполные/с удалёнными выбранными работами исправляются перед публикацией. Не превращать старую отметку published в автоматическое доверие к новому портфолио.
5. Выпускать совместимый сервер с v1+v2. Старый клиент оставляет 3%; новый получает quote 5%, показывает его и создаёт заказ только после согласия. Прежние неоплаченные договорённости не пересчитываются. Включение новых страниц — отдельная проверка Integration, не снятие Demo gate.
6. При остановке выпуска возвращать совместимый код, а не автоматически откатывать schema/снимки. После появления v2 orders прежний код нельзя считать безусловно совместимым: проверить поля и значение subtotal. Финансовая миграция назад/изменение данных не выполняется автоматически.

Источники библиотечных ограничений: [pypdf security](https://pypdf.readthedocs.io/en/stable/user/security.html), [официальный пакет pypdf](https://pypi.org/project/pypdf/). Фактические серверные проверки хранятся в progress/handoff, исторические CI ссылки не выдаются за CI нового неопубликованного кода.
