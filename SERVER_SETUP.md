# STUDLY — подключение купленного сервера

План от 17 октября 2026 года. Это подготовка к размещению, а не отчёт об уже выполненном развёртывании.

## Ресурсы и проверки

- VPS FirstVDS: `153.76.172.88`; по данным владельца Ubuntu 24.04, 2 vCPU, 4 ГБ RAM, 60 ГБ диска.
- Домен в Timeweb: `studly-help.ru`.
- Владелец подтвердил SSH-пользователя `root`, ID сервера `18497152`, дата-центр IXcellerate (Москва), тариф VDS-KVM-NVMe-Разгон-10.0 и установленную панель ispmanager 6 lite. Вход для установки ключа выполнен, но сведения об ОС и службах ещё не прочитаны. Строка `vm18497152#155565` не используется как SSH-логин.
- TCP-соединение с `153.76.172.88:22` успешно проверено с Mac командой `nc -vz -G 5 -w 5`. Это подтверждает доступность порта, но не вход в систему. Запрос публичного ключа SSH типа Ed25519 не вернул ключ; причина не установлена, изменение криптографических настроек сервера не выполнялось.
- Владелец задал пароль `root` в VMmanager. Значение пароля в документацию и файлы проекта не записывается.
- DNS пока возвращает `NXDOMAIN`: проверены NS через `1.1.1.1` и A через `8.8.8.8`. Причина по этому ответу не установлена.
- Владелец отдельно подтвердил, что DNS ещё не настраивал. Для HTTPS остаётся действие в Timeweb: проверить регистрацию и делегирование и указать A-запись основного домена на `153.76.172.88`. Доступа к его кабинету у нас нет.
- В репозитории есть локальная PostgreSQL в `compose.yaml`; готовой конфигурации постоянного размещения пока нет.
- На Mac подготовлен отдельный SSH-ключ. Приватная часть остаётся вне Git и сервера в `~/.ssh/studly_firstvds_ed25519`; на сервер добавляется только `.pub`.
- Через успешное подключение под `root` публичный ключ добавлен в `/root/.ssh/authorized_keys` с сохранением существующих строк. Каталог имеет права `0700`, файл `0600`; сервер вернул `STUDLY_KEY_INSTALLED`. Публичный ключ самого сервера при первом соединении записан в отдельный `~/.ssh/studly_firstvds_known_hosts`; последующие подключения используют `StrictHostKeyChecking=yes`.
- Повторные входы с отключёнными парольными методами завершились `Connection refused` до авторизации. До успешного повтора самостоятельный вход по ключу не считается проверенным. Также наблюдались тайм-ауты соединения; причина нестабильности пока не установлена. Нужна проверка служб и правил доступа из VNC/консоли владельца. Защита и SSH-настройки на сервере не менялись.

## Что требуется от владельца

1. Владелец подтвердил пользователя `root`. Уточнить SSH-порт, если он отличается от стандартного `22`. Пароль не передавать в чат.
2. Публичный ключ уже установлен через SSH; проверить независимый вход только по ключу. При недоступности SSH для диагностики остаются VNC в VMmanager и «Администрирование → Shell-клиент» установленного ispmanager. Переустановка ОС в этот план не входит.
3. В Timeweb проверить, что домен зарегистрирован и делегирован. Если DNS обслуживает Timeweb, для корня домена создать или изменить A-запись на `153.76.172.88`. Поле имени корня в разных панелях обозначается пустым значением, `@` или самим доменом. Если у домена сторонние NS, записи меняются у держателя этих NS. Создание AAAA-записи без рабочего IPv6 сервера не требуется.

Доступ к кабинету регистратора нам не предоставлен; настройки DNS владельцем ещё не подтверждены. Покупка домена сама по себе не устанавливает его A-запись на VPS.

## Порядок дальнейшей работы

1. После установки ключа подключиться по SSH, проверить ОС, ресурсы, существующие службы, порты и конфигурацию доступа. Не заменять неизвестные действующие приложения без изучения.
2. Подготовить конкретную серверную конфигурацию и план запуска процессов на основании проверки. Backend и PostgreSQL должны сохранять данные между перезапусками; PostgreSQL не публикуется в интернете. Секреты создаются отдельно от Git и не выводятся в отчёты.

   На VPS уже установлена ispmanager 6 lite: перед настройкой HTTP/HTTPS проверить её службы и управление конфигурацией веб-сервера. Не устанавливать второй конкурирующий веб-сервер на занятые порты и не удалять панель без изучения. Необходимость и стоимость лицензии панели пока не проверены; новые платные услуги не заказываются.
3. Доработка Telegram OIDC для возврата на сайт завершена локально: [TELEGRAM_WEBSITE_FLOW_PLAN.md](TELEGRAM_WEBSITE_FLOW_PLAN.md). Все 200 серверных тестов, проверки Django, миграций и зависимостей прошли. Контракт и OpenAPI обновлены. Перед размещением выбрать опубликованный коммит и проверить его CI; настоящий вход через Telegram ещё не проверен.
4. Настроить запуск Django через сервер приложений, миграции, служебную статику, приватные аватары и перезапуск после сбоя. Django `runserver` для публичного размещения не использовать.
5. Направить `/api/` и `/admin/` в Django под единым HTTPS-origin. Согласованная версия Frontend размещается без наших изменений `apps/web`; его разработчик подключает API. Версию и готовность интерфейса нужно проверить перед публикацией.
6. После проверки DNS получить бесплатный TLS-сертификат с автоматическим обновлением. Настроить production-параметры Django, доверие к HTTPS-прокси, cookies и CSRF; проверить их настоящими HTTP-запросами.
7. Настроить внешние резервные копии PostgreSQL и аватаров и проверить восстановление перед сохранением настоящих пользовательских данных. Git не является копией этих данных.
8. Подключить Telegram-вход для `https://studly-help.ru`; ожидаемый callback — `https://studly-help.ru/api/v1/auth/telegram/callback/`. Владелец регистрирует параметры через свой BotFather; отдельный Client Secret вводится в приватное окружение. Наличие Bot API token не заменяет этот шаг.
9. Проверить публичные health/ready, права доступа, HTTPS, сессию, CSRF, вход и выход настоящим аккаунтом. Отдельно зафиксировать, какие страницы Frontend реально связаны с Backend.

Платежи остаются отложенными. Наличие сервера не означает готовность к настоящим списаниям и выплатам.
