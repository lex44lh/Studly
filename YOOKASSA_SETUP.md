# STUDLY — настройка тестовой ЮKassa

16 октября 2026 года. ЮKassa согласована как первый кандидат для проверки. Подключение настоящих платежей и совместимость с накоплением заработка ещё не утверждены. Этот этап работает локально и не требует покупки VPS.

## Что уже подготовлено

Backend умеет проверить настройки тестового магазина, получить существующий тестовый платёж и сравнить его с заказом. Сверяются магазин, тестовый режим, идентификаторы платежа/сделки/заказа, валюта RUB и точная сумма из снимка заказа. Позднейшее изменение цены услуги не влияет на эту сверку.

Команда не создаёт платежи, не меняет заказы, не зачисляет заработок и не делает выплаты. `succeeded` в её выводе — наблюдаемое состояние тестового платежа у провайдера. `waiting_for_capture` означает ожидание списания, поэтому не подтверждает завершённое списание. [Процесс платежа ЮKassa](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process).

Код: [клиент](apps/api/payments/yookassa.py), [команда](apps/api/payments/management/commands/check_yookassa_test.py), [локальные тесты](apps/api/payments/tests.py). План до реализации: [YOOKASSA_TEST_PLAN.md](YOOKASSA_TEST_PLAN.md).

## Действия владельца аккаунта

1. Открыть [личный кабинет ЮKassa](https://yookassa.ru/my/) и зарегистрировать аккаунт владельца. Номер телефона, SMS и сведения о владельце заполняются самим владельцем.
2. Запросить у менеджера доступ к тестовой **интернет-площадке «Безопасная сделка»**, сообщив, что ИП/ООО пока нет. Обычный тестовый магазин не подтверждает доступ к этому продукту. [Условия тестирования](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/testing).
3. Передать менеджеру [описание сценария и вопросы](PAYMENT_PROVIDER_QUESTIONS.md): физические лица, накопление, вывод по кнопке, срок хранения, распределение денег, комиссии и возвраты. Этот текст ещё не отправлялся.
4. После выдачи доступа получить `shopId` и секретный ключ именно тестовой площадки. Поля находятся в настройках магазина и разделе интеграции. [Аутентификация API](https://yookassa.ru/developers/using-api/interaction-format).

Секретный ключ хранится только в локальном игнорируемом `apps/api/.env`, без отправки в чат и Git. В существующий файл добавить две строки с полученными значениями, сохранив остальные настройки:

```dotenv
YOOKASSA_TEST_SHOP_ID=
YOOKASSA_TEST_SECRET_KEY=
```

Наличие строк с пустыми значениями не является настройкой. В Git находится только [пример окружения](apps/api/.env.example); настоящий `.env` на этом этапе не менялся. Ключ Telegram-бота не даёт доступа к ЮKassa.

## Проверка на компьютере

Все команды выполнять из корня репозитория. Для первых двух PostgreSQL не нужна.

Проверка наличия и формата настроек, без сети:

```bash
apps/api/.venv/bin/python apps/api/manage.py check_yookassa_test
```

При отсутствии настроек команда сообщает имена недостающих переменных и завершается с ошибкой. Значения секретов не печатаются. При наличии настроек этот режим ещё не доказывает их действительность.

Проверка доступа к магазину через HTTPS API ЮKassa:

```bash
apps/api/.venv/bin/python apps/api/manage.py check_yookassa_test --connect
```

Команда получает `/me` и требует точного совпадения `account_id` и `test=true`. Она не создаёт сделку, поэтому отдельно предупреждает, что доступность Безопасной сделки ещё не проверена. Описание [настроек магазина](https://yookassa.ru/developers/solutions-for-platforms/partners-api/quick-start) показывает эти поля; в STUDLY используется Basic Auth, а не партнёрский OAuth.

Когда появятся существующий тестовый платёж и соответствующий заказ в локальной PostgreSQL, доступна сверка:

```bash
apps/api/.venv/bin/python apps/api/manage.py check_yookassa_test \
  --order-id <ID-заказа-STUDLY> \
  --payment-id <ID-тестового-платежа> \
  --deal-id <ID-тестовой-сделки>
```

Угловые скобки обозначают значения для замены, такую команду нельзя копировать без подстановки. Не используйте демонстрационные услуги для оформления настоящего заказа. Платёж должен содержать `metadata.order_id` как строковый ID заказа, ссылку на ожидаемую сделку и итоговую сумму заказа с надбавкой 3%.

Все три идентификатора передаются вместе. Они заданы оператором вручную, поэтому результат этой диагностики не разрешает автоматически зачислять деньги. Для рабочего приёма оплаты потребуется сохраняемая сервером связь заказа с попыткой оплаты; такой модели пока нет.

## Что мешает следующему шагу

При создании платежа Безопасной сделки нужно сразу указать сумму для исполнителя; вознаграждение площадки должно покрывать комиссию ЮKassa. Это следует из [требований к платежу](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payments). Из согласованных 3% заказчика нельзя вывести окончательную сумму исполнителю: его комиссия отложена до отдельного решения, тариф провайдера не подтверждён. Нулевую или постоянную комиссию исполнителя код не предполагает.

До создания платежей нужно согласовать распределение, обработку отмены при незавершённой оплате и позднего списания. Для накопления также нужно подтверждение условий провайдера: сделки имеют ограниченный срок. Список открытых решений сохранён в [PAYMENTS_PLAN.md](PAYMENTS_PLAN.md).

Для проверки исходящих GET-запросов публичный HTTPS-адрес STUDLY не нужен. Приём уведомлений и полноценный пользовательский сценарий потребуют отдельной настройки адресов. Публичный маршрут уведомлений, кнопка оплаты и создание платёжных объектов пока не добавлены.

## Результат локальной проверки

Все 154 серверных теста прошли на отдельной PostgreSQL, включая 24 новых теста клиента и диагностической команды. HTTP-ответы ЮKassa в этих тестах подменяются, поэтому это не проведённые сделки у провайдера. Проверены отсутствие изменений заказа при успешной/неуспешной сверке и позднем успехе после отмены, точные суммы, состояния и ошибки; новые зависимости и миграции не требуются.

На текущем компьютере команда без параметров подтвердила отсутствие двух настроек ЮKassa. Настоящих запросов с ключами и сверки существующего платежа ещё не было. Frontend не изменялся.
