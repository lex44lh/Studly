# STUDLY — действующий контракт Backend

Обновлено 16 октября 2026 года. Это описание реализованных маршрутов Django. Backend-разработчик не менял `apps/web`. Новая регистрация Frontend находится в ветке друга `codex/frontend-registration`; реальный обмен её форм с Django ещё не проверен. Реализованы оформление заказа, согласие исполнителя, отмена заказчиком до оплаты и отказ исполнителя до согласия. Для первой версии выбран отдельный сайт с Telegram-входом и рублёвой оплатой; платёжный провайдер ещё не подключён.

Добавлены серверная регистрация, совместимые роли, профиль и прогресс. Полный контракт, аватар, сессии и инструкции подключения: [REGISTRATION_API.md](REGISTRATION_API.md). OpenAPI для согласования: [registration.openapi.json](docs/registration.openapi.json). Краткий `/auth/me/` сохранил прежний формат.

Локальный Backend: `http://127.0.0.1:8000`. Все пути ниже заканчиваются `/`. JSON передаётся с `Content-Type: application/json`. В примерах условные ID: брать настоящие значения нужно из ответа API, а не из статического массива Frontend.

Навигация: [API](http://127.0.0.1:8000/api/v1/). При `DEBUG=true` запрос браузера с `Accept: text/html` получает стандартный интерфейс DRF. Запросы с `Accept: application/json` и без указания формата по-прежнему получают JSON. При `DEBUG=false` HTML-представление API отключено; это не отключает отдельную защищённую панель `/admin/`.

## Публичное чтение

| Запрос | Ответ |
|---|---|
| `GET /api/v1/` | Ссылки на действующие разделы API и панель администратора; без запросов к БД |
| `GET /api/v1/health/` | `200 {"status":"ok"}`: работает HTTP, база не проверяется |
| `GET /api/v1/ready/` | `200 {"status":"ok"}`: доступна PostgreSQL; иначе `503 {"status":"unavailable"}` |
| `GET /api/v1/services/` | Страница опубликованных услуг |
| `GET /api/v1/services/<id>/` | Опубликованная услуга; скрытая или отсутствующая — `404` |
| `GET /api/v1/services/<id>/quote/` | Предварительный расчёт цены услуги с надбавкой заказчика 3%; только RUB |
| `GET /api/v1/performers/<id>/` | Публичный профиль исполнителя хотя бы с одной опубликованной услугой; иначе `404` |

Параметры списка услуг:

- `search=Python`: поиск по названию и описанию средствами DRF.
- `performer=42`: услуги конкретного исполнителя.
- `ids=1,2,3`: до 100 положительных ID, например для локального избранного. `ids=` возвращает пустую выборку. ID отсутствующих или скрытых услуг не возвращаются.
- `page=2`: следующая страница; размер страницы 20. Порядок — по возрастанию ID. Некорректный ID фильтра даёт `400`; недоступная страница — `404`.

Формат услуги:

```json
{
  "id": 42,
  "title": "Консультация по Python",
  "description": "Объясню основы языка",
  "price_amount": "900.00",
  "currency": "RUB",
  "duration_days": 4,
  "performer": {"id": 7, "name": "Имя исполнителя"},
  "included": ["Разбор вопросов"],
  "is_demo": false
}
```

Список оборачивается в `{"count":1,"next":null,"previous":null,"results":[...]}`. Для перехода можно использовать `next`; это URL следующей страницы. Цена — строка десятичного числа, без символа валюты. Отображение «900 ₽» и «4 дня» выполняет Frontend. Числа рейтинга, отзывы и статистика не возвращаются: их серверная логика ещё не реализована. У демонстрационных записей всегда `is_demo: true`.

Профиль исполнителя: `{"id":7,"name":"Имя исполнителя","about":"Описание"}`. Telegram ID, пароль, служебные права и OIDC subject публично не выдаются.

## Предварительный расчёт для заказчика

Публичный `GET /api/v1/services/<id>/quote/` берёт текущую цену опубликованной услуги из PostgreSQL. Вход для просмотра расчёта не требуется. Пример для услуги за 1 000 ₽:

```json
{
  "service_id": 42,
  "service_revision": 1,
  "price_amount": "1000.00",
  "currency": "RUB",
  "is_demo": false,
  "buyer_fee_percent": "3.00",
  "buyer_fee_amount": "30.00",
  "total_amount": "1030.00"
}
```

Денежные значения и процент — десятичные строки с двумя знаками после точки. Backend считает надбавку от цены услуги через `Decimal` и округляет её до копеек методом `ROUND_HALF_UP`: половина копейки округляется вверх. Затем складывает цену и округлённую надбавку. Например, для цены `0.50` надбавка `0.02`, итог `0.52`. Текущий каталог допускает цену `0.00`: её расчёт тоже нулевой, но сценарий бесплатного заказа пока не определён.

Цена и процент не принимаются от клиента: параметры запроса не меняют расчёт. Комиссия исполнителя и расходы платёжного провайдера в ответ не включаются. Полученный черновик статусов и ставок исполнителя не утверждён; владелец прямо исключил автоматические статусы, рейтинг и комиссию исполнителя из текущего этапа. Постоянная ставка исполнителя 10% в данных не задаётся. `is_demo: true` явно обозначает расчёт для демонстрационной услуги.

Ответ не кэшируется (`Cache-Control: no-store, no-cache`). Это текущий предварительный расчёт, а не сохранённое предложение или резервирование цены: `service_revision` обозначает прочитанную редакцию. После редактирования услуга скрывается до модерации и расчёт возвращает `404`; после повторной публикации используются новая цена и редакция. Скрытая или отсутствующая услуга — `404`; другая валюта — `400 {"currency":"Расчёт доступен только для услуг в RUB."}`. POST, PUT, PATCH, DELETE — `405`.

Запрос не создаёт заказ, платёж, баланс или выплату и не подтверждает оплату. Правила фиксации цены в будущем заказе определяются отдельно. Разработчик Frontend может использовать API для отображения расчёта, но текущий `apps/web` к нему ещё не подключён.

## Сессия и Telegram

| Запрос | Результат |
|---|---|
| `GET /api/v1/auth/options/` | `telegram_mini_app` и `telegram_website`: настроены ли соответствующие способы входа на сервере |
| `GET /api/v1/auth/csrf/` | CSRF-cookie и `{"csrf_token":"..."}` |
| `POST /api/v1/auth/telegram/mini-app/` | Проверяет `{"init_data":"исходная строка Telegram.WebApp.initData"}`, создаёт сессию |
| `GET /api/v1/auth/telegram/start/` | `302`: переход на страницу Telegram для входа на сайте |
| `GET /api/v1/auth/telegram/callback/` | Проверяет ответ Telegram, создаёт сессию; сейчас возвращает JSON профиля |
| `GET /api/v1/auth/me/` | Текущий пользователь; без входа `403` |
| `POST /api/v1/auth/logout/` | `204`: выход; без входа `403` |

Успешный вход и `/me/` возвращают `{"user":{"id":7,"display_name":"Имя","telegram_username":"username"}}`. Это внутренний ID STUDLY, а не Telegram ID. Один аккаунт используется для заказчика и исполнителя.

Последовательность Mini App: получить CSRF-токен → отправить исходный `initData` заголовком `X-CSRFToken` и JSON-телом → сохранить полученную браузером session-cookie → читать `/me/`. `initDataUnsafe` не заменяет подписанную строку. После входа CSRF-токен меняется: перед следующим POST получить новый через `/csrf/`.

Запросы должны сохранять cookie. Для первой интеграции предполагается общий origin интерфейса и API: инфраструктура направляет `/api/` в Django. В актуальном Frontend этого маршрута пока нет. `CSRF_TRUSTED_ORIGINS` само по себе не включает CORS. Подключение разных доменов и совместимость cookie во всех клиентах Telegram ещё требуют проверки.

`auth/options` не подтверждает успешный вход настоящего пользователя или правильность внешних настроек Telegram. Отдельный бот-токен не заменяет OIDC Client Secret. Callback пока завершает вход JSON-ответом; переход обратно на страницу интерфейса согласуем при подключении.

## Создание, исправление услуги и свои заявки

Требуются сессия пользователя и CSRF для POST и PATCH. Без входа эти маршруты возвращают `403`; чужая услуга на личном маршруте — `404`. Создание и исправление принимают только JSON; другой формат тела — `415`.

| Запрос | Результат |
|---|---|
| `GET /api/v1/my/services/` | Свои услуги всех статусов, пагинация по 20 |
| `POST /api/v1/my/services/` | Создание услуги, `201`; начальный статус всегда `pending` |
| `GET /api/v1/my/services/<id>/` | Своя услуга с текущим статусом |
| `PATCH /api/v1/my/services/<id>/` | Исправление своей услуги и повторная отправка на модерацию, `200` |

Тело создания:

```json
{
  "title": "Консультация по Python",
  "description": "Объясню основы языка",
  "price_amount": "900.00",
  "currency": "RUB",
  "duration_days": 4,
  "included": ["Разбор вопросов"]
}
```

Название, описание, цена и срок обязательны. `currency` необязательна, по умолчанию `RUB`; другие валюты пока не принимаются. `included` необязателен, по умолчанию пустой список. Технические ограничения: название до 200 символов; цена от `0.00` до `99999999.99`, не более двух знаков после точки; срок — целое число от 1 до 32767; до 50 непустых пунктов состава услуги, каждый до 500 символов. Ошибки возвращаются с `400` по именам полей.

Ответ создания, исправления, личного списка и детали имеет поля публичной услуги плюс `status`. Исполнитель определяется из сессии. Передача `id`, `performer`, `status`, `is_demo`, `demo_key`, внутренней `revision` и других неподдерживаемых полей возвращает `400`: клиент не назначает эти значения.

При PATCH передаются только сохраняемые поля, например:

```json
{"title": "Консультация по Python и Django", "price_amount": "950.00"}
```

Непереданные поля сохраняют прежние значения. Допустимы те же поля и ограничения, что при создании. Пустой объект `{}` возвращает `400`; валидный непустой PATCH всегда устанавливает `pending`, даже если значения совпали с прежними. Опубликованная услуга сразу исчезает из каталога; отклонённая или уже ожидающая решения также может быть исправлена. Сохранение содержания, номера редакции и статуса выполняется одной транзакцией с блокировкой записи. Ошибки проверки не меняют услугу. PUT и DELETE на личной детали не поддерживаются (`405` при действительной сессии и CSRF).

Для проверки из браузерного интерфейса DRF после входа используйте поле `Content` с JSON из примера. Не отправляйте полный ответ API обратно: он содержит служебные поля только для чтения. Открытие интерфейса DRF само по себе не выполняет вход и не даёт права записи.

| Статус | Значение | Видимость в публичном каталоге |
|---|---|---|
| `pending` | Ожидает решения модератора | Скрыта |
| `published` | Одобрена | Видна |
| `rejected` | Отклонена | Скрыта |

Удаление, причина отклонения и отдельное снятие с публикации без исправления пока не реализованы; их правила ещё нужно согласовать. Публичный `/services/` остаётся доступен только для чтения: создание и исправление выполняются через `/my/services/`.

## Заказы: оформление, согласие, отмена и отказ

Все маршруты заказов требуют действительную сессию активного пользователя. Для POST также нужен `X-CSRFToken`; получение токена и сохранение cookie описаны в разделе входа выше. Тела запросов — JSON. Без входа или с неверным CSRF возвращается `403`. Ответы запрещают кэширование. Заказчик и исполнитель видят только заказы, в которых участвуют.

| Запрос | Назначение |
|---|---|
| `GET /api/v1/orders/` | Личный список в обеих ролях; по 20 записей, сначала новые по ID |
| `POST /api/v1/orders/` | Оформление заказа, `201`; повтор уже выполненного запроса — `200` |
| `GET /api/v1/orders/<id>/` | Детали заказа для одного из участников; постороннему и для отсутствующего ID — `404` |
| `POST /api/v1/orders/<id>/accept/` | Согласие исполнителя, `200`; повтор возвращает тот же заказ без изменения времени согласия |
| `POST /api/v1/orders/<id>/cancel/` | Заказчик отменяет до оплаты, `200`; разрешено до и после согласия исполнителя |
| `POST /api/v1/orders/<id>/decline/` | Исполнитель отказывается до своего согласия, `200` |

Перед оформлением нужно получить услугу и её `/quote/`, показать заказчику условия и итог с 3%, затем отправить:

```json
{
  "service_id": 42,
  "service_revision": 1,
  "request_key": "b390810f-10c2-45db-812f-5222bcf4ff78"
}
```

Все три поля обязательны. `service_id` и `service_revision` — положительные целые числа до `9223372036854775807`; редакция берётся из `/quote/`. `request_key` — UUID, который клиент генерирует один раз для конкретного оформления. Для новой намеренной покупки, в том числе той же услуги, нужен новый ключ.

**Повтор после обрыва связи:** отправить те же три значения. Если первый запрос уже оформил заказ, сервер вернёт существующую запись с `200`, даже если объявление позднее изменилось или скрылось. Если с этим ключом уже оформлены другие ID услуги или редакция, возвращается `409`. Один ключ действует в пределах одного заказчика; ключ другого пользователя не даёт доступа к его записи. Ключ не заменяет сессию или CSRF.

Заказывать можно только реальные (`is_demo: false`) опубликованные услуги с положительной ценой в RUB у другого активного пользователя. Скрытая или отсутствующая услуга — `404`; демонстрационная, бесплатная, собственная, услуга недоступного исполнителя или другой валюты — `400`. Нулевая цена по-прежнему допустима в каталоге и предварительном расчёте, но не в заказах этого этапа.

Если редакция объявления уже изменилась, создание возвращает `409` с полем `service_revision`; заказа при этом не возникает. Нужно получить обновлённые услугу и расчёт и снова показать их заказчику. Не следует автоматически отправлять новую цену без подтверждения пользователя.

Клиент не передаёт цену, комиссию, валюту, участников, содержание услуги или статус. Такие и любые другие поля вне трёх разрешённых возвращают `400`. Заказчик определяется из сессии, исполнитель — из услуги. Цена, надбавка 3%, итог, название, описание, состав и срок сохраняются на сервере отдельным снимком. Последующее редактирование объявления не меняет условия уже оформленного заказа. Числа цены и округление те же, что в `/quote/`.

Пример ответа оформления и формат детали/элемента списка:

```json
{
  "id": 15,
  "service_id": 42,
  "service_revision": 1,
  "request_key": "b390810f-10c2-45db-812f-5222bcf4ff78",
  "buyer": {"id": 8, "name": "Заказчик"},
  "performer": {"id": 7, "name": "Исполнитель"},
  "title": "Консультация по Python",
  "description": "Объясню основы языка",
  "included": ["Разбор вопросов"],
  "duration_days": 4,
  "price_amount": "1000.00",
  "currency": "RUB",
  "buyer_fee_percent": "3.00",
  "buyer_fee_amount": "30.00",
  "total_amount": "1030.00",
  "status": "pending_acceptance",
  "created_at": "2026-10-16T09:00:00Z",
  "accepted_at": null,
  "closed_at": null,
  "closed_by": null
}
```

Имена участников берутся из их текущих профилей; сохранённый снимок относится к условиям услуги. Telegram ID, email, пароль и служебные права участникам через этот ответ не выдаются. Денежные значения — строки; список оборачивается в `count`, `next`, `previous`, `results`, как каталог. ID и дата примера условные.

Для согласия исполнитель отправляет `POST /api/v1/orders/<id>/accept/` с `{}`. Ответ имеет тот же формат, но `status: "awaiting_payment"` и заполненное `accepted_at` в UTC. Заказчик не может принять заказ за исполнителя (`403`); посторонний получает `404`. Передача дополнительных полей в согласии — `400`. Изменившееся или скрывшееся после оформления объявление не мешает исполнителю согласиться с сохранёнными условиями заказа.

| Состояние | Значение |
|---|---|
| `pending_acceptance` | Заказ оформлен, исполнитель ещё не согласился |
| `awaiting_payment` | Исполнитель согласился, заказ ожидает оплаты |
| `cancelled` | Заказчик отменил неоплаченный заказ |
| `declined` | Исполнитель отказался до согласия |

Для отмены заказчик отправляет `POST /api/v1/orders/<id>/cancel/` с `{}`. Допустимые исходные состояния — `pending_acceptance` и `awaiting_payment`. Для отказа исполнитель отправляет `POST /api/v1/orders/<id>/decline/` с `{}`; допустимо только `pending_acceptance`. Участник другой роли получает `403`, посторонний — `404`. Отказ после согласия — `409`.

Ответы отмены и отказа имеют полный формат заказа. Поле `closed_at` содержит время действия в UTC, `closed_by` — объект `{"id":8,"name":"Заказчик"}` соответствующего участника. Оба поля равны `null`, пока заказ открыт; они добавлены в ответы создания, деталей, списка и согласия. При отмене после согласия `accepted_at` сохраняется. Состав услуги и все суммы не меняются.

Повтор того же действия его участником возвращает `200` и уже существующую запись без изменения автора или времени. Закрытый заказ остаётся доступен обоим участникам. Принять закрытый заказ или заменить отмену отказом и наоборот нельзя (`409`). Если повторить первоначальное оформление с тем же `request_key`, сервер вернёт этот закрытый заказ с `200`; новый заказ самопроизвольно не появится. Причина закрытия отдельным полем пока не поддерживается; любые дополнительные поля в POST-действиях — `400`, неподдерживаемый тип тела — `415`.

**Граница этапа:** в реализованных состояниях подтверждённой оплаты ещё нет. Отмена неоплаченного заказа не выполняет возврат денег. Обработчика платежей и перехода к выполнению пока нет. `duration_days` хранит согласованный срок услуги, но не означает, что уже вычислен дедлайн или начата работа. Комиссия исполнителя, рейтинги, баланс и выплаты в ответ не входят и не рассчитываются. Дополнительные опции, файлы, передача результата и завершение пока не реализованы; произвольное изменение заказа через PUT/PATCH/DELETE не поддерживается (`405` при действительной сессии и CSRF).

Сохранение заказа и проверка редакции выполняются в транзакции с блокировкой услуги. Согласие, отмена и отказ блокируют одну строку заказа: одновременные запросы соблюдают те же правила переходов. В базе дополнительно проверяются уникальность ключа у заказчика, разные участники, положительная цена, RUB, равенство итога цене с надбавкой и соответствие статуса истории согласия/закрытия, включая правильную роль автора закрытия.

## Модерация

Административная панель Backend: `http://127.0.0.1:8000/admin/`. Это стандартный служебный интерфейс Django, исходники Frontend друга он не затрагивает.

Для первого локального администратора владелец выполняет из `apps/api` интерактивную команду:

```bash
.venv/bin/python manage.py createsuperuser
```

Укажите собственный Telegram ID числом (личный ID, не ID бота) и отдельный пароль администратора. Пароль вводится в терминале без отображения; это не токен бота. Автоматическая служебная учётная запись или обход входа в этом этапе не создавались. В обычном Telegram-входе пароль от пользователя не запрашивается.

Модератору нужны `is_staff` и разрешение `catalog.moderate_service`. Суперпользователь получает все разрешения автоматически. Обычный пользователь и сотрудник только с правом просмотра не могут принять решение.

Порядок: открыть раздел услуг → отфильтровать «На модерации» → выбрать записи → действие «Одобрить и опубликовать» или «Отклонить» → просмотреть содержание на странице подтверждения → подтвердить решение. До последнего шага данные не меняются.

Подтверждение подписано сервером, действует 30 минут и связано с модератором, выбранным решением и номерами просмотренных редакций. Если автор успел изменить услугу, старое подтверждение её не публикует: нужно просмотреть новую редакцию. Решения применяются только к реальным услугам со статусом `pending`. Повторная отправка действия не меняет уже принятое решение. Кто принял решение, по какой записи и редакции, сохраняется в журнале Django. Содержание услуги в панели доступно только для чтения.

Существующие демоуслуги остаются опубликованными с `is_demo: true`; это демонстрация, а не реальные одобренные объявления. Новая пользовательская запись всегда реальная и ожидает решения.

## Что ещё не подключено

Категории, изображения и загрузка файлов, сообщения, платежи, отзывы и уведомления ещё не имеют серверной реализации. У заказов работают оформление, личный просмотр, согласие исполнителя, отмена заказчиком до оплаты и отказ исполнителя до согласия; выполнение и завершение ждут следующих этапов. Не следует показывать успешную оплату или публикацию по локальному действию браузера. Отдельные переходы этих процессов нужно согласовать до реализации.
