Запросы с `Accept: application/json` и без указания формата по-прежнему получают JSON. При `DEBUG=false` HTML-представление API отключено; это не отключает отдельную защищённую панель `/admin/`.

## Публичное чтение

| Запрос | Ответ |
|---|---|
| `GET /api/v1/` | Ссылки на действующие разделы API и панель администратора; без запросов к БД |
| `GET /api/v1/health/` | `200 {"status":"ok"}`: работает HTTP, база не проверяется |
| `GET /api/v1/ready/` | `200 {"status":"ok"}`: доступна PostgreSQL; иначе `503 {"status":"unavailable"}` |
| `GET /api/v1/services/` | Страница опубликованных услуг |
| `GET /api/v1/services/<id>/` | Опубликованная услуга; скрытая или отсутствующая — `404` |
| `GET /api/v1/services/<id>/quote/` | Предварительный расчёт цены услуги с надбавкой заказчика 3%; только RUB |
| `GET /api/v1/performers/<id>/` | Публичный профиль исполнителя хотя бы с одной опубликованной услугой; иначе `404` |

Параметры списка услуг:

- С 24 октября в обеих версиях: category — точное значение сохранённой строки; min_price/max_price — неотрицательные decimal-строки до 99999999.99 с точностью до копейки; min_duration/max_duration — целые дни 1–32767. Верхняя граница меньше нижней — 400. ordering: id (default), newest, price_asc, price_desc, duration_asc; равные значения стабилизируются ID. min_rating пока даёт 400, так как источник рейтинга не реализован.
- `search=Python`: поиск по названию и описанию средствами DRF.
- `performer=42`: услуги конкретного исполнителя.
- `ids=1,2,3`: до 100 положительных ID, например для локального избранного. `ids=` возвращает пустую выборку. ID отсутствующих или скрытых услуг не возвращаются.
- `page=2`: следующая страница; размер страницы 20. Порядок — по возрастанию ID. Некорректный ID фильтра даёт `400`; недоступная страница — `404`.

Формат услуги:

```json
{
  "id": 42,
  "title": "Консультация по Python",
  "description": "Объясню основы языка",
  "price_amount": "900.00",
  "currency": "RUB",
  "duration_days": 4,
  "performer": {"id": 7, "name": "Имя исполнителя"},
  "included": ["Разбор вопросов"],
  "is_demo": false
}
```

Список оборачивается в `{"count":1,"next":null,"previous":null,"results":[...]}`. Для перехода можно использовать `next`; это URL следующей страницы. Цена — строка десятичного числа, без символа валюты. Отображение «900 ₽» и «4 дня» выполняет Frontend. Числа рейтинга, отзывы и статистика не возвращаются: их серверная логика ещё не реализована. У демонстрационных записей всегда `is_demo: true`.

Профиль исполнителя: `{"id":7,"name":"Имя исполнителя","about":"Описание"}`. Telegram ID, пароль, служебные права и OIDC subject публично не выдаются.

## Предварительный расчёт для заказчика

Публичный `GET /api/v1/services/<id>/quote/` берёт текущую цену опубликованной услуги из PostgreSQL. Вход для просмотра расчёта не требуется. Пример для услуги за 1 000 ₽:

```json
{
  "service_id": 42,
  "service_revision": 1,
  "price_amount": "1000.00",
  "currency": "RUB",
  "is_demo": false,
  "buyer_fee_percent": "3.00",
  "buyer_fee_amount": "30.00",
  "total_amount": "1030.00"
}
```

Денежные значения и процент — десятичные строки с двумя знаками после точки. Backend считает надбавку от цены услуги через `Decimal` и округляет её до копеек методом `ROUND_HALF_UP`: половина копейки округляется вверх. Затем складывает цену и округлённую надбавку. Например, для цены `0.50` надбавка `0.02`, итог `0.52`. Текущий каталог допускает цену `0.00`: её расчёт тоже нулевой, но сценарий бесплатного заказа пока не определён.

Цена и процент не принимаются от клиента: параметры запроса не меняют расчёт. Комиссия исполнителя и расходы платёжного провайдера в ответ не включаются. Полученный черновик статусов и ставок исполнителя не утверждён; владелец прямо исключил автоматические статусы, рейтинг и комиссию исполнителя из текущего этапа. Постоянная ставка исполнителя 10% в данных не задаётся. `is_demo: true` явно обозначает расчёт для демонстрационной услуги.

Ответ не кэшируется (`Cache-Control: no-store, no-cache`). Это текущий предварительный расчёт, а не сохранённое предложение или резервирование цены: `service_revision` обозначает прочитанную редакцию. После редактирования услуга скрывается до модерации и расчёт возвращает `404`; после повторной публикации используются новая цена и редакция. Скрытая или отсутствующая услуга — `404`; другая валюта — `400 {"currency":"Расчёт доступен только для услуг в RUB."}`. POST, PUT, PATCH, DELETE — `405`.

Запрос v1 не создаёт quote-запись, заказ, платёж, баланс или выплату и не подтверждает оплату. Снимок фиксируется при создании заказа v1. Для сохраняемого расчёта с 5% применяется новый v2-контракт ниже; Integration переключает клиента отдельно.

## Сессия и Telegram

| Запрос | Результат |
|---|---|
| `GET /api/v1/auth/options/` | `telegram_mini_app` и `telegram_website`: настроены ли соответствующие способы входа на сервере |
| `GET /api/v1/auth/csrf/` | CSRF-cookie и `{"csrf_token":"..."}` |
| `POST /api/v1/auth/telegram/mini-app/` | Проверяет `{"init_data":"исходная строка Telegram.WebApp.initData"}`, создаёт сессию |
| `GET /api/v1/auth/telegram/start/` | `302`: переход на Telegram; необязательный `next` задаёт относительный путь возврата на сайт |
| `GET /api/v1/auth/telegram/callback/` | Проверяет Telegram, создаёт сессию; без исходного `next` — JSON, с ним — `303` на сохранённый путь |
| `GET /api/v1/auth/me/` | Текущий пользователь; без входа `403` |
| `POST /api/v1/auth/logout/` | `204`: выход; без входа `403` |

Успешный вход и `/me/` возвращают `{"user":{"id":7,"display_name":"Имя","telegram_username":"username"}}`. Это внутренний ID STUDLY, а не Telegram ID. Один аккаунт используется для заказчика и исполнителя.

Последовательность Mini App: получить CSRF-токен → отправить исходный `initData` заголовком `X-CSRFToken` и JSON-телом → сохранить полученную браузером session-cookie → читать `/me/`. `initDataUnsafe` не заменяет подписанную строку. После входа CSRF-токен меняется: перед следующим POST получить новый через `/csrf/`.

Запросы должны сохранять cookie. Для первой интеграции предполагается общий origin интерфейса и API: инфраструктура направляет `/api/` в Django. В актуальном Frontend этого маршрута пока нет. `CSRF_TRUSTED_ORIGINS` само по себе не включает CORS. Подключение разных доменов и совместимость cookie во всех клиентах Telegram ещё требуют проверки.

`auth/options` не подтверждает успешный вход настоящего пользователя или правильность внешних настроек Telegram. Отдельный бот-токен не заменяет OIDC Client Secret. Для возврата на сайт открывать, например, `/api/v1/auth/telegram/start/?next=%2Fregister%2Froles` обычной навигацией браузера. Допускается один непустой путь от корня текущего origin до 2048 символов; внешний, неоднозначный или повторный `next` даёт `400 invalid_return_path`. Сохраняется только проверенный путь из начала входа; `next` в callback игнорируется. Ошибки не перенаправляют браузер; после обработки попытки, в том числе при `503`, нужен новый вход через `/start/`. Полный порядок и обновление CSRF после входа: [REGISTRATION_API.md](REGISTRATION_API.md).

## Создание, исправление услуги и свои заявки

Требуются сессия пользователя и CSRF для POST и PATCH. Без входа эти маршруты возвращают `403`; чужая услуга на личном маршруте — `404`. Создание и исправление принимают только JSON; другой формат тела — `415`.

| Запрос | Результат |
|---|---|
| `GET /api/v1/my/services/` | Свои услуги всех статусов, пагинация по 20 |
| `POST /api/v1/my/services/` | Создание услуги, `201`; начальный статус всегда `pending` |
| `GET /api/v1/my/services/<id>/` | Своя услуга с текущим статусом |
| `PATCH /api/v1/my/services/<id>/` | Исправление своей услуги и повторная отправка на модерацию, `200` |

Тело создания:

```json
{
  "title": "Консультация по Python",
  "description": "Объясню основы языка",
  "price_amount": "900.00",
  "currency": "RUB",
  "duration_days": 4,
  "included": ["Разбор вопросов"]
}
```

Название, описание, цена и срок обязательны. `currency` необязательна, по умолчанию `RUB`; другие валюты пока не принимаются. `included` необязателен, по умолчанию пустой список. Технические ограничения: название до 200 символов; цена от `0.00` до `99999999.99`, не более двух знаков после точки; срок — целое число от 1 до 32767; до 50 непустых пунктов состава услуги, каждый до 500 символов. Ошибки возвращаются с `400` по именам полей.

Ответ создания, исправления, личного списка и детали имеет поля публичной услуги плюс `status`. Исполнитель определяется из сессии. Передача `id`, `performer`, `status`, `is_demo`, `demo_key`, внутренней `revision` и других неподдерживаемых полей возвращает `400`: клиент не назначает эти значения.

При PATCH передаются только сохраняемые поля, например:

```json
{"title": "Консультация по Python и Django", "price_amount": "950.00"}
```

Непереданные поля сохраняют прежние значения. Допустимы те же поля и ограничения, что при создании. Пустой объект `{}` возвращает `400`; валидный непустой PATCH всегда устанавливает `pending`, даже если значения совпали с прежними. Опубликованная услуга сразу исчезает из каталога; отклонённая или уже ожидающая решения также может быть исправлена. Сохранение содержания, номера редакции и статуса выполняется одной транзакцией с блокировкой записи. Ошибки проверки не меняют услугу. PUT и DELETE на личной детали не поддерживаются (`405` при действительной сессии и CSRF).

Для проверки из браузерного интерфейса DRF после входа используйте поле `Content` с JSON из примера. Не отправляйте полный ответ API обратно: он содержит служебные поля только для чтения. Открытие интерфейса DRF само по себе не выполняет вход и не даёт права записи.

| Статус | Значение | Видимость в публичном каталоге |
|---|---|---|
| `pending` | Ожидает решения модератора | Скрыта |
| `published` | Одобрена | Видна |
| `rejected` | Отклонена | Скрыта |

В старом DTO своих услуг v1 причина отклонения не возвращается; новый v2 возвращает reason. Удаление услуги и отдельное снятие с публикации без исправления не добавлены. Публичный `/services/` остаётся доступен только для чтения. Создание/исправление v1 теперь требуют роль performer; историческое чтение своих объектов не исчезает при переключении интерфейса. В обоих публичных каталогах реальной услуге нужен активный исполнитель с одобренным профилем; изменение профиля скрывает услуги до решения. Услуги с удалёнными выбранными примерами также не видны.

## Заказы: оформление, согласие, отмена и отказ

Все маршруты заказов требуют действительную сессию активного пользователя. Для POST также нужен `X-CSRFToken`; получение токена и сохранение cookie описаны в разделе входа выше. Тела запросов — JSON. Без входа или с неверным CSRF возвращается `403`. Ответы запрещают кэширование. Заказчик и исполнитель видят только заказы, в которых участвуют.

| Запрос | Назначение |
|---|---|
| `GET /api/v1/orders/` | Личный список в обеих ролях; по 20 записей, сначала новые по ID |
| `POST /api/v1/orders/` | Оформление заказа, `201`; повтор уже выполненного запроса — `200` |
| `GET /api/v1/orders/<id>/` | Детали заказа для одного из участников; постороннему и для отсутствующего ID — `404` |
| `POST /api/v1/orders/<id>/accept/` | Согласие исполнителя, `200`; повтор возвращает тот же заказ без изменения времени согласия |
| `POST /api/v1/orders/<id>/cancel/` | Заказчик отменяет до оплаты, `200`; разрешено до и после согласия исполнителя |
| `POST /api/v1/orders/<id>/decline/` | Исполнитель отказывается до своего согласия, `200` |

Перед оформлением нужно получить услугу и её `/quote/`, показать заказчику условия и итог с 3%, затем отправить:

```json
{
  "service_id": 42,
  "service_revision": 1,
  "request_key": "b390810f-10c2-45db-812f-5222bcf4ff78"
}
```

Все три поля обязательны. `service_id` и `service_revision` — положительные целые числа до `9223372036854775807`; редакция берётся из `/quote/`. `request_key` — UUID, который клиент генерирует один раз для конкретного оформления. Для новой намеренной покупки, в том числе той же услуги, нужен новый ключ.

**Повтор после обрыва связи:** отправить те же три значения. Если первый запрос уже оформил заказ, сервер вернёт существующую запись с `200`, даже если объявление позднее изменилось или скрылось. Если с этим ключом уже оформлены другие ID услуги или редакция, возвращается `409`. Один ключ действует в пределах одного заказчика; ключ другого пользователя не даёт доступа к его записи. Ключ не заменяет сессию или CSRF.

Заказывать можно только реальные (`is_demo: false`) опубликованные услуги с положительной ценой в RUB у другого активного пользователя. Скрытая или отсутствующая услуга — `404`; демонстрационная, бесплатная, собственная, услуга недоступного исполнителя или другой валюты — `400`. Нулевая цена по-прежнему допустима в каталоге и предварительном расчёте, но не в заказах этого этапа.

Если редакция объявления уже изменилась, создание возвращает `409` с полем `service_revision`; заказа при этом не возникает. Нужно получить обновлённые услугу и расчёт и снова показать их заказчику. Не следует автоматически отправлять новую цену без подтверждения пользователя.

Клиент не передаёт цену, комиссию, валюту, участников, содержание услуги или статус. Такие и любые другие поля вне трёх разрешённых возвращают `400`. Заказчик определяется из сессии, исполнитель — из услуги. Цена, надбавка 3%, итог, название, описание, состав и срок сохраняются на сервере отдельным снимком. Последующее редактирование объявления не меняет условия уже оформленного заказа. Числа цены и округление те же, что в `/quote/`.

Пример ответа оформления и формат детали/элемента списка:

```json
{
  "id": 15,
  "service_id": 42,
  "service_revision": 1,
  "request_key": "b390810f-10c2-45db-812f-5222bcf4ff78",
  "buyer": {"id": 8, "name": "Заказчик"},
  "performer": {"id": 7, "name": "Исполнитель"},
  "title": "Консультация по Python",
  "description": "Объясню основы языка",
  "included": ["Разбор вопросов"],
  "duration_days": 4,
  "price_amount": "1000.00",
  "currency": "RUB",
  "buyer_fee_percent": "3.00",
  "buyer_fee_amount": "30.00",
  "total_amount": "1030.00",
  "status": "pending_acceptance",
  "created_at": "2026-10-16T09:00:00Z",
  "accepted_at": null,
  "closed_at": null,
  "closed_by": null
}
```

Имена участников берутся из их текущих профилей; сохранённый снимок относится к условиям услуги. Telegram ID, email, пароль и служебные права участникам через этот ответ не выдаются. Денежные значения — строки; список оборачивается в `count`, `next`, `previous`, `results`, как каталог. ID и дата примера условные.

Для согласия исполнитель отправляет `POST /api/v1/orders/<id>/accept/` с `{}`. Ответ имеет тот же формат, но `status: "awaiting_payment"` и заполненное `accepted_at` в UTC. Заказчик не может принять заказ за исполнителя (`403`); посторонний получает `404`. Передача дополнительных полей в согласии — `400`. Изменившееся или скрывшееся после оформления объявление не мешает исполнителю согласиться с сохранёнными условиями заказа.

| Состояние | Значение |
|---|---|
| `pending_acceptance` | Заказ оформлен, исполнитель ещё не согласился |
| `awaiting_payment` | Исполнитель согласился, заказ ожидает оплаты |
| `cancelled` | Заказчик отменил неоплаченный заказ |
| `declined` | Исполнитель отказался до согласия |

Для отмены заказчик отправляет `POST /api/v1/orders/<id>/cancel/` с `{}`. Допустимые исходные состояния — `pending_acceptance` и `awaiting_payment`. Для отказа исполнитель отправляет `POST /api/v1/orders/<id>/decline/` с `{}`; допустимо только `pending_acceptance`. Участник другой роли получает `403`, посторонний — `404`. Отказ после согласия — `409`.

Ответы отмены и отказа имеют полный формат заказа. Поле `closed_at` содержит время действия в UTC, `closed_by` — объект `{"id":8,"name":"Заказчик"}` соответствующего участника. Оба поля равны `null`, пока заказ открыт; они добавлены в ответы создания, деталей, списка и согласия. При отмене после согласия `accepted_at` сохраняется. Состав услуги и все суммы не меняются.

Повтор того же действия его участником возвращает `200` и уже существующую запись без изменения автора или времени. Закрытый заказ остаётся доступен обоим участникам. Принять закрытый заказ или заменить отмену отказом и наоборот нельзя (`409`). Если повторить первоначальное оформление с тем же `request_key`, сервер вернёт этот закрытый заказ с `200`; новый заказ самопроизвольно не появится. Причина закрытия отдельным полем пока не поддерживается; любые дополнительные поля в POST-действиях — `400`, неподдерживаемый тип тела — `415`.

**Граница обоих денежных контрактов:** подтверждённой оплаты нет. Отмена неоплаченного заказа не выполняет возврат денег. Обработчика платежей и перехода к выполнению нет. `duration_days` не означает вычисленный дедлайн. Комиссия исполнителя, рейтинги, баланс и выплаты не рассчитываются. Выбранные дополнения поддерживает только v2 ниже. Передача результата, файлы заказа и завершение ждут правил оплаченного Live. Произвольное изменение заказа через PUT/PATCH/DELETE не поддерживается.

Сохранение заказа и проверка редакции выполняются в транзакции с блокировкой услуги. Согласие, отмена и отказ блокируют одну строку заказа: одновременные запросы соблюдают те же правила переходов. В базе дополнительно проверяются уникальность ключа у заказчика, разные участники, положительная цена, RUB, равенство итога цене с надбавкой и соответствие статуса истории согласия/закрытия, включая правильную роль автора закрытия.

Исходники: [модель](apps/api/orders/models.py), [операции](apps/api/orders/services.py), [сериализаторы](apps/api/orders/serializers.py), [маршруты](apps/api/orders/urls.py), [тесты оформления](apps/api/orders/tests.py), [тесты закрытия](apps/api/orders/test_cancellation.py).

## Модерация

Административная панель Backend: `http://127.0.0.1:8000/admin/`. Это стандартный служебный интерфейс Django, исходники Frontend друга он не затрагивает.

Для первого локального администратора владелец выполняет из `apps/api` интерактивную команду:

```bash
.venv/bin/python manage.py createsuperuser
```

Укажите собственный Telegram ID числом (личный ID, не ID бота) и отдельный пароль администратора. Пароль вводится в терминале без отображения; это не токен бота. Автоматическая служебная учётная запись или обход входа в этом этапе не создавались. В обычном Telegram-входе пароль от пользователя не запрашивается.

Модератору нужны `is_staff` и разрешение `catalog.moderate_service`. Суперпользователь получает все разрешения автоматически. Обычный пользователь и сотрудник только с правом просмотра не могут принять решение.

Порядок: открыть раздел услуг → отфильтровать «На модерации» → выбрать записи → действие «Одобрить и опубликовать» или «Отклонить» → просмотреть содержание на странице подтверждения → подтвердить решение. До последнего шага данные не меняются.

Подтверждение подписано сервером, действует 30 минут и связано с модератором, выбранным решением и номерами просмотренных редакций. Если автор успел изменить услугу, старое подтверждение её не публикует: нужно просмотреть новую редакцию. Решения применяются только к реальным услугам со статусом `pending`. Повторная отправка действия не меняет уже принятое решение. Кто принял решение, по какой записи и редакции, сохраняется в журнале Django. Содержание услуги в панели доступно только для чтения.

Существующие демоуслуги остаются опубликованными с `is_demo: true`; это демонстрация, а не реальные одобренные объявления. Новая пользовательская запись всегда реальная и ожидает решения.

## Расширения STUDLY 2

Машиночитаемая спецификация: [workspace.openapi.json](docs/workspace.openapi.json), 42 path. Воспроизводимый экспорт после изменения сериализаторов: из `apps/api` выполнить `.venv/bin/python operations/export_openapi.py`. Контрактные тесты проверяют наличие указанных маршрутов/методов и совпадение request-полей с действующими сериализаторами. Старый registration OpenAPI подключается ссылками, без копирования его схем.

Описывают новый локально проверенный код от 24 октября. Публикация и deployment ещё не выполнялись. Везде настоящая сессия, для записи свежий CSRF; чужие приватные объекты — 404, нет роли/permission — 403, неверный payload — 400, конфликт — 409. Ввод неизвестных полей в новых mutation DTO запрещён. Даты — ISO 8601 UTC, внутренние числовые ID не являются Telegram ID. UUID создаёт сервер либо клиент для ключа намерения, как указано ниже.

### Аккаунт кабинет и избранное

- `GET /api/v1/account/` → `{id,registration,capabilities}`. registration — существующий Reg без изменений. capabilities: `customer`, `performer`, `create_order`, `create_service`, `django_admin`, `moderate_services`, `moderate_performers`, все boolean. Возможность create_service означает создание черновика, а не публикацию.
- `GET /api/v1/cabinet/?role=customer|performer` → `{role,account_id,registration,capabilities,orders:{count,by_status,url},services,moderation,statistics,unavailable}`. services — объект count по статусам только для performer, для customer null. moderation — DTO ниже либо null. statistics содержит `{completed_orders:null,rating:null,review_count:null}`: этих источников пока нет, нули не подставляются. unavailable: execution/reviews/rating. Кабинет требует соответствующую текущую роль; доступ участника к истории заказов не исчезает из обычного orders API при переключении режима/ролей.
- `GET /api/v1/favorites/` → обычная Page<Service v1>, 20 на страницу, только свои видимые услуги. `PUT /api/v1/favorites/{service_id}/ {}` → 204, повтор и конкурентный PUT не создают дубль. DELETE с `{}` → 204, повтор/нет записи также 204. PUT отсутствующей/скрытой услуги — 404; скрытое избранное не выдаёт её содержание, но запись можно удалить. Чтение по чужому user_id не предусмотрено.

### Общие редакции и намерения

`Version = {"revision":1,"request_key":"UUID"}`. Ключ стабилен при повторе одного намерения. Новое намерение получает новый ключ. Пара ключа и operation-scoped actor уникальна; несовпадающий target/payload под тем же ключом даёт 409. Успешный повтор возвращает **сохранённый исходный response**, включая старый state/revision: после повторного ответа перечитать актуальный ресурс GET. После отклонённого/откаченного запроса receipt не сохраняется. Объект и receipt изменяются одной транзакцией. Решения проверяются по просмотренной редакции; второй конкурентный reviewer не подтверждает незаметно новую версию.

### Портфолио и профиль исполнителя

| Метод и путь v1 | Вход | Успешный ответ |
|---|---|---|
| GET `portfolio/` | page | Page<Example>, только своё |
| POST `portfolio/` | Version + title + url **либо** multipart Version/title/file | 201 `{example,moderation}`; repeat 200 с прежним телом |
| PATCH `portfolio/{uuid}/` | Version + title? + url?; хотя бы одно поле | 200 `{example,moderation}` |
| DELETE `portfolio/{uuid}/` | Version | 200 `{moderation}`, soft delete, повтор того же намерения возвращает прежний ответ |
| GET `portfolio/{uuid}/content/` | Сессия владельца либо staff+accounts.moderate_performer | Поток файла, no-store, attachment, nosniff, CSP sandbox |
| GET `performer/moderation/` | — | Moderation |
| POST `performer/moderation/` | Version | Moderation после подачи |
| POST `staff/performers/{user_id}/decision/` | Version + decision + reason? | Moderation после решения |

Example: `{id:UUID,title,kind:"link"|"file",url:string|null,content_url:string|null,content_type:string|null,size:integer,created_at}`. title до 200 символов, url до 2000, только HTTP(S) без credentials. Сервер URL не запрашивает. Для ссылки size=0. Для замены файла добавляется новая работа; PATCH файла может изменить название, но не превратить файл в URL. Удалённые работы не публикуются; физическое удаление и retention пока не включены, чтобы не потерять материалы связанной истории. Приватный файл владельца/модератора не становится публичным после одобрения. Чтение файла сотрудником журналируется.

Файлы: вход PNG/JPEG/WebP/PDF до 10 МиБ; расширению/MIME клиента не доверяем. Изображения: неанимированные, до 16 MP, декодируются и очищаются от EXIF/XMP, нормализуются в PNG до 1024×1024. PDF: strict parsing pypdf, без шифрования, до 100 страниц/20 000 посещений объектов; активные действия, JavaScript, формы, вложенные файлы и внешние PDF actions отвергаются. Выдача PDF только attachment. Это ограниченная проверка структуры, не антивирусная аттестация. Неверный контент/лимит — 400; файловое хранилище private MEDIA_ROOT, публичного alias нет. Будущий reverse proxy должен разрешать multipart чуть больше 10 МиБ; нынешний production лимит 6m этой задачей не менялся.

Moderation: `{user_id,revision,status,reason,submitted_at,ready_to_submit,missing_fields,approved}`. status: draft/pending/approved/rejected/changes. Readiness: роль performer, непустое имя/описание и хотя бы одна активная работа; **старый performer_ready по специализациям не заменяет approval**. Подача из draft/rejected/changes. decision: approved/rejected/changes, для rejected/changes обязательна непустая reason до 2000 символов. Нужны staff+accounts.moderate_performer; свои решения запрещены. История автора/времени/revision/reason — AuditEvent.

Изменение модерируемых данных, аватара, добавление/правка/удаление работы повышают profile revision. Approved/pending становится pending; услуги скрываются до нового одобрения. Изменение только роли customer, шага или сохранение тех же значений не снимает одобрение. Если обновлённый профиль неполон, он остаётся pending, но approve запрещён с missing_fields; владелец может исправить его, вновь увеличив revision. Опубликованный статус самой услуги не переписывается из-за изменения профиля: видимость зависит от текущего approval и действительности выбранных работ. Удалённые выбранные работы нужно исправить в услуге. Правка содержания опубликованной услуги отдельно требует её новой модерации.

### Услуги v2

Публичные GET `/api/v2/services/`, `services/{id}/` используют те же фильтры search/performer/ids/page, что v1. Service2 = все поля Service v1 + `{revision,category,extras}`. extra: `{id:UUID,title,price_amount:"300.00",extra_days:1}`. Неизвестные рейтинги/отзывы не добавляются. Категория пока строка до 100 символов, не ID утверждённого справочника.

Собственные GET/POST `/api/v2/my/services/`, GET/PATCH `/api/v2/my/services/{id}/`. POST/ PATCH: обязательные request_key и revision; для создания revision=0, для правки — текущая. Разрешены title≤200, description≤10000, category≤100, price_amount decimal≥0, duration_days 1–32767, included≤50 строк≤500, extras≤50 с разными UUID, portfolio_example_ids≤100 разных своих активных работ. Начальный неполный черновик сохраняется с пустыми значениями; пустой черновик не опубликован. currency фиксирована RUB; author/status/is_demo/reason клиентом не задаются.

Ответ private Service2 дополняется `{status,reason,portfolio_example_ids}`. POST нового — 201; repeat 200. PATCH — 200. Новый статус draft; правка draft/rejected/changes/pending возвращает draft. Правка published отправляет в pending по прежнему утверждённому правилу. GET списка — Page, 20 элементов; чужой ID — 404. Все новые записи и правки требуют performer.

`POST /api/v2/my/services/{id}/submit/` с Version проверяет owner, действующее profile approval, непустые title/description/category/included, положительную цену и выбранные свои работы. Возвращает pending с увеличенной revision. `POST /api/v1/staff/services/{id}/decision/` с Decision требует staff+catalog.moderate_service, запрещает собственную услугу, проверяет pending/revision/profile approval/полноту. approved → published, другие решения → rejected/changes; reason возвращается владельцу и сохраняется в аудите. Стандартная Django Admin также не может публиковать неполную услугу или обойти approval; её старый подтверждающий экран сохраняется.

### Сохранённый quote и заказ v2

`POST /api/v2/quotes/` с `{"service_id":42,"extra_ids":["UUID"]}` требует customer/session/CSRF. Не принимаются клиентские суммы, тариф, исполнитель или длительность. Возвращает 201:

```json
{
  "quote_id":"00000000-0000-4000-8000-000000000001",
  "service_id":42,"service_revision":3,"performer_id":7,
  "title":"Консультация","description":"Разбор темы","included":["Разбор"],
  "currency":"RUB","duration_days":4,"tariff_code":"buyer-5-v1",
  "base_price_amount":"1000.00",
  "selected_extras":[{"id":"00000000-0000-4000-8000-000000000002","title":"Отчёт","price_amount":"300.00","extra_days":1}],
  "extras_amount":"300.00","price_amount":"1300.00",
  "buyer_fee_percent":"5.00","buyer_fee_amount":"65.00","total_amount":"1365.00"
}
```

`GET /api/v2/quotes/{uuid}/` возвращает свой сохранённый расчёт. **price_amount v2 — subtotal, основная цена отдельно base_price_amount.** Комиссия Decimal/HALF_UP один раз от subtotal. Пример 1000.10+300.00 даёт fee 65.01 и total 1365.11. Срок = базовые дни + extra_days. Технический subtotal≤99999999.99 RUB и длительность≤32767 дней. Своя/Demo/бесплатная/невидимая услуга не заказывается. Quote сам не резервирует услугу и не подтверждает деньги, автоматический срок действия пока не задан; создание всегда перепроверяет условия.

`POST /api/v2/orders/ {"quote_id":"UUID","request_key":"UUID"}` → 201 Order2, повтор 200 с исходным receipt. Пока объект quote/услуги заблокирован от конкурирующего изменения, сервер сравнивает полный актуальный snapshot с показанным: revision, состав/название, выбранные extras/суммы/дни, tariff code/percent. Любое отличие требует нового quote, просмотра и нового намерения (409, ни заказ, ни receipt не сохраняются). Один quote создаёт максимум один заказ; другой request_key для уже использованного quote даёт 409. Чужой quote — 404. Ключ buyer/request_key общий между v1/v2: использовать его для другого контракта/quote нельзя.

Исторические v1 заказы сохраняют 3%, суммы и условия; seed-миграция добавляет версии buyer-3-v1 и buyer-5-v1, **без пересчёта старых денег**. Активная v2 версия задаётся `STUDLY_V2_BUYER_TARIFF` (default buyer-5-v1); менять процент существующей версии через приложение нельзя, создаётся новая версия. Неизвестная конфигурация — 503, а не возврат к 3%. Повтор успешного заказа возвращает старый snapshot даже при смене тарифа. Миграционный порядок: [BACKEND_ARCHITECTURE_DECISIONS.md](BACKEND_ARCHITECTURE_DECISIONS.md).

GET `/api/v2/orders/?role=customer|performer`, GET `orders/{id}/` → прежний Order v1 + `{revision,tariff_code,base_price_amount,selected_extras,quote_id,available_actions,payment_status:"unpaid"}`. POST `orders/{id}/accept|cancel|decline/` с Version — те же разрешённые неоплаченные переходы, с optimistic guard и receipt. Чтение — только buyer/performer, без принятия UI-роли на доверие. GET `/api/v1/orders/{id}/events/` → Page<{id,actor_id,action,revision,created_at}>. Для старых событий до появления журнала история не выдумывается. Ни один endpoint пользователя не выставляет paid/IN_PROGRESS/COMPLETED.

### Общий чат заказа и безопасность

Каждому заказу соответствует Conversation OneToOne. Новая запись создаётся в одной транзакции с заказом; локальная миграция готовит контексты старых заказов. Отдельный `POST /api/v1/discussions/ {service_id,request_key}` открывает обсуждение чужой реальной видимой услуги для customer. Для пары buyer/service повтор возвращает тот же discussion, первый запрос 201, повтор/существующий 200; демо/своя услуга запрещены. Такой контекст не перепривязывается: каждый следующий заказ получает собственный новый чат.

GET `/api/v1/conversations/` → Page<Conversation> (20). GET `conversations/{uuid}/` либо `orders/{id}/conversation/` → `{id,kind:"order"|"discussion",order_id:number|null,service_id,title,participant_ids,created_at}`. title — снимок названия контекста. Только фактические участники; staff/модератор без участия также получает 404.

GET/POST `conversations/{uuid}/messages/`. POST: `{client_message_id:UUID,text:string≤4000}`. sender/time/status не принимаются. 201 после сохранения в БД; повтор того же намерения — 200, другой текст/контекст с тем же actor-key — 409. Message: `{id,sequence,conversation_id,sender_id,client_message_id,text,status,categories,rules_version,warning,security_case_id,created_at}`. status stored означает сохранено и доступно адресату, **не прочитано человеком**; held означает удержано. GET — cursor pagination 50, `{next,previous,results}`, порядок по server sequence. При ручном release выделяется новый sequence, поэтому сообщение не пропускается за уже прочитанным курсором. ID сообщения остаётся прежним; клиент объединяет обновления по ID.

До доставки проверяются нормализованные текст/контакты/явные призывы уйти в мессенджер или оплатить напрямую. Правила `offplatform-2026-10-24-v1`: категории external_messenger/messenger_contact/contact_request/phone_contact/external_payment. Обычное учебное упоминание Telegram не является нарушением; есть узкие контекстные исключения и тесты. Это детерминированный ограниченный набор правил, не гарантия распознавания любой маскировки. Нет внешнего AI и автоматических санкций.

Held видит только sender с предупреждением, categories/rules_version/case ID; адресату текст/событие не выдаётся. GET/POST `security-cases/{id}/appeal/`: автор читает Case и отправляет Version + reason≤2000. Первая допустимая жалоба сохраняется, меняет case revision и журналируется. Staff имеет отдельный поток ниже; повтор одного намерения не создаёт второе обжалование. Вложения и read/delivery receipts, WebSocket/push пока не согласованы и не добавлены; polling GET допустим.

### Административные ресурсы

GET `/api/v1/staff/me/` требует staff и возвращает `{id,display_name,resources,unavailable}`. resources формируется из настоящих permissions:

| Ресурс GET `staff/{resource}/`, `staff/{resource}/{id}/` | Дополнительное permission | DTO и область |
|---|---|---|
| users | accounts.view_user | id/display_name/is_active/roles, без Telegram ID/email/password |
| performers | accounts.moderate_performer | Moderation + display_name/description/активные Example; detail по user_id |
| services | catalog.moderate_service | private Service2 |
| orders | orders.view_order | Order v1, без общего доступа к сообщениям |
| events | operations.view_auditevent | id/actor_id/operation/target/details/created_at, read-only |
| security-cases | conversations.review_security_case | Case metadata, без текста сообщения в списке |

Page 20, по возрастанию PK. search≤200 поддерживают users/performers/services/orders/events в разрешённых текстовых полях; status только для performers/services/orders и только из enum. Неподдерживаемый фильтр status/search — 400. Неутверждённых сортировок/всеполей поиска нет.

Специальный GET `staff/security-cases/{id}/?purpose=...` требует отдельное case permission и непустое рабочее основание≤500, журналирует просмотр и выдаёт только относящееся к этому случаю сообщение. POST того же пути: Version + decision release|keep + непустая reason≤2000. Собственный case участник не решает даже со staff-правом. Release делает сообщение видимым адресату, keep сохраняет удержание; повтор/конкурентный ответ контролируются receipt/revision. Сотрудник не получает универсальную ленту личной переписки.

Не созданы административные команды изменения оплат/возвратов/выплат, ролей staff, исходов споров, пользовательских отзывов или произвольного статуса заказа. Финансовые отчёты/аналитика не подменяются суммой неоплаченных заказов. Отдельный Frontend `/admin` не публикуется автоматически поверх Django `/admin/`.
