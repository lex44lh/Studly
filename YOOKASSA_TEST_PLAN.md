# STUDLY — первый этап проверки ЮKassa

16 октября 2026 года. План составлен перед реализацией. Владелец подтвердил ЮKassa как первый вариант для проверки тестовой «Безопасной сделки». Поддержка накопления заработка и условия подключения ещё не подтверждены.

## Задача этапа

Подготовить Backend к проверке существующего тестового платежа: получить его непосредственно из API ЮKassa и сравнить с сохранёнными условиями заказа STUDLY. Это первый технический шаг, а не готовый приём оплаты.

Публичных платёжных маршрутов, создания сделок, списаний, выплат, балансов и изменений статуса заказа на этом этапе нет. Комиссия исполнителя и автоматические статусы остаются вне реализации по прямому указанию владельца.

## Почему пока только проверка

ЮKassa требует при создании платежа передавать сумму исполнителю; разница с общей суммой должна покрывать эквайринговую комиссию. Согласованные 3% заказчика сами по себе не определяют это распределение. До создания платежей нужно утвердить финансовое правило и подтвердить тариф. [Приём оплаты в Безопасной сделке](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payments).

Для площадки без данных компании тестирование этого продукта запрашивается у менеджера. Тестовые объекты имеют `test=true`. [Тестирование Безопасной сделки](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/testing). Подготовленный текст обращения: [PAYMENT_PROVIDER_QUESTIONS.md](PAYMENT_PROVIDER_QUESTIONS.md).

## План изменений

1. Добавить отдельный серверный модуль `payments`, использующий уже установленный `requests`. Новые зависимости и миграции не нужны.
2. Добавить пустые настройки `YOOKASSA_TEST_SHOP_ID` и `YOOKASSA_TEST_SECRET_KEY` в пример окружения. Настоящий `.env` не переписывать; значения не выводить.
3. Реализовать только GET-запросы к фиксированному HTTPS API ЮKassa. Сначала проверить тестовый магазин через `/me`, затем получить конкретный платёж. Использовать Basic Auth, ограничение времени ожидания и запрет перенаправлений. Ошибки должны объяснять причину без ключей, полного ответа или карточных данных. [Формат API и аутентификация](https://yookassa.ru/developers/using-api/interaction-format), [справочник API](https://yookassa.ru/developers/api).
4. Проверять совпадение идентификаторов магазина, платежа, сделки и заказа, точной суммы в RUB, обязательного тестового режима и известного состояния платежа. `waiting_for_capture` не считать завершённым списанием. Это наши проверки согласованности; они не заменяют будущую сохранённую связь заказа и попытки оплаты.
5. Добавить служебную команду: без аргументов проверять только наличие локальных настроек; с `--connect` проверять тестовый магазин; с идентификаторами заказа, платежа и сделки выполнять сверку без изменения БД. Эта команда предназначена Backend-разработчику и недоступна посетителям сайта.
6. Проверить успешные ответы, ожидание списания, отказ, подменённые поля, настоящий вместо тестового объекта, ошибки сети/доступа/JSON, отсутствие утечки секретов и отсутствие изменений заказа. Все внешние ответы в локальных тестах подменяются; обращений к реальному магазину в тестах нет.

## Что потребуется после этого этапа

Доступ к тестовой площадке с поддержкой Безопасной сделки; согласованные доли и комиссии; правила отмены при незавершённой оплате, возврата и позднего списания. Только затем — отдельный план попыток оплаты, повторов запросов, уведомлений и перехода к выполнению заказа. Возврат браузера с платёжной страницы сам по себе не подтверждает оплату. Для будущих уведомлений нужно получать актуальное состояние объекта у провайдера: [уведомления ЮKassa](https://yookassa.ru/developers/using-api/webhooks).

Результат этого этапа следует оценивать отдельно: локальные тесты проверяют наш код, а реальная сверка требует выданных ЮKassa настроек и существующего тестового платежа. Вручную переданные идентификаторы в диагностической команде не являются основанием для автоматического зачисления средств.

## Результат

Пункты 1–6 выполнены. Все 154 теста Backend прошли на отдельной PostgreSQL, включая 24 новых теста клиента и команды. Проверки Django и согласованности миграций прошли. Проверка локальных настроек сообщила об отсутствии `YOOKASSA_TEST_SHOP_ID` и `YOOKASSA_TEST_SECRET_KEY`; реальной сверки у провайдера не было. Настоящий `.env`, Frontend и зависимости не изменялись. Инструкция: [YOOKASSA_SETUP.md](YOOKASSA_SETUP.md).
