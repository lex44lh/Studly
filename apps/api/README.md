# STUDLY Backend

Python 3.13, Django 5.2 LTS, Django REST Framework и PostgreSQL 17 для локальной разработки.

Реализованы общий пользователь STUDLY, вход из Telegram Mini App, вход на сайте через Telegram OIDC, серверная сессия, текущий профиль и выход. Оба входа находят один аккаунт по проверенному Telegram ID. Пользователь не разделяется на взаимоисключающие роли заказчика и исполнителя.

Добавлен публичный каталог PostgreSQL: поиск, пагинация, детальная услуга, профиль исполнителя и выборка избранных ID. Четыре демонстрационные услуги перенесены из прототипа. После уточнения разделения работы прежняя локальная интеграция Frontend убрана, установлен неизменённый Frontend друга из GitHub. Сейчас он не подключён к этому API. Актуальный запуск: [RUN_LOCAL.md](../../RUN_LOCAL.md).

Проверки входа используют вымышленные данные и локальные криптографические ключи. Бот [@studly_service_bot](https://t.me/studly_service_bot) создан и подключён к Backend. Для настоящего входа ещё нужен публичный HTTPS-адрес, а для сайта — также OIDC Client Secret и зарегистрированный callback. Клиентское подключение выполняет разработчик Frontend; настоящий вход пользователя пока не проверен. Текущее состояние: [TELEGRAM_SETUP.md](../../TELEGRAM_SETUP.md).

После подтверждения владельцем добавлены создание услуги, просмотр своих заявок и модерация через Django Admin. Новая услуга имеет статус `pending`, публично видны только `published`. Модератор отдельно получает право `catalog.moderate_service`; решения записываются в журнал Django. Существующие демоуслуги сохранены опубликованными с признаком `is_demo`. Чат и платежи ещё не реализованы.

Владелец может исправлять свои услуги через PATCH; после сохранения услуга снова `pending`. Подтверждение модератора связано с просмотренной редакцией: изменение содержания требует нового просмотра. Для локального наблюдения добавлены навигация `/api/v1/` и стандартный браузерный интерфейс DRF при `DEBUG=true`. Настройка PyCharm и Safari описана в [RUN_LOCAL.md](../../RUN_LOCAL.md).

Для первой версии выбран отдельный сайт с Telegram-входом и рублёвой оплатой. Добавлен `GET /api/v1/services/<id>/quote/`: текущая цена опубликованной услуги, надбавка заказчика 3% и итог, с точным округлением до копеек. Это предварительный расчёт без создания заказа и платежа. Накопление заработка, вывод по кнопке и автоматические статусы исполнителей пока требуют завершения правил и подтверждения условий провайдера: [PAYMENTS_PLAN.md](../../PAYMENTS_PLAN.md).

Первый этап заказов: оформление реальной платной опубликованной услуги другого пользователя, неизменяемый снимок условий с надбавкой 3%, личный список и детали, согласие исполнителя. Согласие переводит заказ в ожидание оплаты; начать работу или объявить его оплаченным через этот API пока нельзя. Защита от повторного запроса привязана к UUID и заказчику. Статусы исполнителей, рейтинг и их комиссия не реализованы. План: [ORDERS_PLAN.md](../../ORDERS_PLAN.md).

Добавлены отмена заказчиком до оплаты и отказ исполнителя до своего согласия. Закрытые заказы сохраняются с автором и временем действия; принять их повторно нельзя. Согласованное правило и проверки: [ORDERS_UNPAID_PLAN.md](../../ORDERS_UNPAID_PLAN.md).

После выбора ЮKassa для тестовой проверки добавлен модуль `payments`: только GET-запросы к провайдеру и команда `check_yookassa_test` для проверки магазина/сверки существующего тестового платежа. Сумма сверяется со снимком заказа; статусы заказа не меняются. Доступ к тестовой площадке ещё не настроен. Настройки и команды: [YOOKASSA_SETUP.md](../../YOOKASSA_SETUP.md). Публичных платёжных маршрутов нет.

Действующие форматы и последовательности запросов: [API_CONTRACT.md](../../API_CONTRACT.md). Подготовка постоянного HTTPS: [DEPLOYMENT.md](../../DEPLOYMENT.md).

Схема и границы решения: [TELEGRAM_AUTH.md](../../TELEGRAM_AUTH.md).
Общий план: [BACKEND_START.md](../../BACKEND_START.md).

Автоматические проверки настроены в [GitHub Actions](../../.github/workflows/backend.yml): отдельная PostgreSQL 17, Python 3.13, существующие зависимости, проверки Django/миграций и полный набор тестов. Ключи Telegram/ЮKassa не подключаются; сайт автоматически не размещается. Запуск и чтение результата: [BACKEND_CI_PLAN.md](../../BACKEND_CI_PLAN.md).

## Запуск

Нужны Python 3.13 и запущенный Docker Desktop с Compose. В текущей среде `python3` запускает Python 3.9; при создании окружения используйте `python3.13`.

Из корня проекта, только при первой настройке:

```bash
python3.13 -m venv apps/api/.venv
apps/api/.venv/bin/python -m pip install -r apps/api/requirements.txt
cp apps/api/.env.example apps/api/.env
```

Если `.venv` и `.env` уже существуют, сохраните их. В текущей рабочей папке они уже созданы; локальные секреты сгенерированы случайно. В новой копии проекта замените `POSTGRES_PASSWORD` и `DJANGO_SECRET_KEY` в `.env` собственными случайными значениями до запуска. Файл `.env` исключён из Git. Django читает его автоматически; существующие переменные окружения имеют приоритет.

Затем из корня проекта:

```bash
docker compose --env-file apps/api/.env up -d --wait db
apps/api/.venv/bin/python apps/api/manage.py migrate
apps/api/.venv/bin/python apps/api/manage.py seed_demo_catalog
apps/api/.venv/bin/python apps/api/manage.py check
apps/api/.venv/bin/python apps/api/manage.py test
npm run dev:api
```

Backend доступен на `http://127.0.0.1:8000`. Команда npm — только сокращение запуска Python; зависимости Frontend для неё не нужны.

Контейнер публикует PostgreSQL только на `127.0.0.1`, по умолчанию порт `5433`. Данные сохраняются в Docker volume между остановками. Остановка без удаления данных:

```bash
docker compose --env-file apps/api/.env stop db
```

При повторном запуске уже созданной БД изменение `POSTGRES_PASSWORD` в `.env` само по себе не меняет пароль внутри PostgreSQL. Не удаляйте volume для обычного перезапуска. Локальная конфигурация Docker не является конфигурацией публикации сервиса.

## Маршруты

| Запрос | Результат |
|---|---|
| `GET /api/v1/` | Ссылки на разделы API; при разработке также доступно HTML-представление |
| `GET /api/v1/health/` | Публичная проверка HTTP: `200 {"status":"ok"}`, без обращения к БД |
| `GET /api/v1/ready/` | Проверка PostgreSQL: `200 {"status":"ok"}` либо `503 {"status":"unavailable"}` |
| `GET /api/v1/services/` | Публичный каталог; `search`, `performer`, `ids`, `page` |
| `GET /api/v1/services/<id>/` | Услуга и краткие данные исполнителя |
| `GET /api/v1/services/<id>/quote/` | Предварительный расчёт в RUB: цена, надбавка заказчика 3% и итог; без записи и оплаты |
| `GET /api/v1/performers/<id>/` | Публичное имя и описание исполнителя с услугами |
| `GET, POST /api/v1/my/services/` | Личный список и создание заявки на модерацию; сессия, для POST также CSRF |
| `GET, PATCH /api/v1/my/services/<id>/` | Своя услуга; PATCH сохраняет исправления и возвращает `pending`; чужая — `404` |
| `GET, POST /api/v1/orders/` | Личный список и оформление со снимком условий и надбавкой 3%; POST требует CSRF |
| `GET /api/v1/orders/<id>/` | Детали только для заказчика или исполнителя |
| `POST /api/v1/orders/<id>/accept/` | Только исполнитель: согласие и ожидание оплаты; сессия и CSRF |
| `POST /api/v1/orders/<id>/cancel/` | Только заказчик: отмена до оплаты; сессия и CSRF |
| `POST /api/v1/orders/<id>/decline/` | Только исполнитель: отказ до своего согласия; сессия и CSRF |
| `GET /admin/` | Служебная панель; для решений нужны права сотрудника и модерации |
| `GET /api/v1/auth/options/` | Два признака готовности входа, без секретов |
| `GET /api/v1/auth/csrf/` | CSRF-cookie и JSON `{"csrf_token":"..."}` |
| `POST /api/v1/auth/telegram/mini-app/` | Проверка исходного `initData`, создание/поиск пользователя и сессия |
| `GET /api/v1/auth/telegram/start/` | Перенаправление в Telegram для входа на сайте |
| `GET /api/v1/auth/telegram/callback/` | Проверка ответа OIDC и сессия; пока возвращает JSON профиля |
| `GET /api/v1/auth/me/` | Профиль текущего пользователя; без входа `403` |
| `POST /api/v1/auth/logout/` | Завершение текущей сессии, `204`; без входа `403` |

Успешный вход и `/me/` возвращают:

```json
{"user":{"id":1,"display_name":"Имя пользователя","telegram_username":"username"}}
```

Пример показывает формат, а не существующий профиль или демонстрационную запись в базе. `id` — внутренний ID STUDLY. Секреты, OIDC subject, пароль и служебные права в ответ не включаются.

Для Mini App тело запроса — JSON `{"init_data":"исходная строка Telegram.WebApp.initData"}`. Самостоятельно пересобирать строку из `initDataUnsafe` нельзя. Backend проверяет подпись, свежесть и обязательные поля, затем определяет пользователя; отдельное поле `telegram_id` от клиента не используется.

До POST входа получите `/csrf/` и передайте выданный токен заголовком `X-CSRFToken`, сохранив cookie. Вход меняет CSRF-токен, поэтому перед следующим изменяющим запросом, например выходом, получите его заново. Cookie сессии имеет `HttpOnly`. Для браузерной интеграции предполагается общий origin интерфейса и API, но прокси в актуальном Frontend пока отсутствует. Локальные адреса порта 3000 сохранены в доверенных origin CSRF Backend; это само по себе не включает CORS или прокси. Произвольные междоменные запросы не разрешены.

Основные ошибки входа: `400` — некорректный формат запроса или недействительный/истёкший OIDC state; `401` — неподтверждённые данные Telegram; `403` — ошибка CSRF, недоступный аккаунт или закрытый маршрут без входа; `503` — отсутствующая настройка Telegram либо ошибка соединения с ним. У прикладных ошибок входа есть поле `code`; ошибки полей DRF возвращаются по именам полей.

## Настройка Telegram после создания бота

1. Создать бота через официальный [BotFather](https://t.me/BotFather). Токен сохранить локально в `TELEGRAM_BOT_TOKEN` в `apps/api/.env`.
2. Для Mini App указать в BotFather HTTPS-адрес вашего интерфейса и настроить запуск приложения. Сам URL и интерфейс в этом изменении не публиковались.
3. Для входа с сайта открыть настройки Login Widget в BotFather, зарегистрировать точный callback Backend, получить Client ID и Client Secret. Записать их в `TELEGRAM_OIDC_CLIENT_ID` и `TELEGRAM_OIDC_CLIENT_SECRET`, адрес возврата — в `TELEGRAM_OIDC_REDIRECT_URI`. Использовать тот же бот для обоих сценариев.
4. Для OIDC сохранить стандартный алгоритм подписи Telegram `RS256`; другие алгоритмы в этой реализации не принимаются. Запрашиваются только `openid profile`, без запроса телефона и разрешения писать пользователю.
5. Согласовать подключение с разработчиком Frontend, перезапустить Backend и проверить вход реальным аккаунтом в обоих сценариях, затем повторный вход и выход. Callback OIDC пока отдаёт JSON, последующий переход в интерфейс нужно завершить при настройке настоящего входа.

Для локальной конфигурации Django допускает callback `http://127.0.0.1/...` или `http://localhost/...` только при `DJANGO_DEBUG=true`. Это не гарантирует, что Telegram разрешит зарегистрировать такой адрес; для полной проверки используется зарегистрированный публичный HTTPS-адрес. Секреты не нужно отправлять в чат или включать в исходники.

Официальные протоколы: [проверка Mini App](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), [Telegram OIDC](https://core.telegram.org/bots/telegram-login). OIDC обрабатывает [клиент Authlib для Django](https://docs.authlib.org/en/latest/oauth2/client/web/django.html); отдельный UserInfo-запрос не выполняется.

## Проверки и устройство кода

```bash
apps/api/.venv/bin/python apps/api/manage.py check
apps/api/.venv/bin/python apps/api/manage.py makemigrations --check --dry-run
apps/api/.venv/bin/python apps/api/manage.py test --verbosity 2
apps/api/.venv/bin/python -m pip check
```

Тестам нужна PostgreSQL и право создавать тестовую БД. Пользователь локального контейнера это право имеет. Django создаёт отдельную `test_studly`, применяет к ней миграции и удаляет после тестов. Рабочие данные не очищаются. Тесты Telegram не требуют настоящего бота или доступа в интернет. `HealthEndpointTests` запрещают доступ к БД; тест готовности проверяет реальный запрос PostgreSQL. Другие сценарии проверяют пользователей, сессии, услуги, модерацию и перенос старых данных в тестовой PostgreSQL.

- `accounts/models.py` — пользователь и ограничения БД.
- `accounts/telegram.py` — проверка Mini App и настройка клиента OIDC.
- `accounts/services.py` — общий поиск/создание аккаунта без дубликатов.
- `accounts/views.py`, `accounts/urls.py` — HTTP-вход, профиль, CSRF и выход.
- `accounts/tests.py` — подписи, OIDC, сессии, конфликты аккаунтов и одновременный первый вход.
- `health/tests.py` — HTTP без БД, готовность PostgreSQL и безопасный ответ при сбое.
- `catalog/models.py`, `serializers.py`, `views.py` — каталог и публичные профили.
- `catalog/management/commands/seed_demo_catalog.py` — повторяемое заполнение демоданными без фиктивных Telegram ID.
- `catalog/tests.py` — чтение, фильтрация, поиск, пагинация, ограничения записи и демоданные.
- `catalog/admin.py` — служебные решения модератора и журналирование.
- `catalog/test_moderation.py` — создание, CSRF, изоляция заявок, права и решения модератора.
- `catalog/test_editing.py` — исправление, повторная подача, права владельца и браузерное представление API.
- `catalog/pricing.py`, `catalog/test_pricing.py` — надбавка заказчика 3%, точность сумм, видимость расчёта и защита от подмены цены.
- `catalog/test_migrations.py` — сохранение данных и безопасные начальные статусы.
- `orders/models.py`, `migrations/0001_initial.py` — заказ, снимок условий и ограничения PostgreSQL.
- `orders/services.py`, `serializers.py`, `views.py`, `urls.py` — оформление, доступ участников и согласие исполнителя.
- `payments/yookassa.py`, `payments/management/commands/check_yookassa_test.py` — только чтение тестовой ЮKassa и сверка с условиями заказа.
- `payments/tests.py` — ответы провайдера с подменой HTTP, ошибки, тестовый режим и сохранность заказа при диагностике.
- `orders/tests.py` — 24 проверки заказов, включая повторы и одновременные запросы.
- `orders/test_cancellation.py`, `orders/test_migrations.py` — 21 проверка отмены/отказа, истории, одновременных действий и сохранности старых заказов при миграции.
- `config/views.py`, `config/tests.py` — публичная навигация API без обращения к БД.

Текущий результат: все 154 теста Django прошли на отдельной PostgreSQL, включая 24 новые проверки клиента ЮKassa и диагностической команды с подменой внешнего HTTP. Сохраняются проверки условий и сумм, прав участников, CSRF, модерации, повторов и одновременных действий; отдельно проверено отсутствие изменений заказа при диагностике платежа. Миграции `orders.0001_initial` и `orders.0002_order_cancellation` применены к локальной БД; для модуля платежей миграции не нужны. Проверки Django и миграций прошли. Реального подключения ЮKassa пока нет.

Ранее настоящий HTTP-запрос к расчёту демоуслуги вернул `200`: 500 ₽ + 15 ₽ = 515 ₽, с признаком демоданных и запретом кэширования. Браузерная проверка подтвердила переход из навигации к каталогу и загрузку оформления DRF без ошибок JavaScript. Отдельная проверка настроек с `DEBUG=false` подтвердила отключение HTML-представления при сохранении JSON. Прежние 12 браузерных сценариев относились к убранной интеграции, а не к текущему Frontend друга. Вход реального пользователя и реальная оплата не подтверждены этими тестами.

В `requirements.in` перечислены прямые зависимости и допустимые ветки, в `requirements.txt` закреплены установленные версии. Для повторной установки используйте `requirements.txt`. Корневые команды npm сборки и lint не заменяют проверки Python.

## Границы текущего этапа

Публикация в интернете, маршрутизация публичных доменов и подключение актуального Frontend ещё не выполнялись. При `DJANGO_DEBUG=false` требуется собственный `DJANGO_SECRET_KEY`, а cookie передаются только через HTTPS. Реальные хосты задаются через `DJANGO_ALLOWED_HOSTS`, доверенные origin для CSRF — через `DJANGO_CSRF_TRUSTED_ORIGINS`, если они нужны выбранному размещению.

Пока используется серверная сессия Django с `SameSite=Lax`. Совместимость cookie со встроенным контекстом Telegram Web нужно проверить на выбранных доменах и клиентах. Поддержка всех клиентов Telegram ещё не подтверждена; отдельная передача токенов не добавлялась. Восстановление доступа при потере Telegram, удаление услуг, причина отклонения и самостоятельное снятие с публикации ещё не определены.

Рабочую БД этой задачей не мигрировали: тесты создавали отдельную PostgreSQL test БД.

Зависимости Backend включают `pypdf==6.21.2`. Новый `STUDLY_V2_BUYER_TARIFF=buyer-5-v1` выбирает v2 тариф; v1 сохраняет 3%. Политика настоящих платежей не включена. Экспорт нового OpenAPI после изменения сериализаторов: `.venv/bin/python operations/export_openapi.py` из этой папки. Не использовать production secrets и БД для тестов.
