# STUDLY — план первого запуска Backend на VPS

17 октября 2026 года. План составлен перед изменениями конфигурации запуска. Размещение разрешено владельцем ранее; Frontend остаётся в зоне ответственности другого разработчика.

## Что проверено

Независимый SSH-вход только по установленному ключу успешно выполнен. Получены сведения об Ubuntu 24.04.5, Python, памяти, диске и службах. Следующее соединение вновь завершилось `Connection refused`: устойчивость доступа ещё не подтверждена. Перезагрузка и изменение защиты нами не выполнялись.

На сервере уже работают Nginx на порту 80, Apache на `127.0.0.1:8080`, ispmanager, MySQL и почтовые службы. Установку второго веб-сервера и удаление служб панели план не предусматривает. PostgreSQL, Gunicorn, Docker и Node.js команда проверки в PATH не обнаружила; это не доказывает отсутствие файлов вне PATH.

Публичная A-запись `studly-help.ru` теперь существует, но указывает на `92.53.96.223`, а не на VPS `153.76.172.88`. HTTPS для домена пока не настроен.

## Шаги

1. Подготовить отдельные production-настройки Django: обязательный отключённый DEBUG, HTTPS, secure-cookie, доверие к заголовку HTTPS только от закрытого прокси, отдельные пути статики и приватных аватаров. Локальная разработка сохраняет прежние настройки.
2. Добавить отдельные зависимости серверного запуска Gunicorn, unit systemd и конфигурацию Nginx. Приложение работает от отдельного системного пользователя через Unix-сокет; PostgreSQL доступна только локально. `runserver` не используется.
3. После устойчивого SSH изучить подключения конфигурации Nginx и действующие сайты ispmanager. На проверенном VPS выбраны системные Python 3.12 и PostgreSQL 16 из Ubuntu; совместимость проверяет дополнительное задание CI, прежняя пара 3.13/17 сохраняется. Существующая MySQL не заменяется. Записать точные версии и пути в отчёт до запуска.
4. Разместить только проверенный Backend и файлы запуска, создать новые серверные секреты вне Git с ограниченными правами, применить миграции к новой БД и собрать административную статику. Локальные данные и `.env` автоматически не переносятся.
5. Проверить unit, конфигурацию Nginx, Django deploy-check и доступ к health/ready через сокет. До HTTPS публичный вход, регистрация и админка не открываются.
6. Владелец меняет A-запись основного домена на `153.76.172.88`. После проверки DNS настроить бесплатный сертификат и обновление. Домен HTTP обслуживает только проверку сертификата и перенаправление на HTTPS.
7. Проверить настоящий HTTPS, CSRF, ограничения доступа и перезапуск Backend. Согласованную версию Frontend размещать отдельно без наших изменений исходников. До готовности Frontend корень сайта возвращает явный HTTP 503.
8. Для настоящего Telegram-входа ещё нужны настройки владельца в BotFather и отдельный OIDC Client Secret. До сбора пользовательских данных нужны внешние резервные копии БД и аватаров с проверкой восстановления.

## Проверка изменений и возврат

- Автоматические тесты проверяют отказ запуска с DEBUG, перенаправление HTTP, распознавание HTTPS за доверенным прокси и secure/HttpOnly/SameSite для CSRF-cookie.
- Выполняются все серверные тесты, проверка миграций, зависимостей и отсутствие изменений `apps/web`/`package-lock.json`.
- Серверные конфигурации устанавливаются отдельными файлами; до reload выполняются `nginx -t` и `systemd-analyze verify`. При ошибке новая конфигурация не включается; существующие сайты панели не заменяются.
- Реальные платежи, кошельки, комиссии исполнителя и автоматические статусы остаются отложенными.

Основания: [Django 5.2 — deployment checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/), [Django — SECURE_PROXY_SSL_HEADER](https://docs.djangoproject.com/en/5.2/ref/settings/#secure-proxy-ssl-header), [Gunicorn — запуск с systemd и Nginx](https://gunicorn.org/deploy/).
