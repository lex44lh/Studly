# STUDLY — серверная регистрация

Дата: 16 октября 2026 года. План составлен до реализации. Backend: Django/DRF/PostgreSQL; Frontend не изменяется.

## Что подтверждено владельцем

- Вход через Telegram уже создаёт аккаунт; регистрация дополняет этот аккаунт, а не создаёт пароль или второй аккаунт.
- Роли `customer` и `performer` совместимы. Общая регистрация требует имени и хотя бы одной роли.
- Профиль исполнителя можно заполнить позже. Для готовности исполнителя нужны имя, роль исполнителя и хотя бы одна специализация; прочие поля необязательны.
- Справочник временно пустой: в актуальном Frontend списка нет, владелец предоставит утверждённые значения позже. Тестовые специализации в рабочую БД не добавляются.

## Исходное состояние

Есть Telegram Mini App и OIDC, серверная сессия, CSRF, `GET /auth/me/` с тремя полями. Расширенной регистрации нет. В ветке Frontend `codex/frontend-registration`, коммит `893a6fd`, клиент регистрации явно возвращает `unavailable`; формы ещё не вызывают Django.

Из форм взяты технические форматы: аватар PNG/JPEG/WebP до 5 МиБ; портфолио — необязательный текст со ссылками, курс обучения — необязательная строка. Список специализаций в формах отсутствует. Поля Frontend являются моделями интерфейса, а не согласованным форматом JSON.

## Порядок реализации

1. Добавить независимые роли, город и университет к существующему пользователю; отдельные модели прогресса регистрации, профиля исполнителя и справочника специализаций. Сохранить существующие аккаунты, услуги и заказы миграцией без автоматического назначения ролей и статусов.
2. Реализовать приватные `GET/PATCH /api/v1/registration/`: частичное атомарное сохранение ролей, общего профиля, профиля исполнителя и текущего шага. Данные привязаны только к пользователю из сессии. Сохранённые поля и шаг восстанавливаются после повторного входа с другого устройства; несохранённые изменения браузера серверу неизвестны.
3. Реализовать `POST /api/v1/registration/complete/`: проверить имя и роли, сохранить факт завершения. Повторное завершение идемпотентно. Статусы и недостающие поля вычислять сервером из сохранённых данных; пропуск профиля исполнителя не завершает его заполнение автоматически.
4. Добавить публичный `GET /api/v1/specializations/?search=...` с пагинацией и множественный выбор существующих UUID без продуктового ограничения количества. Администратор управляет справочником через Django. Не подменять утверждённый список примерами из тестов.
5. Реализовать приватные `GET/POST/DELETE /api/v1/registration/avatar/`. Загрузка — `multipart/form-data`, единственное поле `avatar`; проверка содержимого, размера и разрешённых форматов, пересохранение изображения без исходных метаданных. Для декодирования добавить только Backend-зависимость Pillow. Хранить файлы отдельно от исходников и Git, читать через закрытый маршрут с сессией. Файлы портфолио в этой версии не загружаются.
6. Сохранить формат существующих ответов входа и `/auth/me/`. Имя из Telegram использовать до явного изменения пользователем; повторный вход не должен затирать отредактированное имя. Зафиксировать правила действующей сессии и CSRF; описать единый origin и проксирование для разработчика Frontend, не менять конфигурацию Next.js.
7. Подготовить актуальный контракт и отдельный OpenAPI-файл регистрации для согласования с другом. Проверить поля, неизвестные входные данные, права/CSRF, восстановление, атомарность, файлы, миграцию и совместимость прежнего API. Выполнить весь серверный набор тестов.

## Границы

Флаг готовности описывает заполненность профиля. Существующие правила подачи и модерации услуг не меняются в рамках регистрации; применение этого требования к созданию услуг, уже опубликованным объявлениям и последующему снятию роли нужно согласовать отдельно. Изменение ролей не удаляет услуги, заказы или сохранённый профиль исполнителя и не выдаёт служебных прав Django.

Продвижение автоматических статусов, рейтинга, комиссий исполнителя, платёжных операций и реальное подключение ЮKassa остаются отложенными. Публичный HTTPS, реальные настройки OIDC и подключение браузерных форм — отдельные шаги. Реальный вход пользователя нельзя считать проверенным только по серверным тестам.

## Результат реализации

Пункты 1–7 выполнены на сервере. Контракт для согласования и подключения: [REGISTRATION_API.md](REGISTRATION_API.md), [OpenAPI](docs/registration.openapi.json). Единственная новая зависимость — Pillow 12.3.0, только Backend.

Прошли все 187 тестов, включая 33 новые проверки. Подтверждены сессия/CSRF и недоверенный origin, две роли, приватность, сохранение в новой сессии, частичные одновременные изменения, завершение/пропуск, выбор 205 специализаций, валидация изображений и сохранность прежнего аватара при ошибке, соответствие полей/маршрутов OpenAPI, миграция старых пользователей. Проверки Django, полноты миграций, зависимостей и diff прошли. Миграция применена локально; настоящий `/ready/` вернул 200, приватная регистрация без входа — 403, справочник — 200 с пустым списком. Frontend и его lock-файл не изменены.

Настоящие Telegram-вход и обмен форм с Django не проверены. Для них остаются настройки OIDC/HTTPS, подключение Next.js-прокси и адаптера со стороны друга. Формат регистрации реализован и передаётся ему для согласования; сам факт появления спецификации не означает, что клиент уже подключён.
