# STUDLY — автоматические проверки Backend

16 октября 2026 года. План составлен перед реализацией. Получение доступа ЮKassa отложено владельцем; продолжаем технический этап, не зависящий от платёжного кабинета и сервера STUDLY.

## Зачем это нужно

Сейчас Backend имеет 154 теста, которые запускались локально. При совместной работе важно проверять изменения также в чистом окружении, где нет нашей `.venv`, локального `.env` и уже подготовленной базы. GitHub Actions будет выполнять эти проверки после отправки серверных изменений и в pull request.

Этот этап не добавляет продуктовых правил или API. Frontend, его зависимости, конфигурация и исходники не изменяются. Развёртывание сайта не входит в задачу.

## План изменений

1. Добавить `.github/workflows/backend.yml`: запуск на `push` и `pull_request` при изменениях `apps/api`, самого workflow или `compose.yaml`. Предусмотреть ручной запуск после появления workflow в основной ветке.
2. Использовать Linux runner, Python 3.13 и отдельный временный PostgreSQL 17 с проверкой готовности. Настройки БД задаются непосредственно для задания; `.env` с компьютера не передаётся. Тестовый пароль этой временной БД не используется для рабочего размещения.
3. Установить существующие закреплённые зависимости из `apps/api/requirements.txt`, проверить их совместимость через `pip check`, выполнить проверки Django и отсутствие забытых миграций.
4. Применить миграции к пустой временной БД, затем выполнить полный набор тестов с `--noinput`. Тесты Django используют отдельную тестовую БД. Настоящие ключи Telegram и ЮKassa не нужны; секреты репозитория не подключаются.
5. Ограничить права workflow чтением исходников, время задания — 15 минут; отменять устаревший запуск этой же ветки/PR при новых изменениях. Автоматического merge, публикации сайта и изменения настройки защиты веток нет.
6. Проверить YAML доступным локальным парсером, выполнить серверные проверки на чистой копии Backend без `.env`, проверить отсутствие изменений Frontend и опубликовать workflow в `codex/backend`. Отдельно зафиксировать результат реального запуска GitHub, если он доступен: локальный проход не заменяет подтверждение CI.

## Официальные инструкции

- [Python в GitHub Actions](https://docs.github.com/en/actions/tutorials/build-and-test-code/python) — установка Python, зависимостей и выполнение тестов.
- [PostgreSQL как service container](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers) — отдельная БД и проверка готовности для Linux runner.
- [actions/checkout](https://github.com/actions/checkout), [actions/setup-python](https://github.com/actions/setup-python) — используемые официальные actions.

Точка возврата к оплате записана в начале [BACKEND_NEXT.md](BACKEND_NEXT.md). Инструкция тестовой площадки остаётся в [YOOKASSA_SETUP.md](YOOKASSA_SETUP.md).

## Как пользоваться

Workflow называется **Backend checks**. Файл: [backend.yml](.github/workflows/backend.yml). После публикации серверного изменения открыть [Actions репозитория](https://github.com/lex44lh/Studly/actions), выбрать запуск с нужной веткой и коммитом, затем задание **Python 3.13 / PostgreSQL 17**.

Зелёная отметка означает, что все шаги задания прошли. При красной отметке открыть неуспешный шаг: ошибка установки зависимостей, миграций и падение теста — разные причины. В шаге тестов выводятся имена сценариев и общий результат Django. Проверять нужно запуск нужного коммита; прежний зелёный запуск не подтверждает более новые изменения.

Изменения только `apps/web` и обычной документации не запускают серверную проверку. Для ручного запуска предусмотрен `workflow_dispatch`; кнопка **Run workflow** появится после попадания файла workflow в основную ветку `main`. Ветка `main` этим этапом не изменяется. [Условие ручного запуска в GitHub](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).

Сервер STUDLY, домен, данные владельца бота и ключи провайдеров для этих проверок не нужны. Настройка не делает успешный тест обязательным условием merge: защита веток — отдельная настройка GitHub и здесь не меняется. Также эти тесты не подтверждают подключение страниц Frontend или настоящую оплату.

## Локальная проверка перед публикацией

YAML разобран доступным системным парсером. Создана отдельная временная PostgreSQL 17 и копия Backend без `.env`, `.venv` и кэша. В копии использован уже установленный Python 3.13 с закреплёнными пакетами, а не заново установленные зависимости GitHub runner. Настройки соответствовали заданию CI; локальный порт временной БД отличался от порта runner.

Успешно выполнены `pip check`, `manage.py check`, `makemigrations --check --dry-run`, применение всех миграций к пустой БД и все 154 теста с `--noinput`. Временный контейнер остановлен; рабочая PostgreSQL STUDLY и её данные не менялись. Новые локальные зависимости не устанавливались, исходники Backend и Frontend в этом этапе не изменялись.

Это подтверждает команды Backend на текущем компьютере. Доступность actions, установка пакетов на Linux и результат выполнения самого workflow проверяются отдельно после push на странице GitHub Actions.
