## Как наблюдать за разработкой

Для просмотра используем Safari — по выбору владельца. PyCharm установлен, в нём открыта папка Backend `apps/api`.

| Что открыть в Safari | Что видно |
|---|---|
| [Сайт](http://127.0.0.1:3000/) | Текущий интерфейс друга с его демонстрационными данными |
| [Навигация Backend](http://127.0.0.1:8000/api/v1/) | Ссылки на разделы API, проверки сервера и текущую сессию |
| [Каталог Backend](http://127.0.0.1:8000/api/v1/services/) | Настоящий ответ из PostgreSQL в стандартном интерфейсе DRF |
| [Расчёт суммы заказчика](http://127.0.0.1:8000/api/v1/services/1/quote/) | Для существующей демоуслуги №1: 500 ₽ + надбавка 15 ₽ = 515 ₽; это расчёт без оплаты |
| [Личные заказы](http://127.0.0.1:8000/api/v1/orders/) | Только после входа; без него ожидается `403`. Новые заказы сохраняются на Backend, к интерфейсу друга пока не подключены |
| [Модерация](http://127.0.0.1:8000/admin/) | Панель Django; требует учётной записи сотрудника |

В PyCharm выберите существующий Python-интерпретатор `/Users/viktorkovarov/Downloads/Studly-main/apps/api/.venv/bin/python`, если IDE не нашла его автоматически: Settings → Python → Interpreter → Add Local Interpreter → выбрать существующее окружение. Новое окружение создавать не нужно. [Документация PyCharm](https://www.jetbrains.com/help/pycharm/configuring-python-interpreter.html).

Backend запускается командой `npm run dev:api` из корня проекта. Если терминал PyCharm открыт уже в `apps/api`, используйте `.venv/bin/python manage.py runserver 127.0.0.1:8000`. Выберите один способ запуска; второй экземпляр на том же порту не нужен. Сейчас сервер уже запущен.

При сохранении Python-файла Django автоматически перезапускает сервер. После этого обновите нужную страницу в Safari сочетанием `⌘R` или кнопкой GET в интерфейсе DRF. Это обновление ответа по запросу, автоматическая отправка новых данных в браузер не добавлена. В терминале видны запросы и их статусы: `200` — успешный ответ, `400` — ошибка входных данных, `403` — закрытый доступ или CSRF, `404` — запись не найдена либо скрыта. [Автоматическая перезагрузка Django](https://docs.djangoproject.com/en/5.2/ref/django-admin/#runserver).

Стандартный интерфейс API включён только при `DJANGO_DEBUG=true`; для JSON-запросов формат не изменился. Это служебный инструмент Backend из уже установленного DRF, не изменение Frontend. [Browsable API](https://www.django-rest-framework.org/api-guide/renderers/#browsableapirenderer).

Новые функции Backend пока проверяются через API и тесты. На сайте друга они появятся после подключения его страниц к согласованным маршрутам. Для настоящего Telegram-входа всё ещё нужны публичный HTTPS и настройки Telegram.

## Backend

В этой рабочей папке Python-окружение и приватный `apps/api/.env` уже созданы. Не заменяйте существующий `.env` примером.

Из корня проекта при работающем Docker Desktop:

```bash
docker compose --env-file apps/api/.env up -d --wait db
apps/api/.venv/bin/python apps/api/manage.py migrate
apps/api/.venv/bin/python apps/api/manage.py seed_demo_catalog
npm run dev:api
```

Проверка сервера: [health](http://127.0.0.1:8000/api/v1/health/). Проверка подключения PostgreSQL: [ready](http://127.0.0.1:8000/api/v1/ready/).
Данные каталога: [services](http://127.0.0.1:8000/api/v1/services/).

Команда заполнения добавляет четыре демонстрационные услуги и не дублирует их при повторном запуске. Telegram ID демонстрационным исполнителям не назначаются, вход для них отключён.

Проверки:

```bash
apps/api/.venv/bin/python apps/api/manage.py test
apps/api/.venv/bin/python apps/api/manage.py makemigrations --check
```

После первого этапа заказов все 109 тестов Backend прошли на отдельной тестовой PostgreSQL, включая 24 новых проверки заказов. Применена миграция `orders.0001_initial`; рабочие данные каталога, секреты и окружение сохранены. Существующий расчёт демоуслуги №1: 500 ₽ + 15 ₽ = 515 ₽.

Личные заказы: [orders](http://127.0.0.1:8000/api/v1/orders/). Без входа ожидается `403` — это проверка доступа, а не поломка сервера. На рабочей базе демонстрационные заказы не создавались. Демоуслугу оформить нельзя; для ручной проверки нужны два действительных аккаунта и реальная опубликованная услуга. Настоящий Telegram-вход ещё требует внешней настройки. В автоматических тестах создание и согласие проверены на временных пользователях отдельной тестовой БД; эти данные после проверки удаляются.

В Safari можно открыть [навигацию API](http://127.0.0.1:8000/api/v1/), каталог и предварительный расчёт. После настройки входа здесь же доступны личный список, детали и POST согласия исполнителя. Форматы и последовательность запросов описаны в [API_CONTRACT.md](API_CONTRACT.md). Согласованный объём первого этапа: [ORDERS_PLAN.md](ORDERS_PLAN.md). После согласия заказ ждёт оплаты; работа, баланс и выплаты ещё не доступны.

Панель модератора: [Django Admin](http://127.0.0.1:8000/admin/). Учётная запись администратора автоматически не создавалась. Первую создаёт владелец командой `apps/api/.venv/bin/python apps/api/manage.py createsuperuser`, указывая свой личный Telegram ID и отдельный пароль. Правила модерации и форматы запросов описаны в [API_CONTRACT.md](API_CONTRACT.md). Новые пользовательские услуги скрыты до одобрения.

Подробности: [README Backend](apps/api/README.md), [состояние Telegram](TELEGRAM_SETUP.md), [постоянный HTTPS](DEPLOYMENT.md).

## Frontend друга: просмотр и диагностика без изменений

В текущем окружении зависимости уже есть. Если они отсутствуют в новой копии, установка по lock-файлу выполняется из корня:

Проверка и запуск собранной версии:

```bash
npm run lint -w apps/web
npm run build -w apps/web
npm run start -w apps/web -- --hostname 127.0.0.1 --port 3000
```

Открыть [Frontend](http://127.0.0.1:3000). Этот интерфейс показывает данные браузерного прототипа; он пока не читает PostgreSQL через наш API.

Исходный скрипт друга для разработки — `npm run dev:web`. Он сохранён без изменений. Скрипт сборки из GitHub уже использует Webpack.

Результат проверки: lint без ошибок, два предупреждения об изображениях; сборка и TypeScript проходят. Подтверждённые функциональные замечания и шаги воспроизведения находятся в [FRONTEND_ISSUES.md](FRONTEND_ISSUES.md).

## Git и разделение работы

Репозиторий: [lex44lh/Studly](https://github.com/lex44lh/Studly). Backend, миграции, тесты, пример настроек и Markdown-документы версионируются в ветке `codex/backend`, созданной от `main`. Публикация исходников в Git не запускает приложение в интернете и не настраивает Telegram или оплату.

Для новой локальной копии:

```bash
git clone --branch codex/backend https://github.com/lex44lh/Studly.git
```

Разработчику с собственной рабочей копией сначала следует сохранить свои изменения; не сбрасывать их ради переключения ветки. Для знакомства с API достаточно открыть [API_CONTRACT.md](https://github.com/lex44lh/Studly/blob/codex/backend/API_CONTRACT.md) на GitHub. Перед переносом Backend в основную ветку нужно учесть текущую работу Frontend.

Файлы `apps/web` и корневой `package-lock.json` совпадают с полученным коммитом. В корневом `package.json` сохранена только наша команда запуска Python Backend; это не изменение Frontend.

Резервная копия прежнего состояния без секретов — `local-backups/before-github-sync-20261015-160320/source-before-sync.tar.gz`. Мои добавленные файлы интеграции убраны из `apps/web` в ту же резервную папку. Бэкапы, окружение и секреты исключены из Git.

Предыдущие 12 браузерных сценариев относились к убранной интеграции и не считаются подтверждением интеграции актуального Frontend с Backend. Планы и снимки того состояния сохраняются как история, а не как описание текущего продукта.
