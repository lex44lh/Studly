# STUDLY — возврат на сайт после входа Telegram

16 октября 2026 года. План составлен до реализации. Продолжение согласованного входа на отдельном сайте; Backend без изменений Frontend, платёжных правил и внешних настроек.

## Исходное состояние

`GET /api/v1/auth/telegram/start/` начинает OIDC Authorization Code Flow с PKCE, `state` и `nonce`. Callback проверяет ответ Telegram, создаёт серверную сессию и возвращает JSON. Параметра возврата на страницу интерфейса нет. Новые формы регистрации находятся в ветке друга; `/register/roles` существует там, но не переносится в нашу рабочую копию.

## План

1. Добавить необязательный `next` в начало входа: корневой относительный путь сайта, например `/register/roles`. Без `next` сохранить прежний JSON-ответ callback. Адрес callback Telegram не менять и не подменять этим параметром.
2. Проверять путь до начала OAuth: запретить внешние/протокольные URL, двойную начальную косую черту, обратные слеши, управляющие символы, чрезмерную длину и неоднозначные кодированные варианты. Сохранить проверенный путь только в серверной сессии рядом с `state`. Параметр `next`, добавленный непосредственно к callback, игнорировать.
3. После успешной проверки Telegram и создания сессии выполнить `303` на сохранённый относительный путь. Не добавлять Telegram-код, токены, ID или данные пользователя в URL. При ошибке возвращать существующий JSON с кодом ошибки, без перехода на `next`. Сохранить проверку одноразовости и срока действия попытки входа.
4. Проверить полный сценарий с подменой HTTP Telegram: переход, cookie, сохранённый черновик, повторный callback, подмена адреса, ошибки Telegram и истечение state. Не добавлять публичный тестовый вход или тестовых пользователей в рабочую БД.
5. Обновить API-контракт и OpenAPI для друга. При сверке также исправить описание logout: реальный обработчик требует действующую сессию; без неё возвращает 403.

## Границы

Это подготовка серверного перехода. Настоящий вход остаётся непроверенным до появления HTTPS, зарегистрированного callback и Client Secret Telegram, а также общего origin с корректным прокси. Настройки бота/провайдера и Frontend не меняются. Требования к публикации услуг после регистрации, специализации и платежи не расширяются.

## Уточнение проверки — 17 октября

При продолжении проверок обнаружено: Django не сохраняет изменения сессии для ответа `503`. Поэтому удаление использованной попытки при сетевой ошибке Telegram не закреплялось в БД. Перед завершением этапа явно сохраняем расходование попытки в двух ветках `503` (недоступна конфигурация и ошибка HTTP Telegram), очищаем служебный state и проверяем невозможность повторного callback. Успешный ответ без `next` остаётся JSON, с `next` — `303`.

## Результат — 17 октября

Реализованы проверка и серверное сохранение `next`, переход `303` после подтверждённого входа и сохранение прежнего JSON без `next`. Некорректные и повторяющиеся параметры отклоняются до начала OAuth; callback не принимает новый адрес возврата из запроса. При `503` использованное состояние теперь явно сохраняется как израсходованное.

Локально прошли все 200 серверных тестов, включая 13 новых проверок по сравнению с предыдущим завершённым этапом (187). Проверены возврат, cookie, сохранение черновика, свежий CSRF после входа, подмена адреса, повторный/просроченный state, ошибки Telegram, исчезновение конфигурации и действующее правило logout. Проверки Django, незаписанных миграций и зависимостей прошли. Новых зависимостей и миграций в этом этапе нет.

Обновлены [REGISTRATION_API.md](REGISTRATION_API.md), [OpenAPI](docs/registration.openapi.json), [API_CONTRACT.md](API_CONTRACT.md) и инструкции Telegram. Frontend и его lock-файл не менялись. Настоящий Telegram и публичное HTTPS по-прежнему требуют внешней настройки; успешные тесты используют подмену Telegram и не подтверждают вход реального аккаунта.
