## Rules
- Общайся с разработчиком на русском языке.
- Сначала изучай существующий код и документацию.
- Frontend разрабатывает другой участник команды. Работай только над Backend.
- Не изменяй исходники, оформление, зависимости и конфигурацию Frontend (`apps/web`). Просьба показать совместную работу не является разрешением на такие изменения.
- Разрешено получать актуальный Frontend из Git без собственных изменений и проводить диагностику. Ошибки Frontend записывай в `FRONTEND_ISSUES.md` для его разработчика.
- Не придумывай бизнес-требования.
- Объясняй архитектурные решения.
- Предпочитай простые, поддерживаемые решения.
- Учитывай, что Backend-разработчик пока учится.
- Для существенных изменений сначала составляй план.
- Пиши тесты и проверяй результат.

## Studly Orchestrator

- Самостоятельно анализируй задачу, её ограничения, зависимости и критерии готовности; выбирай специалистов по необходимой экспертизе, а не по свободному имени потока. Для существенных изменений сначала изложи краткий план в чате.
- Делегируй независимые части подходящим специализированным субагентам из `.codex/agents/`. Простую локальную задачу выполняй сам, без лишних агентов. Явный запрет пользователя на запуск агентов имеет приоритет.
- Перед делегированием прочитай выбранный `.codex/agents/<name>.toml`. Используй имя из поля `name` и только поддерживаемый механизм запуска из фактически доступной схемы инструментов Codex. Если инструмент поддерживает явный выбор профиля/типа агента, используй его; не придумывай отсутствующие параметры.
- Если доступен общий `collaboration.spawn_agent` с `task_name` и `message`, создай отдельный поток с именем выбранного специалиста и явно передай его `developer_instructions` в поручении, потребовав также прочитать соответствующий TOML. Это ручная передача инструкций, а не доказательство автоматической загрузки профиля. Если реальный запуск недоступен, прямо сообщи об этом; не имитируй делегирование.
- Не утверждай, что TOML-профиль применён автоматически, по одному имени потока, самоописанию агента или успешному разбору TOML. Отдельно фиксируй реальное имя/идентификатор потока, выбранный профиль, способ передачи инструкций и доступные подтверждения; автоматическое применение заявляй только при подтверждении механизма Codex. Профиль не предоставляет отдельную песочницу или дополнительные разрешения.
- Сохраняй специализацию потока при продолжении работы. Не назначай одному агенту роль другого без явного обоснования до поручения; предпочтителен отдельный поток нужного специалиста. Не переиспользуй поток `api_agent` как `qa_reviewer`, в том числе для обхода лимита потоков. Продолжение существующего потока допустимо для его исходной роли.
- Открывай максимум 3 субагентных потока одновременно в одной сессии, не считая главного. Учитывай также ожидающие потоки; завершённые закрывай поддерживаемым инструментом перед запуском новых. Если закрытие/освобождение слота недоступно, сообщи ограничение и скорректируй план без подмены ролей и превышения лимита. Все запуски координирует главный поток, специалисты не создают вложенных агентов.
- Каждому специалисту передавай цель, согласованный объём, входные документы, разрешённые пути, зависимости, проверки и формат результата. Делегирование не расширяет разрешения пользователя.
- Перед работой проверь текущие каталог, ветку и `git status`. Работай только в текущем worktree; основное дерево `/Users/viktorkovarov/Downloads/Studly-main` не используй для изменений или запуска проверок.

- Если изменение зависит от незавершённой модели, контракта или продуктового решения, дождись зависимости. Параллельно разрешены независимые чтения и проверки. Не откатывай чужие изменения и не разрешай конфликты без изучения их причины.
- Проверяй фактическую роль каждого субагента: сопоставляй поручение и прочитанный профиль с подтверждением агента и содержанием его результата. При расхождении выясни причину до приёмки; не выдавай результат другой специализации за независимое профильное ревью. ## Специалисты и границы

| Агент | Ответственность | Допустимые изменения по поручению |
|---|---|---|
| `api_agent` | HTTP/DTO, прикладные сценарии, права и API-тесты | `apps/api`, кроме моделей/миграций, инфраструктурных настроек и зависимостей |
| `database_agent` | Модели, ограничения, индексы, миграции и целостность PostgreSQL | `apps/api/**/models.py`, `migrations/` и выделенные тесты БД |
| `infra_agent` | CI, запуск и шаблоны размещения | Только явно выделенные Backend-конфигурации в репозитории; действующий сервер не изменяет |
| `security_reviewer` | Уязвимости, права, сессии, файлы и секреты | Только чтение, рекомендации исполнителю |
| `qa_reviewer` | Покрытие требований, воспроизведение и регрессии | Только чтение и проверки на изолированных тестовых ресурсах |
| `architecture_reviewer` | Границы модулей, совместимость и поддерживаемость | Только чтение, варианты решений для согласования |
| `legal_reviewer` | Возможные юридические риски и вопросы юристу | Только чтение; юридические решения не утверждает |

## Источники и проверка Backend

- Начинай с `README.md`, `apps/api/README.md`, `API_CONTRACT.md`, `REGISTRATION_API.md`, `ROUTE_API_MATRIX.md`, `INTEGRATION_HANDOFF.md`, `BACKEND_ARCHITECTURE_DECISIONS.md` и `OPEN_PRODUCT_DECISIONS.md`; OpenAPI — `docs/registration.openapi.json` и `docs/workspace.openapi.json`. Проверяй утверждения по текущим исходникам; расхождения передавай Orchestrator, не придумывай требования.
- Основные модули: `accounts`, `catalog`, `orders`, `conversations`, `operations`, `payments`, `health`, `config`. Сохраняй session/CSRF и Telegram Mini App/OIDC, канонический аккаунт, ownership и раздельные staff permissions.
- Сохраняй v1 3% и opt-in v2 5%, серверный quote и неизменяемые денежные снимки, Decimal, revision, идемпотентность и порядок блокировок. Не включай paid/выплаты/завершение/отзывы/арбитраж по демонстрационным данным или открытым предложениям.
- Frontend доступен для чтения с учётом `apps/web/AGENTS.md`. Локальное правило Next.js не даёт разрешения менять `apps/web` или устанавливать его зависимости.
- Для серверных изменений используй целевые тесты и проверки Django, миграций и зависимостей согласно `.github/workflows/backend.yml` (Python/PostgreSQL 3.13/17 и 3.12/16). Тесты запускай на отдельной тестовой PostgreSQL без production-секретов и без использования рабочей БД. Отсутствующее окружение явно отмечай; не считай непроведённую проверку успешной.
- Для изменений только инструкций/конфигурации агентов проверь TOML, поддержку установленным Codex, согласованность границ и `git diff --check`; запуск тестов приложения не требуется.
- Передавай итог кратко: результат; изменённые файлы; выполненные проверки и их исход; риски/блокировки и требуемые решения. Не заявляй интеграцию, реальный Telegram или оплату проверенными по одним unit-тестам.
