## 1. Существующие услуги ведут на отсутствующие профили

Однако [таблица публичных профилей](https://github.com/lex44lh/Studly/blob/ccfde590b6e722d1eeb0694747e10afc7958acb1/apps/web/src/app/profile/%5Bid%5D/page.tsx#L10) содержит только `1`, `2`, `100` и `101`.

Пример воспроизведения:

1. Открыть `/service/3`, услугу «Помощь с Java».
2. Нажать имя «Алексей Смирнов».
3. Открывается `/profile/3` с сообщением «Исполнитель не найден».

Переход подтверждён в браузере. Ссылка формируется в [странице услуги, строка 145](https://github.com/lex44lh/Studly/blob/ccfde590b6e722d1eeb0694747e10afc7958acb1/apps/web/src/app/service/%5Bid%5D/page.tsx#L145); отсутствие профиля обрабатывается в [строке 96 страницы профиля](https://github.com/lex44lh/Studly/blob/ccfde590b6e722d1eeb0694747e10afc7958acb1/apps/web/src/app/profile/%5Bid%5D/page.tsx#L96).

Ожидаемый результат: исполнитель существующей услуги имеет доступный согласованный профиль. При исправлении стоит убрать рассогласование между общим каталогом и отдельными таблицами профилей/услуг на странице профиля. Новые имена, биографии и статистику не нужно придумывать ради заполнения.

Критерий проверки: переход к исполнителю работает для каждой услуги каталога, а отсутствующий ID по-прежнему показывает понятное сообщение.

## 2. Необработанный отказ localStorage ломает страницу чата

Приоритет: ошибка устойчивости при недоступном или переполненном хранилище браузера.

Чтение сообщений защищено `try/catch`, но [сохранение сообщений в ChatWindow, строка 168](https://github.com/lex44lh/Studly/blob/ccfde590b6e722d1eeb0694747e10afc7958acb1/apps/web/src/components/ChatWindow.tsx#L168) выполняется в эффекте без обработки исключения.

Проверка в отдельном браузерном контексте:

1. В браузере создан один демонстрационный чат.
2. Для записи `studly-chat-messages-*` смоделирован `QuotaExceededError` из `Storage.setItem`.
3. Открыт этот чат.
4. Зафиксировано необработанное исключение, страница заменена сообщением «This page couldn’t load».

Это проверка отказа хранилища, а не утверждение, что обычный чат падает при каждом открытии.

Ожидаемый результат: невозможность сохранить сообщения не обрушает страницу. Пользователь получает понятное сообщение о сохранении либо согласованное временное хранение в памяти. Состояние «сообщение сохранено» не должно показываться при неудачной записи.

Критерий проверки: открытие чата и отправка сообщения не приводят к падению при исключении из `localStorage.setItem`.

## Что относится к будущей интеграции, а не к перечисленным ошибкам

В текущем Frontend не найдены запросы `fetch` или `axios` к нашему Backend. Услуги читаются из [src/data/services.ts](https://github.com/lex44lh/Studly/blob/ccfde590b6e722d1eeb0694747e10afc7958acb1/apps/web/src/data/services.ts#L17), заказы и переписка сохраняются в браузере. Дополнительная оплата явно обозначена в коде как [MOCK PAYMENT](https://github.com/lex44lh/Studly/blob/ccfde590b6e722d1eeb0694747e10afc7958acb1/apps/web/src/app/orders/%5Bid%5D/additional-payment/page.tsx#L143); уведомления [статические](https://github.com/lex44lh/Studly/blob/ccfde590b6e722d1eeb0694747e10afc7958acb1/apps/web/src/app/notifications/page.tsx#L13); [личный профиль](https://github.com/lex44lh/Studly/blob/ccfde590b6e722d1eeb0694747e10afc7958acb1/apps/web/src/app/profile/page.tsx#L1) пока содержит только заголовок.

Это границы прототипа, а не подтверждение серверной оплаты, пользовательской авторизации или доставки сообщений.

Backend реализован отдельно на Python/Django/DRF/PostgreSQL. Уже доступны:

| Маршрут | Назначение |
|---|---|
| `GET /api/v1/services/` | Каталог; параметры `search`, `performer`, `ids`, `page` |
| `GET /api/v1/services/<id>/` | Услуга |
| `GET /api/v1/performers/<id>/` | Публичный исполнитель |
| `GET /api/v1/auth/options/` | Готовность входа |
| `GET /api/v1/auth/me/` | Текущая сессия, без входа `403` |

Список возвращает `{count, next, previous, results}`. У услуги сумма — `price_amount` десятичной строкой, валюта — `currency`, срок — `duration_days`, исполнитель — `performer: {id, name}`.

Перед подключением нужно согласовать:

- Получение данных API и маршрутизацию запросов: в [next.config.ts](https://github.com/lex44lh/Studly/blob/ccfde590b6e722d1eeb0694747e10afc7958acb1/apps/web/next.config.ts#L3) сейчас нет прокси API.
- ID, полученные из Backend: фиксированные ID браузерного прототипа не являются ID записей PostgreSQL. Четыре демонстрационные записи Backend не заменялись автоматически семнадцатью примерами Frontend.
- Серверные фильтры: текущий API поддерживает перечисленные параметры; остальные фильтры нового интерфейса требуют отдельного согласования.
- Вход Telegram и обработку загрузки/ошибок. Нужны HTTPS и настройки настоящего бота; клиентский код не должен содержать токен бота или Client Secret.
- Заказы, чат и платежи: Backend этих функций ещё не реализован; правила необходимо согласовать отдельно.

Исходники Frontend исправляет его разработчик. Работа Backend-разработчика ограничивается сервером, диагностикой и передачей контракта API.
