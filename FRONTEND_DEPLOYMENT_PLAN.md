## Порядок

1. Проверить инструкции, состав версии, lock-файл, клиент API и существующие службы VPS. Порт Next.js не публиковать в интернете.
2. Установить отдельный Node.js 24 LTS из официального архива с проверкой SHA-256. Создать отдельного системного пользователя `studly-web` и каталог релиза `/opt/studly-web/releases/<SHA>`; Backend и его окружение не заменять.
3. Получить зафиксированный коммит из GitHub, извлечь только root `package.json`, `package-lock.json` и `apps/web`. Выполнить `npm ci` из существующего lock-файла от непривилегированного пользователя. Сверить исходники и lock-файл до и после сборки; не исправлять Frontend.
4. Выполнить существующие lint, тесты и production-сборку. `NEXT_PUBLIC_STUDLY_DATA_MODE=api`, `DJANGO_API_ORIGIN=https://studly-help.ru`, `NEXT_TELEMETRY_DISABLED=1`. Nginx обслуживает `/api/` напрямую через Django; внутренний rewrite Next не используется для браузерного API.
5. При успешных проверках запустить `next start` через отдельный unit systemd на `127.0.0.1:3000`. Переключить только корневой location HTTPS-vhost на Next; сохранить Django `/api/`, `/admin/`, статику и приватность аватаров.
6. Проверить Nginx до reload, HTTPS-страницы, CSS/JS, ответы API, отсутствие публичного Node-порта, перезапуск процесса и работу каталога в браузере. Ошибки Frontend записывать в `FRONTEND_ISSUES.md`.
7. Зафиксировать версии, реальные проверки, ограничения и откат в документации. До реальных пользовательских данных отдельно настроить внешние резервные копии БД/аватаров и проверить восстановление; затем подключать Telegram и сквозную регистрацию.

## Откат

До переключения сохранить существующий HTTPS-vhost в закрытый серверный каталог. При ошибке проверки вернуть его, выполнить `nginx -t`, затем reload. Backend и база при публикации сайта не меняются. Старые релизы не удалять автоматически.
