Обновлено 24 октября 2026 года. Новые расширения пока в рабочем дереве `codex/backend` поверх `d7a5ffa`, без публикации/deployment. Контракт описывает Django; новая сквозная интеграция с принятым Frontend `5db64a2` не проверена. Frontend не изменялся. OpenAPI: [registration.openapi.json](docs/registration.openapi.json). Сценарии и статус: [ROUTE_API_MATRIX.md](ROUTE_API_MATRIX.md).

Для редактирования модерируемых данных добавлен необязательный верхнеуровневый `performer_revision` в PATCH: брать из `GET /api/v1/performer/moderation/`, устаревший даёт 409. Без него сохраняется совместимый PATCH с блокировкой пользователя; Integration следует передавать guard для защиты от перезаписи. Формат Reg-ответа и краткого auth/me не менялся. Изменение реальных полей одобренного/проверяемого профиля или аватара увеличивает revision, отправляет профиль в pending и скрывает его услуги; смена только customer-роли, шага или no-op не сбрасывает одобрение. Обычная завершённость и performer_ready сохраняют прежние критерии и **не являются moderation approval**.

## Вход и сессии

Пять маршрутов, перечисленных разработчиком Frontend, уже реализованы:

| Запрос | Назначение |
|---|---|
| `GET /api/v1/auth/options/` | Доступность настроенных способов входа |
| `GET /api/v1/auth/csrf/` | `200 {"csrf_token":"..."}` и CSRF cookie |
| `POST /api/v1/auth/telegram/mini-app/` | `{"init_data":"исходная строка Telegram.WebApp.initData"}`; проверка подписи и свежести, вход |
| `GET /api/v1/auth/me/` | `200 {"user":{"id":7,"display_name":"Имя","telegram_username":"username"}}`; без входа `403` |
| `POST /api/v1/auth/logout/` | Выход и удаление текущей серверной сессии, `204` |

Ответ успешного входа имеет тот же формат `{"user": ...}`, что и `/auth/me/`. Формат этих ответов сохранён, расширенный профиль возвращается отдельным маршрутом. Ошибочная подпись/срок Mini App — `401`; неподготовленная конфигурация Telegram — `503`. Токен бота и Client Secret никогда не нужны браузеру.

На отдельном сайте нельзя самостоятельно создавать Mini App `init_data`. Для сайта есть `GET /api/v1/auth/telegram/start/` → Telegram OIDC → `/api/v1/auth/telegram/callback/`. Ему нужны собственные зарегистрированные настройки OIDC и публичный HTTPS; Bot API token их не заменяет. Реальное подключение Telegram пока не проверено. Подробнее: [TELEGRAM_SETUP.md](TELEGRAM_SETUP.md).

Для возврата на страницу сайта Frontend открывает обычной навигацией, например, `/api/v1/auth/telegram/start/?next=%2Fregister%2Froles`. Backend проверяет и сохраняет `next` в серверной сессии. После успешного входа callback отвечает `303` с `Location: /register/roles` и пустым телом. Это путь страницы интерфейса, а не новый адрес OAuth callback. Страница должна существовать в размещённой версии Frontend; её выбор остаётся за разработчиком интерфейса.

Допускается один `next` длиной до 2048 символов: непустой путь от `/` на текущем origin, с необязательными query и fragment. Полные URL, `//`, обратные слеши, управляющие символы и неоднозначные кодированные варианты запрещены; неверный или повторяющийся параметр даёт `400 invalid_return_path` до перехода в Telegram. Без `next` callback сохраняет прежний ответ `200 {"user": ...}`. Параметр `next` непосредственно в callback игнорируется. Backend не добавляет Telegram-коды и токены в адрес страницы.

Ошибки callback остаются JSON без перенаправления. Использованная попытка одноразовая, включая ответ `503`: начать вход заново через `/start/`. После перехода на страницу получить свежий `/auth/csrf/`, проверить `/auth/me/` и загрузить `/registration/`. Черновик регистрации сохраняется. Logout требует действующую сессию и CSRF: первый успешный вызов — `204`, повторный без входа — `403`.

Сессия хранится в PostgreSQL, в браузере — cookie `sessionid`, `HttpOnly`, `SameSite=Lax`, host-only. Срок — 14 дней с последнего сохранения сессии, чтение API его не продлевает. Закрытие вкладки само по себе не завершает сессию. При повторном входе меняется CSRF-токен; logout отзывает текущую сессию. Другие устройства не отключаются автоматически. При `DEBUG=false` session/CSRF cookie имеют `Secure` и требуют HTTPS. Эти значения явно зафиксированы в [settings.py](apps/api/config/settings.py), без изменения прежней политики Django. Основание поведения сессий: [документация Django 5.2](https://docs.djangoproject.com/en/5.2/topics/http/sessions/).

Прогресс регистрации хранится отдельно от сессии: logout и истечение cookie его не стирают. Восстановление — после нового подтверждённого входа в тот же Telegram-аккаунт. До входа сервер не сохраняет анонимный черновик. Изменения, для которых PATCH не завершился успешно, сервером не подтверждены.

## Единый origin, cookies и CSRF

Для первого подключения используем один адрес, видимый браузеру: например, `http://localhost:3000` локально и один HTTPS-домен при размещении. Относительные `/api/v1/...` должны проксироваться к Django; публичный `/admin/` настраивается отдельно. Next.js-прокси на своей стороне добавляет разработчик Frontend. В этой Backend-задаче его конфигурация не менялась.

Прокси должен сохранять методы, multipart-тела, cookies, заголовок `X-CSRFToken`, ответы `Set-Cookie` и поток изображения. На границе размещения нужны согласованные `Host`/`Origin` и настройки доверенных origin Django. Добавление `CSRF_TRUSTED_ORIGINS` само по себе не включает CORS и не заменяет прокси. В проекте сейчас нет разрешения произвольных cross-origin запросов.

Последовательность браузера:

1. Получить `/auth/csrf/` с `credentials: "same-origin"`, сохранить `csrf_token` в памяти.
2. Выполнить вход с этим `X-CSRFToken` и cookie. Не логировать Telegram initData.
3. После успешного входа **снова** получить `/auth/csrf/`: вход обновляет CSRF.
4. Получить `/auth/me/` и `/registration/`.
5. Для всех PATCH/POST/DELETE передавать cookie и `X-CSRFToken`.

Cookie `csrftoken` тоже `HttpOnly`: читать её через `document.cookie` не нужно, используйте JSON из `/auth/csrf/`. Без сессии приватный API возвращает `403`; CSRF тоже может дать `403`, поэтому при ошибке сначала проверяется `/auth/me/`, затем обновляется CSRF. Ошибка не повод повторять запись без контроля её результата.

Не смешивать `localhost` и `127.0.0.1` в одной браузерной сессии. Для прямого просмотра Django можно работать на `http://127.0.0.1:8000`; это отдельный origin. Встраивание в Telegram Web может иметь ограничения сторонних cookie; оно не считается проверенным этим контрактом. Текущий согласованный первый сценарий — отдельный сайт.

## Получение регистрации

`GET /api/v1/registration/` — только текущий пользователь, `200`, `Cache-Control: no-store`. GET не создаёт записи прогресса. ID другого пользователя в URL или теле не принимается для выбора профиля.

```json
{
  "roles": ["customer", "performer"],
  "profile": {
    "display_name": "Алексей",
    "avatar_url": null,
    "university": "",
    "city": "",
    "about": ""
  },
  "performer": null,
  "progress": {
    "current_step": "profile",
    "performer_skipped": false,
    "updated_at": "2026-10-16T10:00:00+00:00"
  },
  "status": {
    "is_complete": false,
    "completed_at": null,
    "missing_fields": [],
    "performer_ready": false,
    "performer_missing_fields": ["performer.specialization_ids"]
  }
}
```

`performer: null` означает, что профиль исполнителя ещё не создавался. У первого GET шаг `roles`, `updated_at: null`; имя может быть предзаполнено проверенными данными Telegram. Пример выше иллюстрирует сохранённый промежуточный шаг, а не исходное состояние каждого аккаунта.

## Сохранение ролей и полей

`PATCH /api/v1/registration/`, JSON, сессия + CSRF. Можно сохранить один блок или несколько одним запросом:

```json
{
  "roles": ["customer", "performer"],
  "profile": {
    "display_name": "Алексей",
    "university": "Название университета",
    "city": "Москва",
    "about": "Общее описание пользователя"
  },
  "performer": {
    "description": "Описание исполнителя",
    "study_year": "2 курс",
    "portfolio": "https://example.org/work\nОписание работы",
    "specialization_ids": []
  },
  "progress": {
    "current_step": "performer",
    "performer_skipped": false
  }
}
```

Ответ `200` — целиком тот же объект, что у GET. Все переданные изменения сохраняются одной транзакцией; ошибка любого поля не сохраняет остальные. Блокировка аккаунта защищает независимые одновременные частичные изменения от потери. Для одновременного изменения одного поля действует последнее успешно сохранённое значение; при подключении форм следует сериализовать автосохранение, чтобы старый запрос не обогнал новый.

| Поле записи | Правило |
|---|---|
| `roles` | Массив `customer`, `performer`, без повторов; заменяет выбор целиком. `[]` допустим для черновика |
| `profile.display_name` | Строка до 255 символов. Непустое имя обязательно для завершения, пустое допускается в черновике |
| `profile.university`, `profile.city` | Необязательные строки до 255 символов |
| `profile.about` | Необязательная строка до 10 000 символов |
| `performer.description`, `performer.portfolio` | Необязательные строки до 10 000 символов |
| `performer.study_year` | Необязательная строка до 100 символов; числовая система курсов не навязывается |
| `performer.specialization_ids` | Массив существующих UUID, без повторов; заменяет выбранный набор целиком. `[]` очищает его |
| `progress.current_step` | `roles`, `profile` или `performer`; сохранённое положение формы, не доказательство заполненности |
| `progress.performer_skipped` | Boolean: пользователь выбрал «заполнить позже»; не даёт готовность исполнителя |

Неуказанное поле сохраняет прежнее значение. Строки обрезаются по краям; очистка — `""`, а не `null`. Пустой PATCH и неизвестные поля — `400`. `avatar_url`, серверные флаги, Telegram ID, права, `completed_at`, чужой ID и комиссии записывать нельзя. Серверные статусы нельзя заменить значениями от клиента.

Передача блока `performer` создаёт профиль при его отсутствии или обновляет существующий. Выключение роли исполнителя не удаляет этот профиль и не меняет историю заказов/услуг. Роли продукта не связаны с `is_staff` или Django permissions.

Общий `about` и `performer.description` — разные поля, соответствующие двум формам Frontend. Прежний публичный `/performers/<id>/` по-прежнему возвращает общий `about`; новые поля и аватар там автоматически не публикуются. Общий `about` уже мог быть публичным для исполнителя с опубликованной услугой. Остальные новые поля доступны через приватный маршрут.

После явного изменения `display_name` повторный вход Telegram не перезаписывает его. До редактирования имя продолжает обновляться из проверенного Telegram-профиля.

## Завершение и готовность

Сначала сохранить поля через PATCH, затем `POST /api/v1/registration/complete/` с `{}`. Обязательны непустое имя и хотя бы одна роль. Исполнитель может завершить общую регистрацию без специализаций, аватара и заполненного профиля исполнителя.

Успех `200`: объект регистрации с `status.is_complete: true` и временем `completed_at`. Повторный POST не меняет время завершения. Если позже очистить обязательное имя или все роли, завершённость и время сбрасываются, после заполнения нужно повторить complete.

Ошибка `400`, например:

```json
{"code":"registration_incomplete","missing_fields":["profile.display_name","roles"]}
```

В GET `missing_fields` перечисляет незаполненные обязательные поля. Если список пустой, а `is_complete` ещё false — поля готовы, осталось вызвать complete. `completed_at` задаёт только Backend.

`performer_ready` показывает **заполненность**: есть роль `performer`, непустое имя и хотя бы одна специализация. Он может стать true до вызова complete. Необязательные поля на него не влияют; `performer_skipped` не подменяет проверку реальных данных. `performer_missing_fields` содержит необходимые для исправления ключи.

Этот флаг не одобряет услугу и не выдаёт служебных прав. В этой задаче он не меняет существующий API подачи/модерации услуг. Применение требования к новым/старым услугам и последствия последующего снятия роли нужно согласовать отдельно. Модерация услуг остаётся обязательной.

## Справочник специализаций

`GET /api/v1/specializations/?search=матем&page=1` доступен без входа. Поиск по вхождению строки в название, без учёта регистра. Порядок — название, UUID. Размер страницы — 100; это **пагинация справочника**, а не ограничение выбранных специализаций.

```json
{"count":0,"next":null,"previous":null,"results":[]}
```

Когда список утверждён и внесён, элемент: `{"id":"UUID","title":"Название"}`. В сохранённом профиле возвращается массив таких объектов `performer.specializations`; для записи используется только `specialization_ids`. Неизвестный UUID, неверный формат или дубли — `400`. Продуктового ограничения количества выбранных специализаций нет; действует общий технический лимит размера HTTP-запроса. Проверен выбор 205 элементов в тестовой БД.

Если прокси выдаёт `next` с внутренним адресом Django, Frontend следует использовать путь и параметры на своём origin, а конфигурацию Host на прокси исправить. Не отправлять cookie на произвольный адрес из данных.

## Аватар и портфолио

`POST /api/v1/registration/avatar/`: сессия + CSRF, `multipart/form-data`, ровно один файл в поле `avatar`. Для `fetch(FormData)` браузер сам выставляет `Content-Type` с boundary — вручную его не указывать.

PNG/JPEG/WebP, до 5 МиБ (5 242 880 байт), один кадр, не более 16 000 000 пикселей. Проверяется содержимое, а не только расширение или MIME. Сервер уменьшает изображение до 1024 × 1024 с сохранением пропорций, пересохраняет в PNG, убирает исходные метаданные и выбирает имя файла. Для этого добавлена Backend-зависимость Pillow; меры обработки основаны на [документации Pillow](https://pillow.readthedocs.io/en/stable/handbook/security.html).

Ответ `200` — объект регистрации с относительным `profile.avatar_url: "/api/v1/registration/avatar/"`. Этот URL читается **с текущей сессией**, относится только к своему аватару и не является публичной ссылкой. Для изображения нужен обычный запрос браузера с cookie через тот же origin; оптимизатор Next/Image на сервере не передаёт сессию автоматически, поэтому выбор способа показа согласует разработчик Frontend. Blob URL предпросмотра и внешний Telegram photo URL в JSON профиля не сохраняются. Backend не скачивает изображение по клиентской ссылке.

`GET /api/v1/registration/avatar/` — бинарный `image/png`, без кэширования; если аватара нет — `404`. `DELETE` без тела, с CSRF — `204`, повторное удаление допустимо. Другой пользователь по этому маршруту не может получить чужой аватар. Для публичных карточек понадобится отдельное согласование публичного формата.

Файлы хранятся в `DJANGO_MEDIA_ROOT`, по умолчанию `apps/api/media/`, и исключены из Git. Прямая раздача этой папки через веб-сервер не включается. При размещении нужны постоянное файловое хранилище и его резервная копия вместе с PostgreSQL. Предыдущий файл удаляется после успешного сохранения нового; при обычной ошибке БД новый файл очищается. Как и у обычного файлового хранилища, аварийное завершение процесса между записью файла и фиксацией БД может оставить неиспользуемый файл — для размещения потребуется периодическая сверка.

Прежнее performer.portfolio остаётся текстом и не считается коллекцией подтверждённых примеров. Новые HTTP(S)-ссылки и PNG/JPEG/WebP/PDF до 10 МиБ хранятся отдельными PortfolioExample с приватной выдачей владельцу/разрешённому модератору. Публичность не включена. Сервер не скачивает URL. Подробные методы, ограничения и повторы централизованы в [API_CONTRACT.md](API_CONTRACT.md), разделе расширений STUDLY 2.

## Что подключить другу

В [RegistrationClient](https://github.com/lex44lh/Studly/blob/893a6fd/apps/web/src/types/registration.ts) явно указано, что это модель интерфейса, а не Django wire contract. Нужен адаптер: `displayName → display_name`, `studyYear → study_year`, `specializations → specialization_ids` при записи, обратное отображение при чтении. `avatarFile` уходит отдельным multipart-запросом, `avatarUrl` из blob не записывается.

`loadDraft` подключается к GET registration, список — к GET specializations со всеми нужными страницами. При переходах нужно вызывать PATCH; при финальном действии — сначала дождаться PATCH/загрузки, затем вызвать complete. «Заполнить позже» сохраняет `performer_skipped: true` и тоже завершает общую регистрацию через complete. Сохранённый `current_step` используется вместе с проверкой обязательных полей на клиенте.

Следующие проверки совместно ещё не выполнены: настоящие cookie через Next.js-прокси, Telegram-вход в браузере, восстановление после перезапуска вкладки с сохранением на Django, multipart через прокси, показ приватного аватара. Запуск UI из другой ветки не считается выполненной интеграцией. HTTPS и реальные OIDC-настройки остаются внешними условиями первого сайта.
