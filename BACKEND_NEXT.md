## План реализации

1. Добавить статусы услуги `pending`, `published`, `rejected`. Новая пользовательская услуга всегда `pending`. Существующие демонстрационные записи сохранить видимыми с признаком `is_demo`; прочие старые записи отправить на модерацию.
2. Добавить защищённые сессией и CSRF создание услуги и просмотр своих заявок. Исполнитель определяется на сервере. Клиент не может назначить себе статус, другого исполнителя или признак демонстрационной записи.
3. Во всех публичных маршрутах показывать только опубликованные услуги; скрытые записи и профили без опубликованных услуг возвращают `404`.
4. Подключить стандартную административную панель Django только для просмотра услуг и решений модератора. Право модерации отдельное; действия применяются к ожидающим решения реальным услугам и записываются в журнал Django. Редактирование содержания, повторная подача и снятие с публикации требуют отдельных правил и пока не добавляются.
5. Добавить `/api/v1/ready/`: проверка PostgreSQL с `200` или `503`, без раскрытия ошибок соединения. `/health/` продолжает проверять только HTTP.
6. Описать действующий API и порядок настройки HTTPS/Telegram. Проверить миграции, права доступа, CSRF, отсутствие публикации без модерации и существующие сценарии входа.

Frontend (`apps/web`) не изменяется. Внешние настройки бота не меняются до появления работающего публичного интерфейса. Для фактического постоянного размещения необходимы выбранный хостинг, домен и доступ владельца; этих данных пока нет. Токен Bot API не даёт доступа к BotFather и кабинету хостинга.

## Следующий этап: наблюдение и редактирование услуг

Владелец подтвердил: исполнитель может исправить свою услугу; после сохранения она снова `pending`. Ранее опубликованная услуга скрывается до нового одобрения, отклонённую можно исправить и отправить повторно.

План до начала реализации:

1. Включить стандартный браузерный интерфейс DRF только при `DEBUG=true`, сохранив JSON основным форматом. Добавить навигацию `/api/v1/`. Запускать Backend с автоматической перезагрузкой Python-кода. Открыть Backend в установленном PyCharm и API в браузере. Frontend не изменяется.
2. Добавить `PATCH /api/v1/my/services/{id}/` для владельца с сессией и CSRF. Разрешить те же поля, что при создании; запретить смену владельца, статуса и служебных полей. Валидный непустой PATCH снова отправляет услугу на модерацию; удаление и PUT не добавляются.
3. Сохранять изменение содержания и статуса одной транзакцией с блокировкой записи. Ввести внутренний номер редакции услуги. Модератор перед решением видит содержание и подтверждает именно показанную редакцию через стандартную служебную панель Django; изменившаяся редакция требует повторного просмотра. Это защищает от одобрения текста, который автор успел заменить.
4. Проверить права, CSRF, ошибки без изменения данных, исчезновение из каталога, повторное одобрение, устаревшее/подменённое подтверждение модерации и сохранность демонстрационных записей. Обновить контракт и локальную инструкцию, выполнить серверные тесты и HTTP-проверки.

16 октября 2026 года. Выполняем уже согласованную часть правил, пока владелец описывает критерии статусов и момент фиксации комиссии исполнителя.

1. Добавить публичный `GET /api/v1/services/{id}/quote/`: сервер берёт цену опубликованной услуги из PostgreSQL и возвращает цену, надбавку заказчика 3% и общую сумму в RUB. Отдельный предварительный расчёт нужен разработчику Frontend для будущего оформления заказа.
2. Считать через `Decimal`, округляя комиссию до копеек методом `ROUND_HALF_UP`: половина копейки округляется вверх. Например, 3% от 0,50 ₽ равны 0,015 ₽; комиссия в ответе — 0,02 ₽, итог — 0,52 ₽. Это техническое правило текущего расчёта фиксируется в контракте API.
3. Скрытые и отсутствующие услуги возвращают `404`; неподдерживаемая валюта — `400`. Параметры клиента не могут менять цену или ставку. Ответ содержит ID и редакцию услуги, признак демоданных и запрет кэширования. Это текущий предварительный расчёт: он не фиксирует условия заказа и не резервирует цену.
4. API выполняет только чтение. Добавление или изменение заказа, списание, зачисление заработка и создание выплаты здесь отсутствуют. Цена 0 допустима в текущем каталоге и даёт нулевой расчёт; правила бесплатных заказов этим не определяются. Комиссия исполнителя в ответ не включается, потому что её основание и момент фиксации ещё обсуждаются.
5. Проверить API, денежное округление и большие суммы, невозможность подмены цены, видимость после редактирования и повторной публикации, демоданные, неподдерживаемые методы и отсутствие записи. Выполнить серверные тесты и проверки Django; обновить контракт. Frontend, зависимости и настройки провайдера не меняются.

После этого требуется завершить правила статусов и расчётов, подтвердить продукт провайдера для накопления и составить план серверных заказов, оплаты и вывода. Для настоящего Telegram-входа на сайте нужны Client Secret и зарегистрированный адрес возврата: [TELEGRAM_SETUP.md](TELEGRAM_SETUP.md). Существующие обработчики входа уже есть; подставной вход в публичный API не добавляется.

Пункты 1–5 выполнены. Добавлен `GET /api/v1/services/{id}/quote/`, точные десятичные суммы и округление надбавки 3% до копеек. Все 85 серверных тестов прошли на отдельной PostgreSQL, включая девять новых тестов расчёта. Проверки Django и миграций прошли; новых миграций и зависимостей нет.

## Последнее ограничение владельца

## Следующий этап: оформление заказа и согласие исполнителя
